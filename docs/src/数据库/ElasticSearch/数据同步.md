

## 同步方案对比

### 双写模式

**概念定义**：在业务代码中，对同一份数据的变更操作同时写入数据库（MySQL）和 Elasticsearch。通常在 Service 层或 DAO 层通过显式调用 ES 客户端 API 完成，是架构最简单、延迟最低的同步方案。

**核心参数**：

| 参数 | 类型 | 说明 |
|------|------|------|
| `BulkProcessor.concurrentRequests` | int | 并发 Bulk 请求数，默认 1 |
| `BulkProcessor.bulkActions` | int | 触发 Bulk 的文档数量阈值，默认 1000 |
| `BulkProcessor.bulkSize` | ByteSizeValue | 触发 Bulk 的字节数阈值，默认 5MB |
| `BulkProcessor.flushInterval` | TimeValue | 定时刷新间隔，默认 1s |
| `RestClientBuilder.maxRetryTimeoutMillis` | int | 最大重试超时，默认 30000ms |

**配置示例**（Java）：

**注意事项与最佳实践**：

- **事务一致性**：MySQL 事务提交前 ES 写入失败会导致脏数据，建议先写 MySQL 再写 ES，ES 写入失败时写入补偿队列（MQ / Redis），由异步任务重试。
- **批量优化**：高并发写入场景必须使用 `BulkProcessor` 聚合批量请求，避免逐条写入导致 ES 集群压力过大。
- **幂等性**：更新操作使用 `doc`（部分更新）或 `index`（全量覆盖），两种方式均为幂等；删除操作使用 `delete` 亦是幂等。
- **适用场景**：业务逻辑简单、数据变更路径单一、对实时性要求极高（毫秒级）的场景。不适合多数据源、多写入路径的复杂业务。
- **ES 8.x 注意**：Java Client 8.x 使用 `co.elastic.clients.elasticsearch` 包，与旧版 `RestHighLevelClient` 不兼容，迁移时需注意 API 变更。

### CDC（Change Data Capture）

**概念定义**：变更数据捕获（CDC）是一种通过监听数据库事务日志（如 MySQL Binlog、PostgreSQL WAL）来捕获数据变更的技术。它将数据库的 INSERT / UPDATE / DELETE 事件实时捕获并推送到下游系统（如 Elasticsearch），实现无侵入的数据同步。

**核心参数**：

| 参数 | 类型 | 说明 |
|------|------|------|
| 同步延迟 | — | 通常 < 100ms（毫秒级），受网络与消费端吞吐影响 |
| 数据完整性 | — | 能捕获所有已提交事务的变更，无丢失风险 |
| 对业务代码侵入性 | — | 零侵入，业务代码无需任何修改 |
| 上游数据源要求 | — | 必须开启 Binlog（MySQL）或 WAL（PostgreSQL），且格式为 ROW |

**配置示例**（Canal 典型拓扑）：

```
MySQL (Binlog ROW)  →  Canal Server  →  Canal Adapter  →  Elasticsearch
                             ↓
                        Zookeeper (HA)
```

**注意事项与最佳实践**：

- **Binlog 格式**：MySQL 必须配置 `binlog-format=ROW`，`STATEMENT` / `MIXED` 格式无法捕获完整行数据变更。
- **起始位点**：全量同步完成后需记录 Binlog 位点（binlog 文件名 + offset），增量同步从此位点启动，避免数据丢失或重复。
- **DDL 变更**：表结构变更（ADD COLUMN / DROP COLUMN）时，CDC 工具可能无法自动感知，需重启或手动同步 Schema 变更。
- **大事务**：单条大事务（如百万行 UPDATE）可能导致 Canal 消费阻塞，上游应避免长事务。

---

### ETL 批量同步

**概念定义**：ETL（Extract-Transform-Load）批量同步通过定时任务（如 Cron）从数据源抽取数据，经过转换处理后批量加载到 Elasticsearch。常见实现方式包括 Logstash JDBC Input、DataX、自定义定时任务等。

**核心参数**：

| 参数 | 类型 | 说明 |
|------|------|------|
| 同步频率 | Cron | 调度周期，如 `*/5 * * * *`（每 5 分钟） |
| 批次大小 | int | 单次抽取的记录数，默认 10000 |
| 增量字段 | 列名 | 用于增量同步的时间戳 / 自增 ID 列，如 `updated_at` |
| 全量覆盖 | boolean | 是否每次全量替换索引，而非增量追加 |

**配置示例**（Cron 定时任务）：

**注意事项与最佳实践**：

- **延迟容忍度**：延迟取决于调度周期，最小粒度受限于数据库查询性能，通常为分钟级，不适合实时性要求高的场景。
- **增量字段选择**：优先使用自增 ID（`AUTO_INCREMENT`）或 `updated_at` 时间戳列；注意时间戳可能因服务器时钟不一致导致数据遗漏。
- **全量 vs 增量**：首次启动执行全量同步，后续采用增量同步；定期（如每日凌晨）执行全量校验，修正增量遗漏。
- **删除感知**：基于时间戳的增量同步无法感知物理删除（DELETE），需通过逻辑删除标志位（`is_deleted`）或对账机制补偿。

---

### 三种方案对比表

| 维度 | 双写模式 | CDC（Canal / Debezium） | ETL 批量同步 |
|------|---------|----------------------|------------|
| 实时性 | 毫秒级 | 毫秒级 | 分钟级 |
| 数据一致性 | 弱（需补偿） | 强（基于事务日志） | 弱（依赖调度） |
| 业务侵入性 | 高（修改代码） | 零侵入 | 零侵入 |
| 架构复杂度 | 低 | 高 | 中 |
| 运维成本 | 低 | 高 | 中 |
| 删除感知 | 天然支持 | 天然支持 | 需逻辑删除 |
| 异构数据源 | 不支持 | 支持 | 支持 |
| 适用规模 | 中小型 | 中大型 | 中大型 |
| 典型工具 | — | Canal / Debezium | Logstash JDBC / DataX |

## Canal

### 架构原理（Canal Server / Canal Adapter / Zookeeper）

**概念定义**：Canal 是阿里巴巴开源的一款基于 MySQL Binlog 的增量数据订阅与消费组件。其核心架构由三部分组成：Canal Server（Binlog 解析与投递）、Canal Adapter（数据适配与落库）、Zookeeper（集群协调与 HA）。

**架构拓扑**：

```
┌─────────┐    Binlog     ┌──────────────┐    TCP/Netty    ┌────────────────┐
│  MySQL   │ ───────────→ │ Canal Server  │ ─────────────→ │ Canal Adapter  │
│ (Master) │              │  (Parser)     │                │  (ES Adapter)  │
└─────────┘              └──────┬───────┘                └───────┬────────┘
                                │                                │
                         ┌──────┴───────┐                        │
                         │  Zookeeper   │                        │
                         │  (HA/协调)    │                ┌───────┴────────┐
                         └──────────────┘                │ Elasticsearch  │
                                                         └────────────────┘
```

**核心参数**：

| 组件 | 参数 | 说明 |
|------|------|------|
| Canal Server | `canal.instance.master.address` | MySQL 主库地址 |
| Canal Server | `canal.instance.dbUsername` | MySQL 复制账号 |
| Canal Server | `canal.instance.filter.regex` | 订阅的表正则，如 `my_db\\..*` |
| Canal Server | `canal.instance.tsdb.enable` | 是否启用 TableMeta 快照 |
| Canal Adapter | `canal.conf.mode` | 运行模式：`tcp` / `kafka` / `rocketMQ` |
| Zookeeper | `canal.zkServers` | ZK 集群地址 |

**配置示例**（Canal Server `instance.properties`）：

```properties
canal.instance.master.address=192.168.1.100:3306
canal.instance.dbUsername=canal
canal.instance.dbPassword=canal@123
canal.instance.filter.regex=my_db\\.products,my_db\\.orders
canal.instance.filter.black.regex=my_db\\._test_.*
canal.instance.tsdb.enable=true
canal.instance.tsdb.dir=${canal.file.data.dir:../conf}/${canal.instance.destination:}
canal.instance.tsdb.url=jdbc:h2:${canal.instance.tsdb.dir}/h2;CACHE_SIZE=1000;MODE=MYSQL;
```

**注意事项与最佳实践**：

- Canal Server 与 Adapter 进程分离部署，Server 负责解析 Binlog，Adapter 负责写入下游，两者通过 TCP 或 MQ 解耦。
- Zookeeper 用于 Canal Server 集群的 HA 协调，保证同一时刻只有一个 Canal Server 实例在消费指定位点。
- Canal 1.1.6+ 支持 ES 8.x，需使用对应的 Adapter 版本。

---

### MySQL Binlog 订阅

**概念定义**：Canal 模拟 MySQL Slave 的交互协议，伪装成 Slave 向 MySQL Master 发送 dump 请求，MySQL Master 收到请求后推送 Binlog 流，Canal 解析后得到行级变更事件。

**核心参数**：

| 参数 | 说明 |
|------|------|
| `binlog-format=ROW` | Binlog 格式必须为 ROW，否则无法获取行级变更 |
| `binlog-row-image=FULL` | 推荐 FULL，确保 UPDATE 前后镜像完整 |
| `server-id` | Canal 伪装 Slave 的 server-id，需与 MySQL 集群内其他实例不冲突 |
| `expire_logs_days` | Binlog 保留天数，建议 >= 7 天 |

**配置示例**（MySQL `my.cnf`）：

```ini
[mysqld]
log-bin=mysql-bin
binlog-format=ROW
binlog-row-image=FULL
server-id=1
expire_logs_days=7
binlog_cache_size=1M
max_binlog_size=500M
```

**Canal 复制账号授权**：

```sql
CREATE USER 'canal'@'%' IDENTIFIED BY 'canal@123';
GRANT SELECT, REPLICATION SLAVE, REPLICATION CLIENT ON *.* TO 'canal'@'%';
FLUSH PRIVILEGES;
```

**注意事项与最佳实践**：

- `server-id` 在 MySQL 主从集群中必须全局唯一，Canal 实例的 `slaveId` 需与所有 Slave 的 `server-id` 不冲突。
- Binlog 过期时间不能过短，否则 Canal 停机期间 Binlog 已被清理，无法恢复增量同步，必须重新全量同步。
- 生产环境推荐 `binlog-row-image=FULL`，确保 UPDATE 操作的 before-image 可用于数据对账。

### Canal Adapter 配置（ES7/ES8）

**概念定义**：Canal Adapter 是 Canal 的客户端适配器，将 Canal Server 投递的增量数据转换为目标存储的写入操作。ES Adapter 负责将行变更事件映射为 ES 的索引 / 更新 / 删除操作。

**核心参数**（ES Adapter `application.yml`）：

| 参数 | 说明 |
|------|------|
| `canal.conf.mode` | 数据消费模式：`tcp`（直连 Server） / `kafka` / `rocketMQ` |
| `canal.conf.srcDataSources.defaultDS.url` | 源库 JDBC URL（用于全量同步） |
| `canal.conf.canalAdapters.outerAdapters.name` | 适配器类型：`es` / `es7` / `es8` |
| `canal.conf.canalAdapters.outerAdapters.hosts` | ES 集群地址 |
| `canal.conf.canalAdapters.outerAdapters.properties.mode` | 写入模式：`rest`（默认） / `transport` |

**配置示例**（Canal Adapter `application.yml`，ES 8.x）：

```yaml
canal.conf:
  mode: tcp
  canalServerHost: 127.0.0.1:11111
  srcDataSources:
    defaultDS:
      url: jdbc:mysql://192.168.1.100:3306/my_db?useUnicode=true
      username: root
      password: root@123
  canalAdapters:
    - instance: example
      groups:
        - groupId: g1
          outerAdapters:
            - name: es8
              hosts: 192.168.1.200:9200
              properties:
                mode: rest
                security.auth: elastic:elastic@123
                cluster.name: my-es-cluster
```

**ES 映射文件**（`es8/products.yml`）：

```yaml
dataSourceKey: defaultDS
destination: example
groupId: g1
esMapping:
  _index: products
  _id: id
  sql: "SELECT p.id, p.name, p.price, p.category_id, p.updated_at
        FROM products p"
  etlCondition: "where p.updated_at >= '{}'"
  commitBatch: 3000
  # 字段映射
  skips:
    - internal_code
  relations:
    category_id:
      name: category
      # 父子文档关联
```

**注意事项与最佳实践**：

- ES 8.x 适配器名称为 `es8`，ES 7.x 为 `es7`，不可混用，否则 API 调用路径不兼容。
- `commitBatch` 根据文档大小调整，过大可能导致 ES 端 Bulk 队列积压，推荐 2000-5000。
- `sql` 字段用于全量同步时的数据查询，必须包含 `_id` 对应字段。
- ES 8.x 默认启用安全认证，`security.auth` 必须配置用户名密码。

### 同步模式（全量 / 增量）

**概念定义**：Canal 支持两种同步模式 —— 全量同步（ETL 模式）将源表全部数据一次性导入 ES；增量同步（实时模式）基于 Binlog 持续捕获变更并实时写入 ES。

**核心参数**：

| 参数 | 说明 |
|------|------|
| `etlCondition` | 全量同步的过滤条件，支持 `{}` 占位符（替换为上次同步时间） |
| `commitBatch` | 全量批处理大小 |
| `syncMode` | 同步模式：`all`（全量） / `incremental`（增量） |

**配置示例**：

```yaml
# 全量同步
esMapping:
  _index: products
  _id: id
  sql: "SELECT * FROM products"
  # 全量同步批大小
  commitBatch: 5000

# 增量同步（基于 Binlog 自动感知）
# 无需额外配置，Canal Server 推送 Binlog 事件后 Adapter 自动处理
```

**全量同步启动命令**：

```bash
# 启动全量同步
curl http://127.0.0.1:8081/etl/es8/products.yml -X POST

# 查询同步状态
curl http://127.0.0.1:8081/etl/es8/products.yml
```

**注意事项与最佳实践**：

- 首次部署时先执行全量同步，再启动增量同步，确保数据完整性。
- 全量同步期间，增量 Binlog 事件会被暂存，全量完成后自动消费积压的增量事件。
- 大表全量同步建议分批执行，`etlCondition` 配合 `{}` 断点续传，避免一次性拉取全表导致 OOM。
- 全量同步过程中源表有大量写入时，需关注 MySQL 主库压力。

### 字段映射与过滤

**概念定义**：Canal Adapter 支持对源表字段进行映射、转换、过滤，将 MySQL 字段值适配为目标 ES 文档字段，支持字段重命名、类型转换、跳过特定字段。

**核心参数**：

| 参数 | 说明 |
|------|------|
| `skips` | 跳过的字段列表（不同步这些字段） |
| `rename` | 字段重命名映射 |
| `relations` | 关联字段映射（多表 JOIN） |
| `sql` | 自定义 SQL 用于字段转换（如 `CONCAT`、`CASE WHEN`） |

**配置示例**：

```yaml
esMapping:
  _index: products
  _id: id
  sql: >
    SELECT
      p.id,
      p.name,
      p.price / 100 AS price_yuan,
      CONCAT('https://cdn.example.com/', p.image) AS image_url,
      CASE WHEN p.status = 1 THEN 'ON_SALE' ELSE 'OFF_SHELF' END AS status_text,
      p.created_at
    FROM products p
  # 跳过敏感字段
  skips:
    - internal_cost
    - supplier_id
  # 字段重命名
  rename:
    old_price: price_original
    brief: description
```

**注意事项与最佳实践**：

- 字段映射在 `sql` 层面通过 SQL 函数实现，灵活度受限于 MySQL 函数能力。
- `skips` 仅跳过字段写入 ES，但 Binlog 中该字段的变更仍会触发 Adapter 处理，如需完全忽略，需在 Canal Server 端配置 `filter.black.field`。
- 复杂字段转换（如 JSON 嵌套、多表聚合）建议在消费端（MQ Consumer）处理，而非在 Adapter SQL 中实现。

### 高可用部署

**概念定义**：Canal 高可用部署通过 Zookeeper 实现 Server 端的故障转移，多台 Canal Server 实例组成集群，同一时刻只有一台处于 Running 状态，其余处于 Standby 状态，主节点故障时自动切换。

**核心参数**：

| 参数 | 说明 |
|------|------|
| `canal.zkServers` | Zookeeper 集群地址 |
| `canal.instance.global.spring.xml` | HA 模式配置文件：`classpath:spring/default-instance.xml` |
| `canal.instance.tsdb.spring.xml` | TSDB 配置：`classpath:spring/tsdb/h2-tsdb.xml` |

**配置示例**（Canal Server HA `canal.properties`）：

```properties
canal.zkServers=zk1:2181,zk2:2181,zk3:2181
canal.serverMode=tcp
canal.instance.global.spring.xml=classpath:spring/default-instance.xml
canal.instance.tsdb.spring.xml=classpath:spring/tsdb/h2-tsdb.xml
```

**部署拓扑**：

```
                 ┌──────────────────┐
                 │   Zookeeper 集群   │
                 └────────┬─────────┘
                          │ (选举 Leader)
          ┌───────────────┼───────────────┐
          │               │               │
   ┌──────┴──────┐ ┌──────┴──────┐ ┌──────┴──────┐
   │ Canal Server│ │ Canal Server│ │ Canal Server│
   │  (Running)  │ │  (Standby)  │ │  (Standby)  │
   └──────┬──────┘ └─────────────┘ └─────────────┘
          │
   ┌──────┴──────┐
   │Canal Adapter│
   └──────┬──────┘
          │
   ┌──────┴──────┐
   │Elasticsearch│
   └─────────────┘
```

**注意事项与最佳实践**：

- Zookeeper 集群建议 3 节点或 5 节点（奇数），保证选举可靠性。
- Canal Server 故障切换期间（通常 < 30s），增量数据会积压在 MySQL Binlog 中，切换完成后自动追赶。
- 配合 Canal Adapter 的 HA 时，建议 Adapter 无状态部署，多个 Adapter 实例通过 MQ 消费同一份数据，自然实现负载均衡。
- TSDB（TableMeta Snapshot）建议使用 H2 或 MySQL 持久化，避免重启后丢失表结构元数据。

## Canal + 消息队列

### Canal + RocketMQ 架构

**概念定义**：Canal Server 将 Binlog 变更事件直接投递到 RocketMQ Topic，下游消费者（可以是 Canal Adapter 或自定义 Java 应用）从 RocketMQ 消费消息并写入 Elasticsearch。该架构实现了源头解析与目标写入的完全解耦。

**架构拓扑**：

```
MySQL  →  Canal Server  →  RocketMQ  →  Consumer Group  →  Elasticsearch
                              │
                     ┌────────┴────────┐
                     │  NameServer 集群  │
                     └─────────────────┘
```

**核心参数**（Canal Server `canal.properties`）：

| 参数 | 说明 |
|------|------|
| `canal.serverMode` | 设置为 `rocketMQ` |
| `rocketmq.producer.group` | 生产者组名 |
| `rocketmq.namesrv.addr` | NameServer 地址 |
| `rocketmq.retry.times.when.send.failed` | 发送失败重试次数 |

**配置示例**：

```properties
canal.serverMode=rocketMQ
rocketmq.producer.group=canal-producer
rocketmq.namesrv.addr=namesrv1:9876;namesrv2:9876
rocketmq.retry.times.when.send.failed=3
rocketmq.enable.message.trace=true
```

**注意事项与最佳实践**：

- 每个 MySQL 实例对应一个 RocketMQ Topic，Topic 命名规则：`{destination}` 或 `canal-{destination}`。
- 消费者建议使用集群消费模式（`CLUSTERING`），同一 Consumer Group 内的消费者分摊消费，避免重复处理。
- 消息顺序性：Canal 保证同一行数据的有序投递，但不同行之间不保证顺序。
- 消费失败需配合 RocketMQ 重试机制（默认 16 次），超过重试次数进入死信队列。

---

### Canal + Kafka 架构

**概念定义**：Canal Server 将 Binlog 变更事件投递到 Kafka Topic，下游消费者（Canal Adapter 或自定义 Consumer）从 Kafka 消费消息并写入 Elasticsearch。Kafka 的高吞吐和持久化能力使其成为大规模数据同步的首选 MQ。

**架构拓扑**：

```
MySQL  →  Canal Server  →  Kafka  →  Consumer Group  →  Elasticsearch
                              │
                     ┌────────┴────────┐
                     │  Kafka Broker 集群 │
                     └─────────────────┘
```

**核心参数**：

| 参数 | 说明 |
|------|------|
| `canal.serverMode` | 设置为 `kafka` |
| `kafka.bootstrap.servers` | Kafka Broker 地址 |
| `kafka.acks` | 生产者 ACK 级别：`all`（推荐） |
| `kafka.compression.type` | 压缩类型：`lz4` / `snappy` |
| `kafka.batch.size` | 批量发送大小（字节） |

**配置示例**：

```properties
canal.serverMode=kafka
kafka.bootstrap.servers=broker1:9092,broker2:9092,broker3:9092
kafka.acks=all
kafka.compression.type=lz4
kafka.batch.size=16384
kafka.linger.ms=5
kafka.retries=3
```

**注意事项与最佳实践**：

- Kafka Topic 分区数建议 >= 消费者实例数，充分利用并行消费能力。
- `acks=all` 确保消息不丢失，但会略微降低吞吐，数据一致性场景必选。
- 同一行数据的变更必须路由到同一分区（按主键 Hash），保证有序消费。
- Kafka 消息保留时间建议 >= 7 天，留足故障恢复窗口。

| 扩展性 | 有限 | 高（消费者水平扩展） |
| 数据回溯 | 不支持 | 支持（MQ 消息重放） |

**概念定义**：在 MQ 消费场景下，由于网络重试、消费者 Rebalance、Canal 重复投递等原因，同一条 Binlog 事件可能被消费多次。幂等处理确保重复消费不会导致 ES 中数据错误。

| 基于业务时间 | 用 `updated_at` 字段判断，只写入更新时间更新的数据 |
| 基于唯一 ID | 使用 `index` 操作天然幂等（相同 `_id` 多次写入结果一致） |

- `ExternalGte` 版本类型确保只有版本号 >= 当前版本的数据才被写入，适合 Binlog 位点场景。

## Logstash

### JDBC Input Plugin

**概念定义**：Logstash JDBC Input Plugin 允许 Logstash 通过 JDBC 连接关系型数据库，执行 SQL 查询并将结果集导入 Elasticsearch。它支持定时调度、增量追踪、多表查询等特性，是 Logstash 实现数据库同步的核心插件。

**核心参数**：

| 参数 | 类型 | 说明 |
|------|------|------|
| `jdbc_driver_library` | string | JDBC 驱动 JAR 路径 |
| `jdbc_driver_class` | string | 驱动类名，如 `com.mysql.cj.jdbc.Driver` |
| `jdbc_connection_string` | string | JDBC 连接串 |
| `jdbc_user` / `jdbc_password` | string | 数据库认证 |
| `statement` | string | 需要执行的 SQL 查询 |
| `schedule` | string | Cron 调度表达式 |
| `use_column_value` | boolean | 是否使用列值作为增量追踪依据 |
| `tracking_column` | string | 增量追踪列，如 `updated_at` 或 `id` |
| `last_run_metadata_path` | string | 上次运行状态持久化路径 |

**配置示例**（`pipelines/mysql-to-es.conf`）：

```
input {
  jdbc {
    jdbc_driver_library => "/opt/logstash/drivers/mysql-connector-j-8.0.33.jar"
    jdbc_driver_class => "com.mysql.cj.jdbc.Driver"
    jdbc_connection_string => "jdbc:mysql://192.168.1.100:3306/my_db?useSSL=false&serverTimezone=Asia/Shanghai"
    jdbc_user => "reader"
    jdbc_password => "reader@123"
    statement => "SELECT * FROM products WHERE updated_at > :sql_last_value"
    schedule => "*/30 * * * *"
    use_column_value => true
    tracking_column => "updated_at"
    tracking_column_type => "timestamp"
    last_run_metadata_path => "/opt/logstash/metadata/.products_last_run"
    clean_run => false
    jdbc_paging_enabled => true
    jdbc_page_size => 10000
  }
}

filter {
  # 字段转换
  mutate {
    rename => { "product_name" => "name" }
    remove_field => ["@version", "internal_cost"]
  }
}

output {
  elasticsearch {
    hosts => ["https://192.168.1.200:9200"]
    index => "products"
    document_id => "%{id}"
    user => "elastic"
    password => "elastic@123"
    ssl => true
    ssl_certificate_verification => false
  }
}
```

**注意事项与最佳实践**：

- 必须将 JDBC 驱动 JAR 放入 `logstash-core/lib/jars/` 或通过 `jdbc_driver_library` 指定路径。
- `jdbc_page_size` 需根据单条记录大小调整，过大会导致 Logstash 内存溢出，过小则增加数据库查询次数。
- `clean_run => true` 会清除上次运行记录，导致全量重新同步，生产环境慎用。

### 定时全量同步

**概念定义**：定时全量同步通过 Logstash JDBC Input 的 `schedule` 参数按固定周期执行 SQL 查询，每次执行将结果集全量写入（覆盖）ES 索引。适用于数据量可控、对实时性要求不高的场景。

**核心参数**：

| 参数 | 说明 |
|------|------|
| `schedule` | Cron 表达式，如 `0 2 * * *`（每日凌晨 2 点） |
| `clean_run` | `true` 时忽略 `last_run_metadata_path`，视为首次运行 |
| `action` | ES Output 写入动作：`index`（默认） / `create` / `update` |

**配置示例**：

```
input {
  jdbc {
    jdbc_connection_string => "jdbc:mysql://192.168.1.100:3306/my_db"
    jdbc_user => "reader"
    jdbc_password => "reader@123"
    statement => "SELECT * FROM products"
    schedule => "0 3 * * *"          # 每日凌晨3点全量同步
    clean_run => false
    jdbc_paging_enabled => true
    jdbc_page_size => 20000
  }
}

output {
  elasticsearch {
    hosts => ["https://192.168.1.200:9200"]
    index => "products"
    document_id => "%{id}"
    action => "index"
    user => "elastic"
    password => "elastic@123"
    ssl => true
  }
}
```

**注意事项与最佳实践**：

- 全量同步期间建议先写入临时索引（如 `products_tmp`），完成后通过 `_reindex` 或别名切换，避免同步期间查询读取到不一致数据。
- 全量同步数据量大时，可调整 `pipeline.workers` 和 `pipeline.batch.size` 优化吞吐。
- 需监控全量同步耗时，确保在下一轮调度前完成，避免任务堆积。

---

### 增量同步（基于时间戳）

**概念定义**：增量同步通过 `tracking_column` 记录上次同步的最大值（时间戳或自增 ID），每次调度仅查询 `> :sql_last_value` 的记录，实现只同步变更数据，大幅降低同步开销。

**核心参数**：

| 参数 | 说明 |
|------|------|
| `use_column_value` | 必须为 `true` |
| `tracking_column` | 增量追踪列，推荐 `updated_at` 或自增 `id` |
| `tracking_column_type` | 列类型：`numeric` / `timestamp` |
| `last_run_metadata_path` | 持久化上次追踪值 |

**配置示例**：

```
input {
  jdbc {
    # ... 连接配置省略
    statement => "SELECT * FROM products WHERE updated_at > :sql_last_value ORDER BY updated_at ASC"
    use_column_value => true
    tracking_column => "updated_at"
    tracking_column_type => "timestamp"
    last_run_metadata_path => "/opt/logstash/metadata/.products_incr"
    schedule => "*/1 * * * *"          # 每分钟增量同步
    clean_run => false
  }
}
```

**注意事项与最佳实践**：

- `:sql_last_value` 是 Logstash 内置占位符，首次运行时值为 `1970-01-01 00:00:00`（timestamp 类型）或 `0`（numeric 类型）。
- 时间戳列必须建索引，否则大表扫描性能极差。建议 `updated_at` 列添加 `INDEX`。
- 基于时间戳的增量同步无法感知物理删除，需配合逻辑删除或定期全量对账。
- 多实例部署时，`last_run_metadata_path` 需指向共享存储（如 NFS / 分布式文件系统），避免各实例独立追踪导致数据不一致。

### Pipeline 配置（Input / Filter / Output）

**概念定义**：Logstash Pipeline 由 Input（数据源）、Filter（数据转换）、Output（数据目标）三个阶段组成，采用声明式配置，以管道方式串联数据处理流程。

**核心参数**：

| 阶段 | 关键参数 | 说明 |
|------|---------|------|
| Input | `jdbc` | 数据库输入插件 |
| Filter | `mutate` | 字段增删改、类型转换、重命名 |
| Filter | `ruby` | 自定义 Ruby 脚本处理 |
| Filter | `grok` | 正则提取结构化字段 |
| Output | `elasticsearch` | ES 输出插件 |
| Pipeline | `pipeline.workers` | 工作线程数（默认 CPU 核数） |
| Pipeline | `pipeline.batch.size` | 批次大小（默认 125） |

**完整 Pipeline 配置示例**：

```
input {
  jdbc {
    jdbc_driver_library => "/opt/logstash/drivers/mysql-connector-j-8.0.33.jar"
    jdbc_driver_class => "com.mysql.cj.jdbc.Driver"
    jdbc_connection_string => "jdbc:mysql://192.168.1.100:3306/my_db"
    jdbc_user => "reader"
    jdbc_password => "reader@123"
    statement => "SELECT * FROM products WHERE updated_at > :sql_last_value"
    schedule => "*/30 * * * *"
    use_column_value => true
    tracking_column => "updated_at"
    tracking_column_type => "timestamp"
    last_run_metadata_path => "/opt/logstash/metadata/.products"
    jdbc_paging_enabled => true
    jdbc_page_size => 10000
  }
}

filter {
  # 字段重命名
  mutate {
    rename => {
      "product_name" => "name"
      "product_price" => "price"
    }
    remove_field => ["@version", "@timestamp", "internal_cost"]
  }

  # 类型转换
  mutate {
    convert => {
      "price" => "float"
      "stock" => "integer"
      "is_active" => "boolean"
    }
  }

  # 添加计算字段
  ruby {
    code => "
      price_cents = event.get('price').to_f * 100
      event.set('price_cents', price_cents.to_i)
    "
  }

  # JSON 字段解析
  json {
    source => "attributes_json"
    target => "attributes"
    remove_field => ["attributes_json"]
  }
}

output {
  elasticsearch {
    hosts => ["https://192.168.1.200:9200"]
    index => "products"
    document_id => "%{id}"
    user => "elastic"
    password => "elastic@123"
    ssl => true
    ssl_certificate_verification => false
    manage_template => false
    template_name => "products_template"
  }

  # 错误处理：写入死信索引
  if "_elasticsearch_index_failed" in [tags] {
    file {
      path => "/opt/logstash/failures/products_failed_%{+YYYY-MM-dd}.json"
      codec => json_lines
    }
  }
}
```

**注意事项与最佳实践**：

- `manage_template => false` 在 ES 8.x 中建议关闭，由应用侧通过 Index Template 管理 Mapping，避免 Logstash 自动推断类型错误。
- `remove_field` 移除 `@version`、`@timestamp` 等 Logstash 内部字段，减少 ES 存储开销。
- Filter 阶段异常可使用 `tag_on_failure` 打标签，配合条件判断写入死信队列。

### 多表关联同步

**概念定义**：多表关联同步指将 MySQL 中多张关联表（如 `products` + `categories`）的数据通过 JOIN 查询合并为一条 ES 文档，实现数据的反规范化存储，提升搜索查询效率。

**核心参数**：

| 参数 | 说明 |
|------|------|
| `statement` | 包含 JOIN 的 SQL 查询 |
| `jdbc_paging_enabled` | JOIN 查询必须启用分页，否则 OOM |
| `use_column_value` | 增量字段必须属于主表，避免 JOIN 导致重复 |

**配置示例**：

```
input {
  jdbc {
    # ... 连接配置省略
    statement => "
      SELECT
        p.id, p.name, p.price, p.stock, p.updated_at,
        c.id AS category_id, c.name AS category_name,
        b.id AS brand_id, b.name AS brand_name,
        GROUP_CONCAT(t.name SEPARATOR ',') AS tags
      FROM products p
      LEFT JOIN categories c ON p.category_id = c.id
      LEFT JOIN brands b ON p.brand_id = b.id
      LEFT JOIN product_tags pt ON p.id = pt.product_id
      LEFT JOIN tags t ON pt.tag_id = t.id
      WHERE p.updated_at > :sql_last_value
      GROUP BY p.id
      ORDER BY p.updated_at ASC
    "
    use_column_value => true
    tracking_column => "updated_at"
    tracking_column_type => "timestamp"
    jdbc_paging_enabled => true
    jdbc_page_size => 5000
    schedule => "*/30 * * * *"
  }
}

output {
  elasticsearch {
    hosts => ["https://192.168.1.200:9200"]
    index => "products"
    document_id => "%{id}"
    user => "elastic"
    password => "elastic@123"
    ssl => true
  }
}
```

**注意事项与最佳实践**：

- 多表 JOIN 查询性能显著低于单表查询，`tracking_column` 必须在主表上建立索引，且增量字段必须属于主表。
- 关联表数据变更不会触发增量同步（如 `categories` 表更新），需要额外 Pipeline 或在应用层触发关联数据刷新。
- `GROUP_CONCAT` 拼接的字段注意长度限制（默认 1024），可通过 `SET SESSION group_concat_max_len = 10240` 调大。
- 复杂 JOIN 场景建议使用 `jdbc_fetch_size` 与 `jdbc_page_size` 配合，控制内存占用。

## Debezium

### 架构原理（Kafka Connect）

**概念定义**：Debezium 是基于 Kafka Connect 框架构建的 CDC 工具，通过数据库的复制协议（MySQL Binlog / PostgreSQL WAL / MongoDB Oplog）捕获行级变更，并以标准化事件格式发布到 Kafka Topic，实现数据库变更的实时捕获与分发。

**架构拓扑**：

```
┌──────────┐    Binlog    ┌─────────────────┐    Kafka Topic    ┌──────────────┐
│  MySQL    │ ──────────→ │ Debezium         │ ───────────────→ │ Kafka         │
│ (Master)  │             │ Connector (Source)│                  │ (Broker 集群)  │
└──────────┘             └─────────────────┘                  └──────┬───────┘
                                                                     │
                            ┌────────────────────────┐                │
                            │ Elasticsearch Sink      │ ←─────────────┘
                            │ Connector / Consumer     │
                            └────────────────────────┘
```

**核心参数**：

| 参数 | 说明 |
|------|------|
| `connector.class` | `io.debezium.connector.mysql.MySqlConnector` |
| `database.hostname` / `database.port` | MySQL 连接信息 |
| `database.user` / `database.password` | 复制账号 |
| `database.server.id` | Debezium 的 server-id（全局唯一） |
| `database.server.name` | 服务名称，作为 Kafka Topic 前缀 |
| `table.include.list` | 订阅的表列表 |
| `snapshot.mode` | 快照模式：`initial` / `schema_only` / `never` |
| `offset.storage` | Offset 存储：Kafka Topic 或文件 |

**配置示例**（Debezium MySQL Connector JSON）：

```json
{
  "name": "products-connector",
  "config": {
    "connector.class": "io.debezium.connector.mysql.MySqlConnector",
    "database.hostname": "192.168.1.100",
    "database.port": "3306",
    "database.user": "debezium",
    "database.password": "debezium@123",
    "database.server.id": "184054",
    "database.server.name": "my_db",
    "table.include.list": "my_db.products,my_db.orders",
    "database.history.kafka.bootstrap.servers": "broker1:9092,broker2:9092",
    "database.history.kafka.topic": "schema-changes.my_db",
    "snapshot.mode": "initial",
    "snapshot.locking.mode": "minimal",
    "include.schema.changes": true,
    "transforms": "unwrap",
    "transforms.unwrap.type": "io.debezium.transforms.ExtractNewRecordState",
    "transforms.unwrap.drop.tombstones": false,
    "key.converter": "org.apache.kafka.connect.json.JsonConverter",
    "value.converter": "org.apache.kafka.connect.json.JsonConverter"
  }
}
```

**注意事项与最佳实践**：

- Debezium 的 MySQL 账号需具备 `SELECT`、`RELOAD`、`SHOW DATABASES`、`REPLICATION SLAVE`、`REPLICATION CLIENT` 权限。
- `snapshot.mode=initial` 在首次启动时执行全量快照，快照完成后自动切换为增量模式。
- `ExtractNewRecordState` SMT（Single Message Transform）用于提取 `after` 字段，去除 Debezium 事件包装，简化下游消费。
- Offset 存储于 Kafka 内部 Topic，Connector 重启后自动从上次 Offset 恢复，无需外部状态管理。

### Flink CDC 集成

**概念定义**：Flink CDC 是 Apache Flink 生态中的 CDC 连接器，与 Debezium 引擎深度集成，可直接在 Flink SQL / DataStream 中消费 CDC 事件并执行实时 ETL 转换后写入 Elasticsearch，实现端到端的流式数据同步。

**核心参数**：

| 参数 | 说明 |
|------|------|
| `connector` | `mysql-cdc`（Flink CDC Connector） |
| `hostname` / `port` | MySQL 连接 |
| `database-name` / `table-name` | 库表过滤 |
| `server-id` | Flink CDC 任务的 server-id 范围 |
| `scan.startup.mode` | 启动模式：`initial` / `latest-offset` / `timestamp` |

**配置示例**（Flink SQL）：

```sql
-- 创建 MySQL CDC 源表
CREATE TABLE products_source (
    id BIGINT,
    name STRING,
    price DECIMAL(10, 2),
    stock INT,
    category_id BIGINT,
    updated_at TIMESTAMP(3),
    PRIMARY KEY (id) NOT ENFORCED
) WITH (
    'connector' = 'mysql-cdc',
    'hostname' = '192.168.1.100',
    'port' = '3306',
    'username' = 'flink',
    'password' = 'flink@123',
    'database-name' = 'my_db',
    'table-name' = 'products',
    'server-id' = '5400-5404',
    'scan.startup.mode' = 'initial'
);

-- 创建 ES Sink 表
CREATE TABLE products_sink (
    id BIGINT,
    name STRING,
    price DECIMAL(10, 2),
    stock INT,
    category_id BIGINT,
    updated_at TIMESTAMP(3),
    PRIMARY KEY (id) NOT ENFORCED
) WITH (
    'connector' = 'elasticsearch-7',
    'hosts' = 'https://192.168.1.200:9200',
    'index' = 'products',
    'username' = 'elastic',
    'password' = 'elastic@123',
    'sink.bulk-flush.max-actions' = '1000',
    'sink.bulk-flush.interval' = '1s'
);

-- 实时同步
INSERT INTO products_sink
SELECT * FROM products_source;
```

**注意事项与最佳实践**：

- Flink CDC 2.x 基于 Debezium 引擎，`server-id` 需为每个并行度分配一个独立 ID，通过范围指定（如 `5400-5404` 表示并行度 5）。
- `scan.startup.mode=initial` 首次启动执行全量快照，后续基于 Binlog 增量；`latest-offset` 跳过全量仅做增量。
- ES Sink Connector 需注意版本匹配：ES 8.x 需使用 `elasticsearch-7` Connector（Flink 官方暂未提供 ES 8 专用 Connector），部分 API 可能存在兼容性问题。
- Checkpoint 机制保证了 Flink CDC 的 Exactly-Once 语义，故障恢复后不会重复或丢失数据。

### 与 Canal 对比

| 维度 | Canal | Debezium |
|------|-------|----------|
| 生态依赖 | 自研，依赖 Zookeeper（HA） | 基于 Kafka Connect，依赖 Kafka |
| 架构复杂度 | 中（Server + Adapter） | 高（Kafka + Connect + Connector） |
| 数据源支持 | MySQL（主要）、MariaDB | MySQL、PostgreSQL、MongoDB、Oracle、SQL Server 等 |
| Schema 变更感知 | 不支持自动感知 | 支持（Schema History Topic） |
| 数据格式 | Protobuf（Canal 自定义） | JSON / Avro（标准化） |
| 活跃度 | 较低（2023 年后更新放缓） | 高（活跃维护，Red Hat 支持） |
| MQ 集成 | 原生支持 RocketMQ / Kafka | 仅 Kafka（原生） |
| 全量同步 | 内置 ETL 模式 | 内置 Snapshot 模式 |
| Flink 集成 | 需自行解析 Protobuf | Flink CDC 官方集成 |
| 社区 / 文档 | 中文社区活跃 | 国际化社区，英文文档完善 |

**注意事项与最佳实践**：

- 纯 MySQL 场景且团队技术栈偏 Java / 阿里系，Canal 上手更快，文档更友好。
- 多数据源（MySQL + PostgreSQL + MongoDB）场景，Debezium 是更统一的选择。
- 已有 Kafka 基础设施的团队，Debezium 可直接复用 Kafka 运维体系，减少额外组件。
- 需要 Flink 流计算做实时转换的场景，Flink CDC（Debezium 引擎）是首选方案。

## 数据一致性

### 全量 + 增量对账

**概念定义**：全量 + 增量对账是一种周期性的数据一致性校验机制。全量对账对比源库与 ES 的全量数据，增量对账校验最近一段时间内的变更数据是否完整同步。两者结合可覆盖静态数据与动态数据的完整性校验。

**核心参数**：

| 参数 | 说明 |
|------|------|
| 对账周期 | 全量建议每日凌晨，增量建议每 5-15 分钟 |
| 对账字段 | 主键 + 关键业务字段 + 版本号 / 时间戳 |
| 差异阈值 | 差异率超过阈值时触发告警与自动修复 |

- 全量对账耗时长，需在业务低峰期执行，避免对源库和 ES 造成过大压力。
- 对账期间数据持续变更可能导致"假阳性"差异，可在对账结果中标注时间窗口，对差异数据二次校验。
- 对账任务需记录执行日志与结果快照，便于问题追溯与趋势分析。

**概念定义**：抽样一致性检查通过统计学抽样方法（随机抽样、分层抽样、时间窗口抽样）从数据集中选取部分样本进行比对，以较低的成本快速评估整体数据一致性水平，是日常巡检的轻量级方案。

| 参数 | 说明 |
|------|------|
| 抽样比例 | 建议 0.1% ~ 1%，根据数据量调整 |
| 抽样策略 | 随机抽样 / 分层抽样（按分类 / 时间层） / 热点数据抽样 |
| 检查频率 | 建议每 30 分钟或每小时 |

- `randomScore` 查询在 ES 中对大索引有性能开销，建议在非高峰期执行或限制 `size`。
- 抽样检查结果中的差异率是统计估计值，不能完全代表全量一致性，需结合全量对账交叉验证。

### 数据修复策略

**概念定义**：数据修复策略是在检测到 ES 与源库数据不一致时，对 ES 中的数据进行纠正的机制。修复策略包括单条修复、批量修复、全量重建三种粒度，根据差异规模和紧急程度选择。

**核心参数**：

| 策略 | 适用场景 | 修复延迟 |
|------|---------|---------|
| 单条修复 | 少量差异数据 | 实时 |
| 批量修复 | 中等规模差异 | 分钟级 |
| 全量重建 | 大规模差异 / 索引损坏 | 小时级 |

- 修复前记录差异数据快照，修复后二次校验，确保修复成功。

## Reindex

### Reindex API

**概念定义**：Reindex API 是 Elasticsearch 内置的索引数据迁移 API，可将一个或多个索引中的文档复制到另一个索引中。复制过程中支持字段映射转换、脚本加工、子集筛选，是索引重建、数据结构变更的核心工具。

**核心参数**：

| 参数 | 说明 |
|------|------|
| `source.index` | 源索引名称（支持通配符、多索引） |
| `source.query` | 过滤条件，仅复制匹配的文档 |
| `source.size` | 限制复制的文档数量 |
| `dest.index` | 目标索引名称 |
| `dest.op_type` | 写入操作类型：`index`（默认） / `create` |
| `conflicts` | 冲突处理：`abort`（默认） / `proceed` |
| `script` | 文档转换脚本 |

**配置示例**：

```json
POST _reindex
{
  "source": {
    "index": "products_v1",
    "query": {
      "range": {
        "created_at": {
          "gte": "2024-01-01"
        }
      }
    },
    "size": 10000
  },
  "dest": {
    "index": "products_v2",
    "op_type": "create"
  },
  "conflicts": "proceed",
  "script": {
    "source": """
      ctx._source.price_yuan = ctx._source.price / 100;
      ctx._source.remove('price');
      ctx._source.index_version = 'v2';
    """,
    "lang": "painless"
  }
}
```

**注意事项与最佳实践**：

- `conflicts=proceed` 在目标索引已存在相同 `_id` 文档时跳过冲突，而非终止整个 Reindex 任务。
- `op_type=create` 确保不覆盖目标索引已有文档，配合 `conflicts=proceed` 实现增量复制。
- Reindex 是同步操作，大索引执行时间可能很长（数小时），建议使用异步 Reindex（`wait_for_completion=false`）。
- 源索引在 Reindex 期间可正常读写，Reindex 读取的是执行时刻的快照数据。

---

### 跨集群迁移

**概念定义**：跨集群 Reindex 通过 `remote` 参数指定源集群，从远程 ES 集群读取文档并写入本地集群，实现跨数据中心、跨版本的索引数据迁移。

**核心参数**：

| 参数 | 说明 |
|------|------|
| `source.remote.host` | 远程集群地址（需在 `elasticsearch.yml` 中预配置） |
| `source.remote.username` | 远程集群认证用户 |
| `source.remote.password` | 远程集群认证密码 |
| `source.remote.socket_timeout` | Socket 超时时间 |
| `source.remote.connect_timeout` | 连接超时时间 |

**配置示例**（`elasticsearch.yml` 白名单配置）：

```yaml
# 在目标集群 elasticsearch.yml 中添加
reindex.remote.whitelist: "source-cluster:9200, source-cluster-2:9200"
```

**跨集群 Reindex 请求**：

```json
POST _reindex
{
  "source": {
    "remote": {
      "host": "https://source-cluster:9200",
      "username": "elastic",
      "password": "elastic@123",
      "socket_timeout": "60s",
      "connect_timeout": "30s"
    },
    "index": "products",
    "query": {
      "match_all": {}
    }
  },
  "dest": {
    "index": "products"
  }
}
```

**注意事项与最佳实践**：

- 远程集群地址必须在 `elasticsearch.yml` 的 `reindex.remote.whitelist` 中预先配置，否则请求被拒绝。
- 跨集群 Reindex 受网络带宽限制，大索引迁移建议使用 `slice` 并行度提升速度。
- 远程集群的 ES 版本兼容性：源集群 ES 版本需与目标集群的 Transport 协议兼容（ES 7.x 可迁移至 ES 8.x）。
- 跨集群 Reindex 不支持 SSL 证书验证的自定义配置，如需 TLS 双向认证，建议使用 Logstash 或自定义脚本。

### 字段映射转换

**概念定义**：Reindex 过程中通过 `script` 参数对源文档进行字段级转换，实现字段重命名、类型转换、数据清洗、默认值填充等操作，在不修改源索引的前提下完成数据模型升级。

**核心参数**：

| 操作 | Script 示例 |
|------|-----------|
| 字段重命名 | `ctx._source.new_name = ctx._source.remove('old_name')` |
| 类型转换 | `ctx._source.price = Double.parseDouble(ctx._source.price_str)` |
| 默认值填充 | `if (ctx._source.status == null) { ctx._source.status = 'ACTIVE' }` |
| 嵌套字段提取 | `ctx._source.city = ctx._source.address?.city` |
| 布尔转换 | `ctx._source.is_active = ctx._source.status == 1` |

**配置示例**：

```json
POST _reindex
{
  "source": {
    "index": "products_v1"
  },
  "dest": {
    "index": "products_v2",
    "pipeline": "products_v2_pipeline"
  },
  "script": {
    "source": """
      // 字段重命名
      ctx._source.product_name = ctx._source.remove('name');
      ctx._source.product_desc = ctx._source.remove('description');

      // 价格转换：分 → 元
      if (ctx._source.price_cents != null) {
        ctx._source.price = ctx._source.price_cents / 100.0;
        ctx._source.remove('price_cents');
      }

      // 默认值
      if (ctx._source.stock == null) {
        ctx._source.stock = 0;
      }

      // 状态码 → 枚举
      def statusMap = ['0':'DELETED', '1':'ACTIVE', '2':'SUSPENDED'];
      ctx._source.status_text = statusMap.getOrDefault(
        String.valueOf(ctx._source.status), 'UNKNOWN');

      // 数组处理
      if (ctx._source.tags instanceof String) {
        ctx._source.tags = ctx._source.tags.splitOnToken(',');
      }
    """,
    "lang": "painless"
  }
}
```

**注意事项与最佳实践**：

- Painless 脚本中 `remove()` 方法返回被移除的值，可用于字段重命名的一行实现。
- 脚本中的 `null` 安全检查（`!= null`）和默认值处理是必备的防御性编程实践。
- 复杂字段转换建议配合 `pipeline` 参数使用 Ingest Pipeline，在文档写入阶段执行转换，保持 Reindex Script 简洁。
- Reindex Script 在大文档量场景下显著影响性能，建议先在小范围测试，评估吞吐后再全量执行。

### 异步 Reindex 与进度监控

**概念定义**：异步 Reindex（`wait_for_completion=false`）将 Reindex 任务提交为后台异步任务，立即返回 Task ID，通过 Task API 查询任务进度、状态，并支持取消任务。适用于大索引长时间迁移场景。

**核心参数**：

| 参数 | 说明 |
|------|------|
| `wait_for_completion` | `false` 时异步执行，返回 Task ID |
| `slices` | 并行度（`auto` 自动分片 / 数字指定） |
| `requests_per_second` | 限速（每秒请求数），如 `-1` 不限速 |

**配置示例**：

```json
POST _reindex?wait_for_completion=false&slices=auto&requests_per_second=5000
{
  "source": {
    "index": "products_v1"
  },
  "dest": {
    "index": "products_v2"
  }
}
```

**返回结果**：

```json
{
  "task": "oTUltX4IQMOUUVeiohTt8A:123456"
}
```

**进度查询**：

```json
GET _tasks/oTUltX4IQMOUUVeiohTt8A:123456
```

**返回示例**：

```json
{
  "completed": false,
  "task": {
    "node": "oTUltX4IQMOUUVeiohTt8A",
    "id": 123456,
    "type": "transport",
    "action": "indices:data/write/reindex",
    "status": {
      "total": 5000000,
      "updated": 0,
      "created": 2300000,
      "deleted": 0,
      "batches": 2300,
      "version_conflicts": 0,
      "noops": 0,
      "retries": {
        "bulk": 0,
        "search": 0
      },
      "throttled_millis": 0,
      "requests_per_second": 5000,
      "throttled_until_millis": 0
    },
    "running_time_in_nanos": 1284567000000
  }
}
```

**取消任务**：

```json
POST _tasks/oTUltX4IQMOUUVeiohTt8A:123456/_cancel
```

**注意事项与最佳实践**：

- `slices` 参数决定并行度：`auto` 根据源索引分片数自动分配，也可手动指定数字（如 `slices=5`），每个 Slice 独立执行，总吞吐倍增。
- `requests_per_second` 限速保护目标集群，避免 Reindex 冲击正常业务写入。建议从较低值（如 1000）逐步上调。
- 进度监控中 `created` + `updated` 之和为已完成文档数，`total` 为预估总数（非精确值）。
- 异步 Reindex 任务在 ES 节点重启后丢失，需重新提交。大索引 Reindex 建议配合定时检查脚本，任务失败自动重试。
