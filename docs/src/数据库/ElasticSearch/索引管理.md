

## 索引生命周期管理（ILM）

### ILM 概述

**概念定义**

ILM（Index Lifecycle Management）是 Elasticsearch 提供的索引自动化管理机制，将索引的完整生命周期划分为五个阶段，每个阶段可配置一组 Action，当索引满足过渡条件时自动进入下一阶段。ILM 的核心价值在于：减少人工运维成本、降低热节点存储压力、自动归档冷数据。

ILM 的五个阶段按温度递减排列：

| 阶段 | 说明 | 典型用途 |
|------|------|----------|
| Hot | 索引正在被频繁写入和查询 | 实时写入，高 IOPS |
| Warm | 索引不再写入，但仍有查询需求 | 只读索引，中等 IOPS |
| Cold | 索引查询频率很低 | 低 IOPS，可接受延迟 |
| Frozen | 索引几乎不被查询 | 极低成本存储 |
| Delete | 索引已过期 | 释放存储空间 |

**核心参数表**

| 参数 | 类型 | 说明 |
|------|------|------|
| `phases` | Object | 定义各阶段配置 |
| `phases.hot` | Object | 热阶段配置 |
| `phases.warm` | Object | 温阶段配置 |
| `phases.cold` | Object | 冷阶段配置 |
| `phases.frozen` | Object | 冻结阶段配置 |
| `phases.delete` | Object | 删除阶段配置 |
| `_meta` | Object | 策略元数据（自定义标签） |

**REST API**

```bash
# 查看所有 ILM 策略
curl -X GET "localhost:9200/_ilm/policy?pretty"

# 查看指定策略
curl -X GET "localhost:9200/_ilm/policy/my_policy?pretty"

# 查看 ILM 状态
curl -X GET "localhost:9200/_ilm/status?pretty"

# 手动触发 ILM 执行
curl -X POST "localhost:9200/_ilm/start"
curl -X POST "localhost:9200/_ilm/stop"
```

**注意事项**

- ILM 依赖 `_ilm/policy` 定义的策略，策略需绑定到索引或索引模板。
- 索引必须配置 `index.lifecycle.name` 和 `index.lifecycle.rollover_alias` 才能参与 ILM。
- ILM 默认每 10 分钟执行一次检查（由 `indices.lifecycle.poll_interval` 控制）。
- 阶段过渡依赖 `min_age` 参数，从索引创建时间开始计算，而非从上一阶段完成时间计算。
- Frozen 阶段需要 Elasticsearch 的 Searchable Snapshots 功能（基础 License 及以上）。

---

### Hot 阶段

**概念定义**

Hot 阶段是索引生命周期的起点，负责处理高吞吐写入。在该阶段索引处于活跃写入状态，需要高 IOPS 的存储资源。Hot 阶段的核心目标是：在写入压力可控的前提下，通过 Rollover 自动创建新索引，避免单索引过大。

**核心参数表**

| 参数 | 类型 | 说明 |
|------|------|------|
| `min_age` | String | 进入下一阶段的最小年龄（例：`"30m"`、`"1d"`） |
| `actions.rollover` | Object | 滚动条件配置 |
| `actions.rollover.max_age` | String | 按时间滚动阈值 |
| `actions.rollover.max_size` | String | 按大小滚动阈值 |
| `actions.rollover.max_docs` | Long | 按文档数滚动阈值 |
| `actions.rollover.max_primary_shard_size` | String | 按主分片大小滚动阈值 |
| `actions.set_priority` | Object | 设置索引优先级（值越大恢复优先级越高） |
| `actions.set_priority.priority` | Integer | 优先级值，Hot 阶段建议设 100 |

**REST API**

```bash
# 仅 Hot 阶段的 ILM 策略
curl -X PUT "localhost:9200/_ilm/policy/hot_only_policy" -H 'Content-Type: application/json' -d'
{
  "policy": {
    "phases": {
      "hot": {
        "min_age": "0ms",
        "actions": {
          "rollover": {
            "max_age": "1d",
            "max_size": "50gb",
            "max_primary_shard_size": "30gb"
          },
          "set_priority": {
            "priority": 100
          }
        }
      }
    }
  }
}'
```

**注意事项**

- Hot 阶段必须设置 `min_age: "0ms"`，因为索引创建后立即进入 Hot 阶段。
- Rollover 条件为 OR 关系：满足任一条件即触发滚动。
- 如果未配置 Rollover，索引将一直停留在 Hot 阶段直到 `min_age` 到期。
- Hot 阶段建议使用 `set_priority` 将优先级设为最高（100），确保节点恢复时优先分配。

---

### Warm 阶段

**概念定义**

Warm 阶段在索引完成 Rollover 后进入，此时索引不再写入，转为只读状态。Warm 阶段的典型操作包括：将分片迁移到中等性能节点、执行 Force Merge 减少段数量、缩小主分片以降低内存开销。

**核心参数表**

| 参数 | 类型 | 说明 |
|------|------|------|
| `min_age` | String | 从索引创建时间起算的过渡年龄 |
| `actions.set_priority` | Object | 设置索引优先级，Warm 建议 50 |
| `actions.allocate` | Object | 分片分配策略 |
| `actions.allocate.require` | Object | 节点属性要求（如 `data: warm`） |
| `actions.allocate.number_of_replicas` | Integer | 副本数 |
| `actions.forcemerge` | Object | 强制合并段 |
| `actions.forcemerge.max_num_segments` | Integer | 合并后最大段数，建议 1 |
| `actions.shrink` | Object | 缩容主分片数 |
| `actions.shrink.number_of_shards` | Integer | 目标主分片数 |
| `actions.readonly` | Object | 设为只读 |
| `actions.migrate` | Object | 迁移到其他数据层 |
| `actions.migrate.enabled` | Boolean | 是否启用迁移 |

**REST API**

```bash
curl -X PUT "localhost:9200/_ilm/policy/hot_warm_policy" -H 'Content-Type: application/json' -d'
{
  "policy": {
    "phases": {
      "hot": {
        "min_age": "0ms",
        "actions": {
          "rollover": { "max_size": "50gb", "max_age": "1d" },
          "set_priority": { "priority": 100 }
        }
      },
      "warm": {
        "min_age": "2d",
        "actions": {
          "set_priority": { "priority": 50 },
          "forcemerge": { "max_num_segments": 1 },
          "shrink": { "number_of_shards": 1 },
          "allocate": {
            "number_of_replicas": 1,
            "require": { "data": "warm" }
          }
        }
      }
    }
  }
}'
```

**注意事项**

- Force Merge 操作消耗大量 CPU 和 IO，建议在低峰期执行，且只在不再写入的索引上使用。
- Shrink 操作会创建新索引，源索引名需满足 `shrink-<origin>` 命名规则，且源索引必须设为只读且所有分片在同一节点。
- 从 Hot 过渡到 Warm 基于 `min_age`，该值从索引创建时间开始计算，而非 Rollover 时间。
- 8.x 中 `migrate` action 已标记为 deprecated，推荐使用 `allocate` 配合节点属性。

---

### Cold 阶段

**概念定义**

Cold 阶段用于处理极少被查询的索引。在此阶段，索引通常被迁移到低成本存储节点，并可能降低副本数。8.x 中 Cold 阶段的核心能力是 Searchable Snapshots，可将索引备份到快照仓库后仅保留本地缓存，大幅降低存储成本。

**核心参数表**

| 参数 | 类型 | 说明 |
|------|------|------|
| `min_age` | String | 从索引创建时间起算的过渡年龄 |
| `actions.set_priority` | Integer | 索引优先级，Cold 建议 0 |
| `actions.allocate` | Object | 节点分配策略 |
| `actions.allocate.require` | Object | 如 `data: cold` |
| `actions.allocate.number_of_replicas` | Integer | 副本数，Cold 阶段可设为 0 |
| `actions.searchable_snapshot` | Object | 可搜索快照配置 |
| `actions.searchable_snapshot.snapshot_repository` | String | 快照仓库名称 |
| `actions.searchable_snapshot.force_merge_index` | Boolean | 是否在挂载前先执行 Force Merge |

**REST API**

```bash
curl -X PUT "localhost:9200/_ilm/policy/full_ilm_policy" -H 'Content-Type: application/json' -d'
{
  "policy": {
    "phases": {
      "hot": {
        "min_age": "0ms",
        "actions": {
          "rollover": { "max_size": "50gb", "max_age": "1d" }
        }
      },
      "warm": {
        "min_age": "2d",
        "actions": { "forcemerge": { "max_num_segments": 1 } }
      },
      "cold": {
        "min_age": "7d",
        "actions": {
          "set_priority": { "priority": 0 },
          "allocate": {
            "number_of_replicas": 0,
            "require": { "data": "cold" }
          },
          "searchable_snapshot": {
            "snapshot_repository": "my_repository",
            "force_merge_index": true
          }
        }
      }
    }
  }
}'
```

**注意事项**

- Searchable Snapshot 需要预先配置快照仓库（`_snapshot/my_repository`）。
- 挂载为 Searchable Snapshot 后，索引数据从快照仓库读取，本地仅缓存频繁访问的数据。
- Cold 阶段建议将副本数设为 0，进一步降低存储成本。
- 如果集群没有专门的冷节点，`allocate.require` 可省略。

---

### Frozen 阶段

**概念定义**

Frozen 阶段是索引查询成本最低的阶段。进入 Frozen 阶段后，索引被挂载为 Frozen Searchable Snapshot，仅保留极少的本地缓存，查询延迟较高但存储成本极低。该阶段适用于合规归档、审计日志等场景。

**核心参数表**

| 参数 | 类型 | 说明 |
|------|------|------|
| `min_age` | String | 从索引创建时间起算的过渡年龄 |
| `actions.searchable_snapshot` | Object | 可搜索快照配置 |
| `actions.searchable_snapshot.snapshot_repository` | String | 快照仓库名称 |
| `actions.searchable_snapshot.storage` | String | 存储类型，Frozen 阶段固定为 `"shared_cache"` |

**REST API**

```bash
curl -X PUT "localhost:9200/_ilm/policy/with_frozen_policy" -H 'Content-Type: application/json' -d'
{
  "policy": {
    "phases": {
      "hot": {
        "min_age": "0ms",
        "actions": {
          "rollover": { "max_size": "50gb", "max_age": "1d" }
        }
      },
      "warm": {
        "min_age": "2d",
        "actions": { "forcemerge": { "max_num_segments": 1 } }
      },
      "cold": {
        "min_age": "7d",
        "actions": {
          "searchable_snapshot": {
            "snapshot_repository": "my_repository"
          }
        }
      },
      "frozen": {
        "min_age": "30d",
        "actions": {
          "searchable_snapshot": {
            "snapshot_repository": "my_repository",
            "storage": "shared_cache"
          }
        }
      }
    }
  }
}'
```

**注意事项**

- Frozen 阶段仅在 `fully-populated` 模式下需要显式配置；若 Cold 阶段已挂载为 `shared_cache` 模式的 Searchable Snapshot，则 Frozen 阶段可省略。
- Frozen 索引的查询延迟较高（通常秒级），不适合实时查询场景。
- 需要 Enterprise License 或白金版 License 才能使用 Frozen 阶段的 Searchable Snapshot。
- 查询 Frozen 索引前需显式调用 `POST /_search` 并等待结果，或使用 `ignore_throttled=false` 参数。

---

### Delete 阶段

**概念定义**

Delete 阶段是 ILM 的终点，在索引超过保留期限后自动删除索引以释放存储空间。该阶段不可逆，需谨慎配置 `min_age`。

**核心参数表**

| 参数 | 类型 | 说明 |
|------|------|------|
| `min_age` | String | 从索引创建时间起算的删除年龄 |
| `actions.delete` | Object | 删除动作（通常为空对象） |
| `actions.delete.delete_searchable_snapshot` | Boolean | 是否同时删除关联的快照（默认 `true`） |

**REST API**

```bash
curl -X PUT "localhost:9200/_ilm/policy/with_delete_policy" -H 'Content-Type: application/json' -d'
{
  "policy": {
    "phases": {
      "hot": {
        "min_age": "0ms",
        "actions": {
          "rollover": { "max_size": "50gb", "max_age": "1d" }
        }
      },
      "delete": {
        "min_age": "90d",
        "actions": {
          "delete": {}
        }
      }
    }
  }
}'
```

**注意事项**

- Delete 阶段不可逆，建议 `min_age` 设置足够的缓冲时间。
- 配合快照仓库使用：在删除前确认索引已有快照备份。
- 建议在 `phases` 中不定义 Delete 阶段，而是通过独立的生命周期策略仅限 Delete 操作和 `min_age` 来控制。
- 如果索引是 Data Stream 的一部分，Delete 阶段会删除整个后备索引，但不会删除 Data Stream 本身。

---

### ILM Policy 定义

**概念定义**

ILM Policy 是 ILM 的核心配置单元，一个 JSON 文档描述索引从创建到删除的完整生命周期行为。Policy 定义后，通过索引模板或直接绑定到索引上生效。

**核心参数表**

| 参数 | 类型 | 说明 |
|------|------|------|
| `policy` | Object | 策略根对象 |
| `policy.phases` | Object | 阶段定义（hot/warm/cold/frozen/delete） |
| `policy._meta` | Object | 自定义元数据 |
| `policy.phases.<phase>.min_age` | String | 阶段过渡年龄 |
| `policy.phases.<phase>.actions` | Object | 该阶段执行的动作 |

**REST API**

```bash
# 创建完整 ILM Policy
curl -X PUT "localhost:9200/_ilm/policy/logs_policy" -H 'Content-Type: application/json' -d'
{
  "policy": {
    "_meta": {
      "description": "应用日志保留策略 - 热30天/温60天/冷90天/删180天",
      "project": "app-logging",
      "version": 1
    },
    "phases": {
      "hot": {
        "min_age": "0ms",
        "actions": {
          "rollover": { "max_size": "30gb", "max_age": "1d", "max_docs": 100000000 },
          "set_priority": { "priority": 100 }
        }
      },
      "warm": {
        "min_age": "30d",
        "actions": {
          "set_priority": { "priority": 50 },
          "forcemerge": { "max_num_segments": 1 },
          "shrink": { "number_of_shards": 1 },
          "allocate": { "require": { "data": "warm" }, "number_of_replicas": 1 }
        }
      },
      "cold": {
        "min_age": "60d",
        "actions": {
          "set_priority": { "priority": 0 },
          "searchable_snapshot": { "snapshot_repository": "backup_repo" }
        }
      },
      "delete": {
        "min_age": "180d",
        "actions": { "delete": {} }
      }
    }
  }
}'

# 查看所有策略
curl -X GET "localhost:9200/_ilm/policy?pretty"

# 删除策略
curl -X DELETE "localhost:9200/_ilm/policy/logs_policy"
```

**注意事项**

- Policy 的名称全局唯一，修改已存在的 Policy 会影响所有绑定的索引。
- 删除 Policy 不影响已创建的索引，但新索引无法再引用该 Policy。
- `_meta` 字段不会影响 ILM 行为，用于存放团队自定义元数据。
- 8.x 中新增了 `deprecate` phase（试验性），用于标记即将废弃的索引。

---

### Actions

**概念定义**

Actions 是 ILM 在各阶段执行的具体操作。每个阶段可配置零个或多个 Action，Action 按 `actions` 对象中的定义顺序执行。8.x 支持的 Action 包括：Rollover、Shrink、Force Merge、Freeze、Delete、Allocate、Migrate、Set Priority、Readonly、Searchable Snapshot 等。

---

#### Rollover

**概念定义**：当索引满足指定条件（大小/时间/文档数）时，自动创建新索引并将写入别名指向新索引。

**核心参数表**

| 参数 | 类型 | 说明 |
|------|------|------|
| `max_age` | String | 最大索引年龄（如 `"1d"`） |
| `max_size` | String | 最大索引主分片总大小（如 `"50gb"`） |
| `max_docs` | Long | 最大文档数 |
| `max_primary_shard_size` | String | 最大主分片大小（8.x 新增） |

**REST API**

```bash
curl -X PUT "localhost:9200/_ilm/policy/rollover_action_policy" -H 'Content-Type: application/json' -d'
{
  "policy": {
    "phases": {
      "hot": {
        "min_age": "0ms",
        "actions": {
          "rollover": {
            "max_age": "1d",
            "max_size": "50gb",
            "max_docs": 100000000,
            "max_primary_shard_size": "25gb"
          }
        }
      }
    }
  }
}'
```

**注意事项**：Rollover 条件为 OR 关系；需要配合 `index.lifecycle.rollover_alias` 使用；Rollover 后原索引停止写入，新索引接管写入。

---

#### Shrink

**概念定义**：减少索引的主分片数量，缩小索引以降低内存开销。新分片数必须是原分片数的因子。

**核心参数表**

| 参数 | 类型 | 说明 |
|------|------|------|
| `number_of_shards` | Integer | 目标主分片数 |
| `max_primary_shard_size` | String | （8.x 替代方案）按主分片大小缩容 |

**REST API**

```bash
curl -X PUT "localhost:9200/_ilm/policy/shrink_action_policy" -H 'Content-Type: application/json' -d'
{
  "policy": {
    "phases": {
      "hot": {
        "min_age": "0ms",
        "actions": { "rollover": { "max_size": "50gb" } }
      },
      "warm": {
        "min_age": "2d",
        "actions": {
          "shrink": { "number_of_shards": 1 }
        }
      }
    }
  }
}'
```

**注意事项**：Shrink 前索引必须设为只读；所有分片必须位于同一节点；目标分片数必须是原分片数的因子；新分片数不能为 0 或大于原分片数。

---

#### Force Merge

**概念定义**：强制合并 Lucene 段（Segment），减少段数量以提升查询性能。通常配合 `max_num_segments: 1` 将段合并为一个。

**核心参数表**

| 参数 | 类型 | 说明 |
|------|------|------|
| `max_num_segments` | Integer | 合并后最大段数，建议 1 |
| `index_codec` | String | 可选，指定压缩算法（如 `"best_compression"`） |

**REST API**

```bash
curl -X PUT "localhost:9200/_ilm/policy/forcemerge_action_policy" -H 'Content-Type: application/json' -d'
{
  "policy": {
    "phases": {
      "hot": {
        "min_age": "0ms",
        "actions": { "rollover": { "max_size": "50gb" } }
      },
      "warm": {
        "min_age": "2d",
        "actions": {
          "forcemerge": { "max_num_segments": 1, "index_codec": "best_compression" }
        }
      }
    }
  }
}'
```

**注意事项**：Force Merge 消耗大量 CPU/IO；只应在不再写入的索引上执行；合并后索引变为只读；`index_codec` 仅在关闭索引时生效。

---

#### Freeze

**概念定义**：冻结索引使其变为只读，并释放内存中的数据结构。8.x 中 Freeze 已标记为 deprecated，推荐使用 Searchable Snapshot 替代。

**REST API**

```bash
# 8.x 中已不推荐，仅供兼容
curl -X POST "localhost:9200/my_index/_freeze"
curl -X POST "localhost:9200/my_index/_unfreeze"
```

**注意事项**：冻结后索引不可写入；查询需使用 `ignore_throttled=false` 参数；推荐迁移到 Searchable Snapshot。

---

#### Delete

**概念定义**：永久删除索引，释放所有存储空间。

**核心参数表**

| 参数 | 类型 | 说明 |
|------|------|------|
| `delete_searchable_snapshot` | Boolean | 是否同步删除快照（默认 `true`） |

**注意事项**：不可逆操作；建议在删除前做好快照备份。

---

#### Allocate

**概念定义**：控制索引分片在集群节点间的分配策略，包括节点属性过滤、副本数调整。

**核心参数表**

| 参数 | 类型 | 说明 |
|------|------|------|
| `number_of_replicas` | Integer | 副本数 |
| `include` | Object | 节点需满足的属性（非空交集） |
| `exclude` | Object | 节点需排除的属性 |
| `require` | Object | 节点必须满足的属性（全部匹配） |
| `total_shards_per_node` | Integer | 每节点最大分片数 |

**REST API**

```bash
curl -X PUT "localhost:9200/_ilm/policy/allocate_action_policy" -H 'Content-Type: application/json' -d'
{
  "policy": {
    "phases": {
      "warm": {
        "min_age": "2d",
        "actions": {
          "allocate": {
            "number_of_replicas": 1,
            "require": { "box_type": "warm" },
            "total_shards_per_node": 10
          }
        }
      }
    }
  }
}'
```

**注意事项**：`require` 条件必须全部满足；`include` 条件满足一个即可；节点属性在 `elasticsearch.yml` 中通过 `node.attr.<name>` 配置。

---

#### Migrate

**概念定义**：将索引从当前数据层迁移到其他数据层（`data_hot` / `data_warm` / `data_cold` / `data_frozen` / `data_content`）。8.x 中已标记为 deprecated，推荐使用 `allocate` 配合节点属性。

**核心参数表**

| 参数 | 类型 | 说明 |
|------|------|------|
| `enabled` | Boolean | 是否启用自动迁移，默认 `false` |

**注意事项**：8.x 中 `migrate` 已不推荐使用；请改用 `index.routing.allocation.include._tier_preference` 配合 `allocate` action。

---

## Rollover 滚动索引

### 按时间滚动

**概念定义**

基于索引创建时间触发 Rollover。当索引年龄超过 `max_age` 阈值时，ILM 自动创建新索引并将写入别名指向新索引。

**核心参数表**

| 参数 | 类型 | 说明 |
|------|------|------|
| `max_age` | String | 最大年龄阈值（`"1h"`、`"1d"`、`"7d"`） |
| `index.lifecycle.rollover_alias` | String | 滚动别名（索引设置中配置） |

**REST API**

```bash
# 创建按时间滚动的模板
curl -X PUT "localhost:9200/_index_template/logs_template" -H 'Content-Type: application/json' -d'
{
  "index_patterns": ["logs-*"],
  "template": {
    "settings": {
      "index.lifecycle.name": "time_rollover_policy",
      "index.lifecycle.rollover_alias": "logs-write"
    }
  }
}'

# 手动触发 Rollover（按时间）
curl -X POST "localhost:9200/logs-write/_rollover?pretty" -H 'Content-Type: application/json' -d'
{
  "conditions": {
    "max_age": "1d"
  }
}'
```

**注意事项**

- `max_age` 从索引创建时间开始计算，单位支持：`ms`、`s`、`m`、`h`、`d`。
- 时间滚动适合日志量稳定的场景，通常结合大小滚动作为兜底条件。
- 如果仅使用 `max_age`，应设置较大的值（如 `1d`），避免过于频繁滚动导致大量小索引。

---

### 按大小滚动

**概念定义**

基于索引主分片总大小触发 Rollover。当索引大小超过 `max_size` 阈值时，自动创建新索引。

**核心参数表**

| 参数 | 类型 | 说明 |
|------|------|------|
| `max_size` | String | 最大主分片总大小（`"10gb"`、`"50gb"`） |
| `max_primary_shard_size` | String | 最大单主分片大小（8.x 新增，推荐） |

**REST API**

```bash
# 手动触发（按大小）
curl -X POST "localhost:9200/logs-write/_rollover?pretty" -H 'Content-Type: application/json' -d'
{
  "conditions": {
    "max_size": "50gb"
  }
}'

# 按主分片大小滚动（8.x 推荐）
curl -X POST "localhost:9200/logs-write/_rollover?pretty" -H 'Content-Type: application/json' -d'
{
  "conditions": {
    "max_primary_shard_size": "30gb"
  }
}'
```

**注意事项**

- `max_size` 计算的是所有主分片的总大小，而非索引总大小（不含副本）。
- 8.x 推荐使用 `max_primary_shard_size` 替代 `max_size`，因为它更精确地反映单分片压力。
- 大小估算有延迟（约 60 秒），实际触发时可能略超阈值。
- 建议 `max_size` 设为 JVM 堆内存的 50% 以内，避免单分片过大。

---

### 按文档数滚动

**概念定义**

基于索引文档数量触发 Rollover。当文档数超过 `max_docs` 阈值时，自动创建新索引。

**核心参数表**

| 参数 | 类型 | 说明 |
|------|------|------|
| `max_docs` | Long | 最大文档数阈值 |

**REST API**

```bash
curl -X POST "localhost:9200/logs-write/_rollover?pretty" -H 'Content-Type: application/json' -d'
{
  "conditions": {
    "max_docs": 100000000
  }
}'
```

**注意事项**

- 文档数统计不区分删除文档（含 `_doc` 计数），删除后不会减少。
- 适合文档大小均匀的场景，不适合文档大小差异大的场景。
- 通常与 `max_size` 组合使用，任一条件满足即触发。

---

### 自动滚动策略

**概念定义**

通过 ILM Policy 将 Rollover 条件自动化，无需手动调用 `_rollover` API。索引模板绑定 ILM Policy 后，新创建的索引自动参与生命周期管理。

**核心参数表**

| 参数 | 类型 | 说明 |
|------|------|------|
| `index.lifecycle.name` | String | ILM 策略名称 |
| `index.lifecycle.rollover_alias` | String | 用于滚动的写入别名 |

**REST API**

```bash
# 步骤1：创建 ILM Policy
curl -X PUT "localhost:9200/_ilm/policy/auto_rollover_policy" -H 'Content-Type: application/json' -d'
{
  "policy": {
    "phases": {
      "hot": {
        "min_age": "0ms",
        "actions": {
          "rollover": {
            "max_age": "1d",
            "max_size": "30gb",
            "max_docs": 50000000,
            "max_primary_shard_size": "20gb"
          }
        }
      },
      "delete": {
        "min_age": "30d",
        "actions": { "delete": {} }
      }
    }
  }
}'

# 步骤2：创建索引模板
curl -X PUT "localhost:9200/_index_template/auto_rollover_template" -H 'Content-Type: application/json' -d'
{
  "index_patterns": ["app-logs-*"],
  "template": {
    "settings": {
      "index.lifecycle.name": "auto_rollover_policy",
      "index.lifecycle.rollover_alias": "app-logs-write"
    }
  }
}'

# 步骤3：创建初始索引并绑定别名
curl -X PUT "localhost:9200/app-logs-000001" -H 'Content-Type: application/json' -d'
{
  "aliases": {
    "app-logs-write": { "is_write_index": true }
  }
}'
```

**注意事项**

- 初始索引必须手动创建，且名称需满足 `*-000001` 格式以便 ILM 递增。
- `is_write_index: true` 是关键设置，确保写入别名指向正确的索引。
- 多个条件组合时，任一条件满足即触发滚动（OR 逻辑）。
- Data Stream 方式可以替代手动创建初始索引（详见 Data Stream 章节）。

---

## 索引模板

### Composable Index Template

**概念定义**

Composable Index Template（可组合索引模板）是 7.8+ 引入的新模板机制，8.x 中已成为默认模板类型。它将旧版 `_template` API 替换为更灵活的层级化模板系统，支持多个模板叠加生效，并由 Component Template 提供可复用的配置片段。

**核心参数表**

| 参数 | 类型 | 说明 |
|------|------|------|
| `index_patterns` | String[] | 索引名称匹配模式（如 `["logs-*", "metrics-*"]`） |
| `template` | Object | 模板配置（settings、mappings、aliases） |
| `composed_of` | String[] | 引用的 Component Template 名称列表 |
| `priority` | Integer | 模板优先级（值越大优先级越高） |
| `version` | Long | 模板版本号 |
| `_meta` | Object | 自定义元数据 |
| `data_stream` | Object | Data Stream 配置（`hidden`、`allow_custom_routing`） |

**REST API**

```bash
# 创建 Composable Index Template
curl -X PUT "localhost:9200/_index_template/logs_template" -H 'Content-Type: application/json' -d'
{
  "index_patterns": ["logs-*"],
  "priority": 100,
  "version": 1,
  "_meta": {
    "description": "应用日志模板"
  },
  "composed_of": ["common_settings", "logs_mappings"],
  "template": {
    "settings": {
      "index.lifecycle.name": "logs_policy",
      "index.lifecycle.rollover_alias": "logs-write",
      "index.number_of_replicas": 1
    },
    "mappings": {
      "properties": {
        "@timestamp": { "type": "date" },
        "level": { "type": "keyword" },
        "message": { "type": "text" }
      }
    }
  }
}'

# 查看所有模板
curl -X GET "localhost:9200/_index_template?pretty"

# 查看指定模板
curl -X GET "localhost:9200/_index_template/logs_template?pretty"

# 删除模板
curl -X DELETE "localhost:9200/_index_template/logs_template"

# 模拟模板匹配（验证哪个模板会匹配给定索引名）
curl -X POST "localhost:9200/_index_template/_simulate_index/logs-2024-01" -H 'Content-Type: application/json' -d'
{
  "index_patterns": ["logs-*"],
  "priority": 100,
  "composed_of": ["common_settings"],
  "template": {
    "settings": { "index.number_of_replicas": 1 }
  }
}'
```

**注意事项**

- 8.x 中 `_template`（旧版）API 仍然可用但不推荐，新项目应使用 `_index_template`。
- `composed_of` 中的 Component Template 按数组顺序叠加，后者的配置覆盖前者。
- 顶层 `template` 中的配置优先级最高，覆盖 `composed_of` 中所有 Component Template 的配置。
- 模板优先级只影响同级 Index Template 之间的冲突，Component Template 之间无优先级概念。

---

### Component Template

**概念定义**

Component Template（组件模板）是可复用的配置片段，被 Composable Index Template 通过 `composed_of` 引用。组件模板将 settings、mappings、aliases 拆分为独立单元，避免重复配置，提升可维护性。

**核心参数表**

| 参数 | 类型 | 说明 |
|------|------|------|
| `template` | Object | 配置片段（settings、mappings、aliases） |
| `_meta` | Object | 自定义元数据 |
| `version` | Long | 版本号 |
| `allow_auto_create` | Boolean | 是否允许自动创建匹配的索引 |

**REST API**

```bash
# 创建 Settings Component Template
curl -X PUT "localhost:9200/_component_template/common_settings" -H 'Content-Type: application/json' -d'
{
  "template": {
    "settings": {
      "index.number_of_shards": 3,
      "index.number_of_replicas": 1,
      "index.refresh_interval": "5s",
      "index.codec": "best_compression"
    }
  },
  "_meta": {
    "description": "通用索引设置"
  }
}'

# 创建 Mappings Component Template
curl -X PUT "localhost:9200/_component_template/logs_mappings" -H 'Content-Type: application/json' -d'
{
  "template": {
    "mappings": {
      "_source": { "enabled": true },
      "dynamic": "strict",
      "properties": {
        "@timestamp": { "type": "date", "format": "epoch_millis||strict_date_optional_time" },
        "level": { "type": "keyword" },
        "message": { "type": "text", "fields": { "keyword": { "type": "keyword", "ignore_above": 256 } } },
        "host": { "type": "keyword" },
        "trace_id": { "type": "keyword" }
      }
    }
  },
  "_meta": { "description": "日志字段映射" }
}'

# 查看所有 Component Template
curl -X GET "localhost:9200/_component_template?pretty"

# 删除 Component Template
curl -X DELETE "localhost:9200/_component_template/common_settings"
```

**注意事项**

- Component Template 之间可按任意顺序组合，`composed_of` 数组顺序决定覆盖关系。
- 修改 Component Template 不会自动更新已创建的索引，仅影响新索引。
- 不能在一个 Component Template 中定义 `index_patterns` 或 `priority`，这些属性属于 Index Template。
- 别名（aliases）也可以在 Component Template 中定义。

---

### 模板优先级

**概念定义**

当多个 Composable Index Template 匹配同一个索引名称时，通过 `priority` 字段决定哪个模板生效。优先级值越大越优先，相同优先级时行为未定义（可能随机选择）。

**核心参数表**

| 参数 | 类型 | 说明 |
|------|------|------|
| `priority` | Integer | 模板优先级，默认 0，值越大越优先 |

**REST API**

```bash
# 低优先级模板（兜底）
curl -X PUT "localhost:9200/_index_template/default_template" -H 'Content-Type: application/json' -d'
{
  "index_patterns": ["*"],
  "priority": 0,
  "template": {
    "settings": {
      "index.number_of_shards": 1,
      "index.number_of_replicas": 0
    }
  }
}'

# 高优先级模板（覆盖特定模式）
curl -X PUT "localhost:9200/_index_template/important_logs_template" -H 'Content-Type: application/json' -d'
{
  "index_patterns": ["important-*"],
  "priority": 500,
  "template": {
    "settings": {
      "index.number_of_shards": 5,
      "index.number_of_replicas": 2
    }
  }
}'
```

**注意事项**

- `policy` 默认为 0，多个默认优先级模板同时匹配时结果不可预测。
- 实际项目中建议将 `priority` 的间隔设为 100 或 1000，便于后续插入中间优先级模板。
- 优先级仅在多个 Index Template 的 `index_patterns` 同时匹配时生效，不是针对 Component Template 内部的。
- 使用 `_simulate_index` API 可验证模板优先级叠加结果。

---

### 模板匹配规则

**概念定义**

当创建索引时，Elasticsearch 根据索引名称匹配所有 `index_patterns` 符合的模板，并按优先级合并配置。匹配规则决定了最终索引的 settings、mappings、aliases 组合。

**核心规则**

1. 所有匹配的 Index Template 按其 `priority` 降序排列。
2. 配置合并顺序：低优先级模板先应用，高优先级模板的配置覆盖低优先级的同名字段。
3. `composed_of` 中的 Component Template 按数组顺序从左到右叠加，后覆盖前。
4. 顶层 `template` 中的配置具有最高优先级。
5. 索引创建时显式指定的 settings/mappings 优先级最高，覆盖所有模板配置。

**REST API**

```bash
# 模拟索引创建，查看最终合并结果
curl -X POST "localhost:9200/_index_template/_simulate_index/my-index-2024-01-01"

# 模拟指定模板的合并结果
curl -X POST "localhost:9200/_index_template/_simulate/logs_template"
```

**注意事项**

- 索引名称匹配使用通配符模式（`*` 匹配多字符，`?` 匹配单字符）。
- 如果没有任何模板匹配，索引使用默认配置（1 个分片、1 个副本、动态映射）。
- 8.x 中 Data Stream 的匹配规则与普通索引一致，但额外要求模板中 `data_stream: {}` 非空对象。

---

## Data Stream

### Data Stream 概念

**概念定义**

Data Stream（数据流）是 7.9+ 引入的时序数据抽象层，专为 append-only 的时序数据（日志、指标、APM）设计。Data Stream 内部由多个隐藏的 `.ds-*` 后备索引（Backing Index）组成，上层通过统一的流名称暴露写入和查询接口。

**核心特性**

- 单一写入端点：通过 Data Stream 名称写入，自动路由到最新的后备索引
- 自动 Rollover：绑定 ILM Policy 后自动管理后备索引的滚动
- 时间排序：后备索引按 `@timestamp` 字段组织，查询时自动过滤
- 隐藏索引：后备索引为隐藏索引（`.ds-*`），用户无需直接操作

**核心参数表**

| 参数 | 类型 | 说明 |
|------|------|------|
| `name` | String | Data Stream 名称 |
| `timestamp_field` | String | 时间戳字段名，默认 `@timestamp` |
| `indices` | Array | 后备索引列表（只读） |
| `generation` | Integer | 当前写入索引的代数 |
| `hidden` | Boolean | 是否隐藏 Data Stream |

**REST API**

```bash
# 查看所有 Data Stream
curl -X GET "localhost:9200/_data_stream?pretty"

# 查看特定 Data Stream 的统计信息
curl -X GET "localhost:9200/_data_stream/logs-app/_stats?pretty"

# 获取 Data Stream 的后备索引
curl -X GET "localhost:9200/_data_stream/logs-app?pretty"
```

**注意事项**

- Data Stream 要求 `@timestamp` 字段，且字段类型为 `date`。
- 写入数据时必须包含 `@timestamp` 字段，否则会被拒绝。
- 后备索引按 `.ds-<data_stream_name>-<yyyy.MM.dd>-<generation>` 格式命名。
- 8.x 中 Data Stream 支持 `index_mode: "time_series"`（TSDS），详见 TSDS 章节。

---

### 创建与使用

**概念定义**

Data Stream 的创建需要：一个匹配的 Composable Index Template（包含 `data_stream: {}` 声明）、ILM Policy 绑定、以及首次写入时自动创建第一个后备索引。

**REST API**

```bash
# 步骤1：创建 ILM Policy
curl -X PUT "localhost:9200/_ilm/policy/logs_ds_policy" -H 'Content-Type: application/json' -d'
{
  "policy": {
    "phases": {
      "hot": {
        "min_age": "0ms",
        "actions": {
          "rollover": { "max_size": "30gb", "max_age": "1d" }
        }
      },
      "delete": {
        "min_age": "30d",
        "actions": { "delete": {} }
      }
    }
  }
}'

# 步骤2：创建索引模板（声明 data_stream）
curl -X PUT "localhost:9200/_index_template/logs_ds_template" -H 'Content-Type: application/json' -d'
{
  "index_patterns": ["logs-app"],
  "data_stream": {},
  "priority": 200,
  "template": {
    "settings": {
      "index.lifecycle.name": "logs_ds_policy"
    },
    "mappings": {
      "properties": {
        "@timestamp": { "type": "date" },
        "level": { "type": "keyword" },
        "message": { "type": "text" },
        "host": { "type": "keyword" }
      }
    }
  }
}'

# 步骤3：写入数据，自动创建 Data Stream
curl -X POST "localhost:9200/logs-app/_doc" -H 'Content-Type: application/json' -d'
{
  "@timestamp": "2024-01-15T10:00:00Z",
  "level": "INFO",
  "message": "Application started",
  "host": "server-01"
}'

# 验证 Data Stream 已创建
curl -X GET "localhost:9200/_data_stream/logs-app?pretty"
```

**注意事项**

- `index_patterns` 必须精确匹配 Data Stream 名称（如 `"logs-app"`），不能使用通配符。
- 模板中必须声明 `"data_stream": {}` 或 `"data_stream": { "hidden": false }`。
- 只有 `create` 和 `index` 操作可以创建 Data Stream，`_bulk` 中首次写入也会触发创建。
- 第一次写入时，Elasticsearch 自动创建 `.ds-logs-app-<yyyy.MM.dd>-000001` 后备索引。

---

### 写入与查询

**概念定义**

Data Stream 作为写入和查询的统一入口。写入时自动路由到最新的后备索引（Write Index）；查询时自动搜索所有匹配的后备索引。

**核心参数表**

| 参数 | 类型 | 说明 |
|------|------|------|
| `op_type` | String | 写入操作类型：`create`（仅创建）或 `index`（创建或更新） |
| `refresh` | String | 刷新策略：`true`、`false`、`wait_for` |

**REST API**

```bash
# 写入单条文档
curl -X POST "localhost:9200/logs-app/_doc" -H 'Content-Type: application/json' -d'
{
  "@timestamp": "2024-01-15T10:00:00Z",
  "level": "ERROR",
  "message": "Connection timeout",
  "host": "server-01"
}'

# 批量写入
curl -X POST "localhost:9200/logs-app/_bulk" -H 'Content-Type: application/json' -d'
{ "create": {} }
{ "@timestamp": "2024-01-15T10:01:00Z", "level": "INFO", "message": "Bulk msg 1", "host": "server-01" }
{ "create": {} }
{ "@timestamp": "2024-01-15T10:02:00Z", "level": "WARN", "message": "Bulk msg 2", "host": "server-02" }
'

# 查询所有后备索引
curl -X GET "localhost:9200/logs-app/_search?pretty" -H 'Content-Type: application/json' -d'
{
  "query": {
    "range": {
      "@timestamp": {
        "gte": "2024-01-01",
        "lte": "2024-01-31"
      }
    }
  }
}'

# 按时间范围查询（Data Stream 自动优化）
curl -X GET "localhost:9200/logs-app/_search?pretty" -H 'Content-Type: application/json' -d'
{
  "query": {
    "bool": {
      "filter": [
        { "range": { "@timestamp": { "gte": "now-7d" } } },
        { "term": { "level": "ERROR" } }
      ]
    }
  },
  "sort": [{ "@timestamp": "desc" }],
  "size": 100
}'
```

**注意事项**

- Data Stream 只支持 `create` 操作，不支持 `update` 和 `delete`（文档级别的更新/删除需通过 `_update_by_query` 或 `_delete_by_query`）。
- 搜索时 Data Stream 自动过滤 `@timestamp` 范围，减少不必要的索引扫描。
- 写入时 `@timestamp` 字段必须存在，否则返回 400 错误。
- 查询时如果指定 `sort` 为 `@timestamp`，Elasticsearch 可跳过没有匹配时间范围的后备索引。

### TSDS（Time Series Data Stream）

**概念定义**

TSDS（Time Series Data Stream）是 8.x 引入的时序数据流优化，通过 `index_mode: "time_series"` 启用。TSDS 对时序数据做了底层优化：使用合成的 `_tsid`（时间序列 ID）替代 `_id`、支持时间维度的自动压缩、启用 `time_series` 路由。适合指标类数据（Metrics、APM）。

**核心参数表**

| 参数 | 类型 | 说明 |
|------|------|------|
| `index.mode` | String | 设为 `"time_series"` 启用 TSDS |
| `index.routing_path` | String[] | 时间序列路由维度字段（必需） |
| `time_series_dimension` | Boolean | 标记字段为维度字段（keyword 类型） |
| `time_series_metric` | String | 标记字段为指标字段（`gauge`、`counter`、`histogram` 等） |

**REST API**

```bash
# 创建 TSDS 模板
curl -X PUT "localhost:9200/_index_template/metrics_tsds_template" -H 'Content-Type: application/json' -d'
{
  "index_patterns": ["metrics-*"],
  "data_stream": {},
  "priority": 300,
  "template": {
    "settings": {
      "index.mode": "time_series",
      "index.routing_path": ["host", "region"],
      "index.lifecycle.name": "metrics_policy"
    },
    "mappings": {
      "properties": {
        "@timestamp": { "type": "date" },
        "host": { "type": "keyword", "time_series_dimension": true },
        "region": { "type": "keyword", "time_series_dimension": true },
        "cpu_usage": { "type": "double", "time_series_metric": "gauge" },
        "request_count": { "type": "long", "time_series_metric": "counter" },
        "latency": { "type": "aggregate_metric_double", "time_series_metric": "gauge", "metrics": ["min", "max", "avg"] }
      }
    }
  }
}'

# 写入 TSDS 数据
curl -X POST "localhost:9200/metrics-system/_doc" -H 'Content-Type: application/json' -d'
{
  "@timestamp": "2024-01-15T10:00:00Z",
  "host": "server-01",
  "region": "us-east-1",
  "cpu_usage": 75.5,
  "request_count": 1500
}'

# TSDS 聚合查询（自动利用时间维度优化）
curl -X GET "localhost:9200/metrics-system/_search?pretty" -H 'Content-Type: application/json' -d'
{
  "query": {
    "bool": {
      "filter": [
        { "range": { "@timestamp": { "gte": "now-1h" } } },
        { "term": { "host": "server-01" } }
      ]
    }
  },
  "aggs": {
    "avg_cpu": { "avg": { "field": "cpu_usage" } },
    "total_requests": { "sum": { "field": "request_count" } }
  }
}'
```

**注意事项**

- TSDS 仅支持 `create` 操作，不支持 `update` 和 `delete`（同普通 Data Stream）。
- 维度字段必须是 `keyword` 类型，且标记 `time_series_dimension: true`。
- `routing_path` 必须是维度字段的子集，会影响数据分布和查询性能。
- TSDS 的 `_id` 由 `_tsid` 和 `@timestamp` 合成，无法指定自定义 ID。
- TSDS 需要 Elasticsearch 8.x 白金版 License 或 Enterprise License。
- 聚合查询中 TSDS 可利用时间维度修剪，跳过不相关的段。

### Data Stream Lifecycle（DSL）

**概念定义**

Data Stream Lifecycle（DSL）是 8.14+ 引入的轻量级生命周期管理机制，作为 ILM 的简化替代方案。DSL 直接在索引模板或 Data Stream 上配置数据保留策略，无需定义复杂的 ILM Policy 和多阶段 Action。对时序数据场景而言，只需"保留多久后自动删除"这一条规则即可。

**适用场景**

| 场景 | 推荐方案 | 原因 |
|------|---------|------|
| 简单日志保留 | DSL | 只需定期删除过期数据 |
| 指标数据降采样 | DSL | 内置 Downsampling 支持 |
| 多阶段温度管理 | ILM | 需要 hot/warm/cold 分层 |
| 复杂索引操作 | ILM | 需要 Shrink、Force Merge、Migrate 等 Action |

**核心参数**

| 参数 | 类型 | 说明 |
|------|------|------|
| `lifecycle.data_retention` | String | 数据保留时间（如 `"7d"`、`"30d"`），到期后自动删除 |
| `lifecycle.downsampling` | Array | 降采样配置数组，每个元素指定 `after` 和 `fixed_interval` |
| `index.lifecycle.prefer_ilm` | Boolean | 设为 `false` 时使用 DSL 而非 ILM（无 ILM Policy 时自动忽略） |

**与 ILM 的对比**

| 维度 | ILM | DSL |
|------|-----|-----|
| 配置复杂度 | 高（5 阶段 + 多 Action） | 低（一行配置） |
| 阶段管理 | Hot/Warm/Cold/Frozen/Delete | 自动管理 |
| 版本支持 | 7.x+ | 8.14+ |
| 滚动策略 | 通过 ILM Policy 控制 | 自动按时间滚动 |
| 降采样 | 通过 Downsampling Action | 内置 `lifecycle.downsampling` |
| 力合并 | 支持 | 不支持（自动管理段） |
| 适用场景 | 复杂温度分层 | 简单时序数据管理 |

**REST API 示例**

```bash
# 索引模板中配置 DSL
curl -X PUT "localhost:9200/_index_template/logs-template" \
  -H "Content-Type: application/json" \
  -d '{
    "index_patterns": ["logs-*"],
    "data_stream": {},
    "priority": 500,
    "template": {
      "settings": {
        "index.lifecycle.prefer_ilm": false
      },
      "lifecycle": {
        "data_retention": "30d"
      }
    }
  }'

# 为已有 Data Stream 配置 DSL
curl -X PUT "localhost:9200/_data_stream/logs-app/_lifecycle" \
  -H "Content-Type: application/json" \
  -d '{
    "lifecycle": {
      "data_retention": "30d"
    }
  }'

# 配置带降采样的 DSL
curl -X PUT "localhost:9200/_index_template/metrics-template" \
  -H "Content-Type: application/json" \
  -d '{
    "index_patterns": ["metrics-*"],
    "data_stream": {},
    "template": {
      "settings": {
        "index.mode": "time_series",
        "index.lifecycle.prefer_ilm": false
      },
      "lifecycle": {
        "data_retention": "90d",
        "downsampling": [
          { "after": "1d", "fixed_interval": "1h" },
          { "after": "7d", "fixed_interval": "1d" }
        ]
      }
    }
  }'

# 查看 Data Stream 的生命周期状态
curl -X GET "localhost:9200/_data_stream/logs-app/_lifecycle?pretty"
```

**注意事项**

- DSL 和 ILM 互斥：一个 Data Stream 不能同时使用 DSL 和 ILM。`prefer_ilm: false` 显式声明使用 DSL。
- DSL 仅适用于 Data Stream，不能用于普通索引。
- 如果 Data Stream 已绑定 ILM Policy，切换到 DSL 时需先移除 ILM Policy 并设置 `prefer_ilm: false`。
- 降采样仅在 TSDS（`index.mode: "time_series"`）中可用。
- DSL 的 `data_retention` 从索引创建时间开始计算，而非从写入时间计算。
- 8.14+ 版本中 DSL 功能已 GA，推荐在简单场景中替代 ILM。

## 索引别名

### Alias 基础

**概念定义**

索引别名（Index Alias）是索引的虚拟名称，提供一层间接访问。一个别名可以指向一个或多个索引，一个索引也可以有多个别名。别名是 Elasticsearch 实现零停机索引切换、多索引查询、权限控制的核心机制。

**核心参数表**

| 参数 | 类型 | 说明 |
|------|------|------|
| `aliases` | Object | 别名定义 |
| `is_write_index` | Boolean | 是否为写入索引（多索引别名时必需） |
| `is_hidden` | Boolean | 是否为隐藏别名 |
| `filter` | Object | 过滤条件（Filtered Alias） |
| `index_routing` | String | 索引路由值 |
| `search_routing` | String | 搜索路由值 |

**REST API**

```bash
# 创建索引时同时定义别名
curl -X PUT "localhost:9200/my-index-000001" -H 'Content-Type: application/json' -d'
{
  "aliases": {
    "my-index-read": {},
    "my-index-write": { "is_write_index": true }
  }
}'

# 为已有索引添加别名
curl -X PUT "localhost:9200/my-index-000001/_alias/my-alias"

# 查看别名指向的索引
curl -X GET "localhost:9200/_alias/my-alias?pretty"

# 查看所有别名
curl -X GET "localhost:9200/_cat/aliases?v"

# 删除别名
curl -X DELETE "localhost:9200/my-index-000001/_alias/my-alias"

# 通过别名查询（透明地查询所有关联索引）
curl -X GET "localhost:9200/my-alias/_search?pretty"
```

**注意事项**

- 别名名称不能与索引名称重复。
- 多索引别名必须指定 `is_write_index: true` 的写入索引，否则写入操作会失败。
- 删除别名不影响底层索引。
- 别名在 ILM Rollover 中起关键作用：写入别名指向当前活跃索引。

---

### Filtered Alias（过滤别名）

**概念定义**

Filtered Alias 在别名上附加一个查询过滤器，所有通过该别名的查询操作都会自动应用该过滤条件，实现对同一索引的不同视图访问。典型场景：多租户数据隔离、软删除过滤、用户权限控制。

**核心参数表**

| 参数 | 类型 | 说明 |
|------|------|------|
| `filter` | Object | 查询 DSL 过滤条件 |
| `filter.term` | Object | 精确匹配过滤 |
| `filter.range` | Object | 范围过滤 |
| `filter.bool` | Object | 组合过滤 |

**REST API**

```bash
# 创建过滤别名（租户隔离）
curl -X PUT "localhost:9200/orders-000001/_alias/orders-tenant-a" -H 'Content-Type: application/json' -d'
{
  "filter": {
    "term": { "tenant_id": "tenant-a" }
  }
}'

# 创建带时间范围的过滤别名
curl -X PUT "localhost:9200/logs-000001/_alias/logs-recent" -H 'Content-Type: application/json' -d'
{
  "filter": {
    "range": {
      "@timestamp": { "gte": "now-7d" }
    }
  }
}'

# 通过过滤别名查询（自动应用过滤器）
curl -X GET "localhost:9200/orders-tenant-a/_search?pretty" -H 'Content-Type: application/json' -d'
{
  "query": {
    "match": { "product": "laptop" }
  }
}'
```

**注意事项**

- 过滤别名仅在查询时生效，写入操作不受过滤条件约束。
- 过滤条件在 Lucene 层面与查询条件合并，性能开销极小。
- 不能通过过滤别名进行 `_update_by_query` 或 `_delete_by_query`，这些操作会忽略别名过滤。
- 过滤别名可与 `is_write_index` 组合使用，但写入不受过滤条件限制。

---

### 零停机索引切换

**概念定义**

利用别名实现索引的零停机切换：创建新索引，将数据迁移或写入新索引，然后原子性地将别名从旧索引切换到新索引。这是索引重建、Mapping 变更、分片调整的核心运维手段。

**REST API**

```bash
# 步骤1：创建新索引（如调整分片数或 Mapping）
curl -X PUT "localhost:9200/my-index-v2" -H 'Content-Type: application/json' -d'
{
  "settings": {
    "index.number_of_shards": 5,
    "index.number_of_replicas": 2
  },
  "mappings": {
    "properties": {
      "new_field": { "type": "keyword" }
    }
  }
}'

# 步骤2：Reindex 数据到新索引
curl -X POST "localhost:9200/_reindex" -H 'Content-Type: application/json' -d'
{
  "source": { "index": "my-index-v1" },
  "dest": { "index": "my-index-v2" }
}'

# 步骤3：原子切换别名（_actions 支持原子多操作）
curl -X POST "localhost:9200/_aliases" -H 'Content-Type: application/json' -d'
{
  "actions": [
    { "remove": { "index": "my-index-v1", "alias": "my-index" } },
    { "add": { "index": "my-index-v2", "alias": "my-index" } }
  ]
}'

# 步骤4：确认别名已切换
curl -X GET "localhost:9200/_alias/my-index?pretty"

# 步骤5：删除旧索引
curl -X DELETE "localhost:9200/my-index-v1"
```

**注意事项**

- `_aliases` 的 `actions` 数组中的所有操作是原子性的，这是实现零停机的关键。
- 在别名切换期间，应用层无需修改代码，通过别名访问无缝切换。
- Reindex 操作会消耗集群资源，建议在低峰期执行，并控制 `requests_per_second` 限速。
- 务必在切换后验证别名指向正确，再删除旧索引。

---

### Write Index 控制

**概念定义**

当一个别名指向多个索引时，必须指定一个 Write Index 来处理写入操作。Write Index 是别名指向的索引中唯一接受写入的索引，ILM Rollover 依赖此机制。

**核心参数表**

| 参数 | 类型 | 说明 |
|------|------|------|
| `is_write_index` | Boolean | 是否为写入索引（默认 `false`） |
| `index.lifecycle.rollover_alias` | String | ILM 滚动别名 |

**REST API**

```bash
# 多索引别名，指定写入索引
curl -X PUT "localhost:9200/logs-000001" -H 'Content-Type: application/json' -d'
{
  "aliases": {
    "logs": { "is_write_index": true }
  }
}'

curl -X PUT "localhost:9200/logs-000002" -H 'Content-Type: application/json' -d'
{
  "aliases": {
    "logs": { "is_write_index": false }
  }
}'

# 写入时自动路由到 is_write_index: true 的索引
curl -X POST "localhost:9200/logs/_doc" -H 'Content-Type: application/json' -d'
{
  "@timestamp": "2024-01-15T10:00:00Z",
  "message": "Routed to logs-000001"
}'

# 手动切换 Write Index
curl -X POST "localhost:9200/_aliases" -H 'Content-Type: application/json' -d'
{
  "actions": [
    { "add": { "index": "logs-000001", "alias": "logs", "is_write_index": false } },
    { "add": { "index": "logs-000002", "alias": "logs", "is_write_index": true } }
  ]
}'
```

**注意事项**

- 一个别名最多只能有一个 `is_write_index: true` 的索引。
- 不使用 `is_write_index` 且别名指向多索引时，写入操作会失败。
- ILM Rollover 依赖 `index.lifecycle.rollover_alias`，该别名必须指定 Write Index。
- 通过 `_aliases` API 可以原子性地切换 Write Index，避免写入中断。

## 其他操作

### Force Merge

**概念定义**

Force Merge 是强制合并 Lucene 段（Segment）的操作。每个 Elasticsearch 分片由多个 Lucene 段组成，段越多查询性能越差。Force Merge 将多个段合并为少量段，提升查询性能，但消耗大量 CPU 和 IO 资源。

**核心参数表**

| 参数 | 类型 | 说明 |
|------|------|------|
| `max_num_segments` | Integer | 合并后的最大段数（建议 `1`） |
| `only_expunge_deletes` | Boolean | 仅驱逐已删除文档的段（默认 `false`） |
| `flush` | Boolean | 是否在合并后执行 flush（默认 `true`） |
| `requests_per_second` | String | 限速（如 `"100mb"`），避免影响集群 |

**REST API**

```bash
# 强制合并为 1 个段
curl -X POST "localhost:9200/my-index/_forcemerge?max_num_segments=1&pretty"

# 仅清理已删除文档
curl -X POST "localhost:9200/my-index/_forcemerge?only_expunge_deletes=true&pretty"

# 带限速的 Force Merge
curl -X POST "localhost:9200/my-index/_forcemerge?max_num_segments=1&requests_per_second=50mb&pretty"

# 合并多个索引
curl -X POST "localhost:9200/index-1,index-2/_forcemerge?max_num_segments=1"

# 查看当前段数
curl -X GET "localhost:9200/_cat/segments/my-index?v&h=index,shard,segment,size,docs.count"
```

**注意事项**

- Force Merge 是资源密集型操作，建议在低峰期执行，且仅在不再写入的只读索引上使用。
- 合并后段数可能大于 `max_num_segments`，因为每个分片独立合并。
- 合并大段时可能导致节点 OOM，建议对大数据量索引分批合并。
- Force Merge 后索引变为只读，需手动恢复写入权限。
- 8.x 中 Force Merge 已集成到 ILM 的 Warm 阶段，推荐自动化执行。

---

### Shrink（缩容）

**概念定义**

Shrink 操作将索引的主分片数量减少到更小的值。新分片数必须是原分片数的因子（如 8 -> 4 -> 2 -> 1）。Shrink 过程会创建新索引，原索引数据被硬链接复制到新索引，性能优于 Reindex。

**核心参数表**

| 参数 | 类型 | 说明 |
|------|------|------|
| `target_index` | String | 目标索引名称 |
| `number_of_shards` | Integer | 目标主分片数 |
| `settings` | Object | 目标索引的额外设置 |
| `aliases` | Object | 目标索引的别名 |

**REST API**

```bash
# 步骤1：源索引必须设为只读
curl -X PUT "localhost:9200/my-index/_settings" -H 'Content-Type: application/json' -d'
{
  "settings": {
    "index.blocks.write": true
  }
}'

# 步骤2：确保所有分片在同一节点上
curl -X PUT "localhost:9200/my-index/_settings" -H 'Content-Type: application/json' -d'
{
  "settings": {
    "index.routing.allocation.require._name": "node-1"
  }
}'

# 步骤3：执行 Shrink
curl -X POST "localhost:9200/my-index/_shrink/my-index-shrunk" -H 'Content-Type: application/json' -d'
{
  "settings": {
    "index.number_of_shards": 1,
    "index.number_of_replicas": 1,
    "index.codec": "best_compression"
  },
  "aliases": {
    "my-index-read": {}
  }
}'

# 监控 Shrink 进度
curl -X GET "localhost:9200/_cat/recovery/my-index-shrunk?v"
```

**注意事项**

- Shrink 前源索引必须设为只读（`index.blocks.write: true`）。
- 所有分片必须位于同一节点（通过 `index.routing.allocation.require._name` 控制）。
- 目标分片数必须是源分片数的因子，如 8 -> 4 -> 2 -> 1。
- 源索引和目标索引不可同节点时执行 Shrink（需先迁移分片）。
- Shrink 使用硬链接（hard link）复制文件，磁盘空间占用小，速度快。
- 设置 `index.codec: best_compression` 可在 Shrink 时重新压缩段文件。

---

### Split（扩容）

**概念定义**

Split 操作将索引的主分片数量增加到更大的值。新分片数必须是原分片数的整数倍（如 1 -> 2 -> 4 -> 8）。Split 过程创建新索引，将原分片数据拆分到更多分片中。

**核心参数表**

| 参数 | 类型 | 说明 |
|------|------|------|
| `target_index` | String | 目标索引名称 |
| `number_of_shards` | Integer | 目标主分片数（必须是原分片数的整数倍） |
| `settings` | Object | 目标索引的额外设置 |
| `aliases` | Object | 目标索引的别名 |

**REST API**

```bash
# 步骤1：源索引设为只读
curl -X PUT "localhost:9200/my-index/_settings" -H 'Content-Type: application/json' -d'
{
  "settings": {
    "index.blocks.write": true
  }
}'

# 步骤2：执行 Split（1 分片 -> 4 分片）
curl -X POST "localhost:9200/my-index/_split/my-index-split" -H 'Content-Type: application/json' -d'
{
  "settings": {
    "index.number_of_shards": 4,
    "index.number_of_replicas": 1
  },
  "aliases": {
    "my-index-expanded": {}
  }
}'

# 监控 Split 进度
curl -X GET "localhost:9200/_cat/recovery/my-index-split?v"
```

**注意事项**

- Split 前源索引必须设为只读。
- 目标分片数必须是源分片数的整数倍（如 `number_of_routing_shards` 未设置时，最大拆分倍数为 1024）。
- 如果设置了 `index.number_of_routing_shards`，目标分片数必须是该值的因子。
- Split 的实际原理是创建新索引并复制数据，因此会消耗额外磁盘空间。
- 相比 Shrink，Split 的使用场景较少，通常用于从单分片索引扩容。

### Close / Open

**概念定义**

Close 操作关闭索引，释放内存中的数据结构，索引不可读写；Open 操作重新打开索引，恢复读写能力。Close/Open 适用于临时释放内存、修改静态配置（如 `codec`、`analysis` 设置）。

**核心参数表**

| 参数 | 类型 | 说明 |
|------|------|------|
| `wait_for_active_shards` | String | 等待活跃分片数（Open 时） |
| `timeout` | String | 操作超时时间 |

**REST API**

```bash
# 关闭索引
curl -X POST "localhost:9200/my-index/_close?pretty"

# 打开索引
curl -X POST "localhost:9200/my-index/_open?pretty"

# 批量关闭
curl -X POST "localhost:9200/index-1,index-2/_close"

# 关闭后修改静态配置
curl -X PUT "localhost:9200/my-index/_settings" -H 'Content-Type: application/json' -d'
{
  "settings": {
    "index.codec": "best_compression",
    "index.analysis.analyzer.default.type": "standard"
  }
}'

# 重新打开
curl -X POST "localhost:9200/my-index/_open"
```

**注意事项**

- 关闭的索引不占用堆内存，但磁盘空间不变。
- 关闭索引后，所有分片被标记为 unassigned，集群状态变为 Yellow（如有副本）或 Red（无副本）。
- 静态配置（如 `index.codec`、`index.number_of_shards` 的部分属性）只能在关闭状态下修改。
- 动态配置（如 `index.number_of_replicas`、`index.refresh_interval`）无需关闭索引即可修改。
- 关闭索引无法被搜索，搜索请求会报错。

### Downsampling（降采样）

**概念定义**

Downsampling 是 8.x 引入的指标数据降采样功能，通过预聚合将高分辨率指标数据压缩为低分辨率数据，大幅降低存储成本。降采样后的索引仍然可查询，但只能读取聚合结果。

**核心参数表**

| 参数 | 类型 | 说明 |
|------|------|------|
| `fixed_interval` | String | 降采样时间间隔（如 `"1h"`、`"1d"`） |
| `metrics` | Object[] | 指标聚合配置 |
| `metrics[].name` | String | 聚合后的字段名 |
| `metrics[].type` | String | 聚合类型（`min`、`max`、`sum`、`avg`、`value_count`） |
| `metrics[].field` | String | 源字段名 |
| `dimensions` | String[] | 保留的维度字段 |
| `target_index` | String | 降采样目标索引 |

**REST API**

```bash
# 创建降采样 Configuration
curl -X PUT "localhost:9200/_downsample/metrics-2024-01" -H 'Content-Type: application/json' -d'
{
  "fixed_interval": "1h",
  "metrics": [
    { "name": "cpu_avg", "type": "avg", "field": "cpu_usage" },
    { "name": "cpu_max", "type": "max", "field": "cpu_usage" },
    { "name": "cpu_min", "type": "min", "field": "cpu_usage" },
    { "name": "request_sum", "type": "sum", "field": "request_count" },
    { "name": "sample_count", "type": "value_count", "field": "cpu_usage" }
  ],
  "dimensions": ["host", "region"],
  "target_index": "metrics-2024-01-1h-downsampled"
}'

# 查询降采样索引
curl -X GET "localhost:9200/metrics-2024-01-1h-downsampled/_search?pretty" -H 'Content-Type: application/json' -d'
{
  "query": {
    "bool": {
      "filter": [
        { "range": { "@timestamp": { "gte": "2024-01-01", "lte": "2024-01-31" } } },
        { "term": { "host": "server-01" } }
      ]
    }
  },
  "aggs": {
    "avg_cpu": { "avg": { "field": "cpu_avg" } }
  }
}'
```

**注意事项**

- Downsampling 仅适用于 TSDS（Time Series Data Stream）的指标数据。
- 降采样后原始高精度数据丢失，只能查询聚合结果（`min`、`max`、`sum`、`avg`、`value_count`）。
- `fixed_interval` 支持：`"1m"`、`"5m"`、`"15m"`、`"1h"`、`"1d"` 等。
- 降采样后的索引也可加入 ILM 管理，进一步降低存储成本。
- 降采样是 8.x 的新功能，需要 Elasticsearch 8.x 白金版 License。

### Reindex

**概念定义**

Reindex 操作将数据从一个索引复制到另一个索引，支持数据过滤、字段转换、脚本处理。Reindex 是索引迁移、Mapping 变更、分片调整的核心手段。与 Shrink/Split 不同，Reindex 是通用的数据复制机制。

**核心参数表**

| 参数 | 类型 | 说明 |
|------|------|------|
| `source.index` | String/String[] | 源索引名称 |
| `source.query` | Object | 过滤条件（仅复制匹配文档） |
| `source._source` | String[] | 指定要复制的字段 |
| `dest.index` | String | 目标索引名称 |
| `dest.op_type` | String | 写入策略：`index`（默认）或 `create` |
| `dest.pipeline` | String | 目标索引的 Ingest Pipeline |
| `script` | Object | 文档转换脚本 |
| `conflicts` | String | 冲突处理：`abort`（默认）或 `proceed` |
| `requests_per_second` | Integer | 限速（每秒请求数），默认 `-1`（不限速） |
| `slices` | Integer/String | 并行度：`auto` 或指定分片数 |

**REST API**

```bash
# 基础 Reindex
curl -X POST "localhost:9200/_reindex" -H 'Content-Type: application/json' -d'
{
  "source": { "index": "old-index" },
  "dest": { "index": "new-index" }
}'

# 过滤数据 + 字段选择
curl -X POST "localhost:9200/_reindex" -H 'Content-Type: application/json' -d'
{
  "source": {
    "index": "old-index",
    "query": {
      "range": { "@timestamp": { "gte": "2024-01-01" } }
    },
    "_source": ["field1", "field2", "@timestamp"]
  },
  "dest": { "index": "new-index" }
}'

# 带脚本转换的 Reindex
curl -X POST "localhost:9200/_reindex" -H 'Content-Type: application/json' -d'
{
  "source": { "index": "old-index" },
  "dest": {
    "index": "new-index",
    "pipeline": "enrich_pipeline"
  },
  "script": {
    "source": "ctx._source.new_field = ctx._source.remove(\"old_field\")",
    "lang": "painless"
  },
  "conflicts": "proceed"
}'

# 限速 + 并行 Reindex
curl -X POST "localhost:9200/_reindex?requests_per_second=1000&slices=auto&wait_for_completion=false" -H 'Content-Type: application/json' -d'
{
  "source": { "index": "old-index" },
  "dest": { "index": "new-index" }
}'

# 查询 Reindex 任务进度
curl -X GET "localhost:9200/_tasks?detailed=true&actions=*reindex&pretty"
```

**注意事项**

- Reindex 不会自动复制索引设置（settings）和映射（mappings），目标索引需提前创建或使用模板。
- 目标索引不存在时，Reindex 会自动创建，但映射将基于源文档动态推断，可能导致字段类型不一致。
- 使用 `conflicts: "proceed"` 可忽略版本冲突，适合增量数据追加。
- `requests_per_second` 用于限速，避免 Reindex 影响集群正常服务，建议设为 500-2000。
- `slices: "auto"` 启用并行 Reindex，利用多线程提升速度，但会增加集群负载。
- 异步 Reindex（`wait_for_completion=false`）返回 `task_id`，可通过 `_tasks` API 监控进度。
- Reindex 是数据迁移的首选方案，但大数据量场景建议使用快照恢复或 Logstash。
