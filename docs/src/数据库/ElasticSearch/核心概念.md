## ES 概述

### Elastic Stack 全家桶

Elastic Stack 是以 Elasticsearch 为核心的全文检索与数据分析工具链，由以下组件构成：

| 组件 | 定位 | 核心职责 |
|------|------|----------|
| **Elasticsearch** | 分布式搜索与分析引擎 | 存储、索引、全文检索、聚合分析 |
| **Kibana** | 可视化与管控平台 | 数据看板、Dev Tools、集群监控、Alerting |
| **Logstash** | 服务端数据采集管道 | ETL：采集 → 转换 → 写入 ES |
| **Beats** | 轻量级采集 Agent | Filebeat（日志）、Metricbeat（指标）、Packetbeat（网络）等 |
| **Elastic Agent** | 统一采集器（8.x 推荐） | 替代 Beats + Logstash 的单一 Agent 方案 |
| **Fleet** | 集中式 Agent 管理（Kibana 内） | 策略下发、版本升级、健康监控 |
| **APM Server** | 应用性能监控 | 分布式追踪、服务依赖拓扑、延迟分析 |
| **Elastic Cloud** | 官方托管服务 | 托管 ES 集群 + 解决方案（含 Serverless） |

**注意事项**:
- 8.x 起，Elastic Agent + Fleet 是官方推荐的数据采集方案，传统 Beats 仍受支持但演进放缓。
- Logstash 在 8.x 中仍为 GA，但繁重 ETL 场景建议使用 Kafka/Flink 缓冲层。
- 8.x 安全默认开启，所有组件间通信强制 TLS，需统一管理证书。

---

### 适用场景与反模式

**适用场景（正向）**:

| 场景 | 典型用法 | 备注 |
|------|----------|------|
| 全文搜索 | 商品搜索、文档检索、站内搜索 | 分词 + 倒排索引，天然优势 |
| 日志分析 | 应用日志、审计日志、安全日志 | 配合 Data Stream + ILM 做冷热分层 |
| 指标监控 | 服务器指标、业务指标聚合 | 配合 TSDS（Time Series Data Stream） |
| APM / 可观测性 | 分布式追踪、Span 检索 | 8.x 原生集成了 Elastic APM |
| 向量检索 | 语义搜索、RAG 知识库 | 8.x 原生 kNN + 9.x semantic_text |
| 地理空间查询 | LBS、围栏、附近的人 | geo_point / geo_shape 类型 |
| 实时聚合分析 | 大盘统计、漏斗分析、同比环比 | Aggregation + ES\|QL |

**反模式（不适用）**:

| 场景 | 原因 | 替代方案 |
|------|------|----------|
| 事务性主库（OLTP） | 无 ACID 事务，写入有近实时延迟 | MySQL / PostgreSQL |
| 关联查询密集型 | 无 JOIN（ES\|QL LOOKUP JOIN 仅 8.18+ 预览） | 关系型数据库 |
| 多表关联聚合 | 非关系模型，嵌套/join 类型性能差 | ClickHouse / Druid |
| 高频更新（单文档） | 更新 = 标记删除 + 重新索引，成本高 | Redis / MongoDB |
| 精确数值计算 | 浮点精度问题，非计算引擎 | Spark / Flink |
| 冷数据归档 | 磁盘成本高，不如对象存储 | S3 / MinIO + searchable snapshot |

**注意事项**:
- ES 不是关系型数据库的替代品，最佳实践是"关系型做主库 + ES 做搜索读库"，通过 CDC 同步。
- 全文检索 + 聚合分析可共存，但需合理规划索引 Mapping 和分片策略。

---

### 与关系型数据库对比

| 维度 | Elasticsearch 8.x | MySQL / PostgreSQL |
|------|-------------------|---------------------|
| 数据模型 | Index → Document（JSON） | Database → Table → Row |
| 查询语言 | Query DSL / ES\|QL | SQL |
| 索引结构 | 倒排索引 + BKD Tree + HNSW | B+Tree / Hash |
| 事务 | 无（仅单文档原子性） | ACID |
| 扩展性 | 水平分片（Shard），天然分布式 | 主从复制 / 分库分表 |
| 一致性 | 最终一致性（可调 quorum） | 强一致性 |
| 写入延迟 | 近实时（默认 1s refresh） | 实时 |
| Schema | 动态 Mapping（可显式定义） | 静态 Schema |
| 全文检索 | 分词、TF-IDF / BM25、高亮 | LIKE / 全文索引（性能差） |
| 聚合分析 | 多维聚合、Pipeline、Matrix | GROUP BY + 窗口函数 |
| Java 客户端 | `elasticsearch-java` | JDBC / JPA |

**概念映射速查**:

```
MySQL                          Elasticsearch
─────────────────────────────────────────────────
Database        ──────────▶    Index
Table           ──────────▶    Index（8.x 中已无 Type 概念）
Row             ──────────▶    Document
Column          ──────────▶    Field
Schema          ──────────▶    Mapping
SQL             ──────────▶    Query DSL / ES|QL
INSERT/UPDATE   ──────────▶    Index API / Update API
SELECT          ──────────▶    Search API
JOIN            ──────────▶    Nested / Join / ES|QL LOOKUP JOIN
GROUP BY        ──────────▶    Aggregation
```

**注意事项**:
- 7.x 之前 Index 下可建多个 Type（类比 Table），8.x 已彻底移除 Type 概念，每个 Index 仅一种文档类型，固定为 `_doc`。
- ES 的 JOIN 能力弱，应通过"宽表化"或"应用层 Join"替代，避免在查询时使用 `nested` 或 `join` 类型做复杂关联。

## 核心概念

### Index（索引）

**概念定义**:
Index 是 Elasticsearch 中最高层级的逻辑存储单元，由一组具有相似结构的 Document 组成。在物理层面，一个 Index 由若干个 Shard 承载，每个 Shard 底层是一个完整的 Lucene 索引实例。可将 Index 理解为"数据库 + 表"的集合体（8.x 中一个 Index 即一张表）。

**核心参数**:

| 参数 | 默认值 (8.x) | 说明 |
|------|-------------|------|
| `number_of_shards` | 1 | 主分片数量，创建后不可修改（可 `_shrink` / `_split` 变更） |
| `number_of_replicas` | 1 | 每个主分片的副本数，可动态调整 |
| `refresh_interval` | 1s | 写入数据多久后可被搜索到（近实时） |
| `routing.allocation.total_shards_per_node` | -1（不限） | 同 Index 分片在单节点上的最大数量 |
| `codec` | `default`（LZ4） | 压缩算法，可选 `best_compression`（DEFLATE） |
| `max_result_window` | 10000 | `from + size` 分页上限 |
| `mapping.total_fields.limit` | 1000 | 单 Index 最大字段数，防止 Mapping 爆炸 |

**REST API 示例**:

```bash
# 创建索引（显式指定分片与副本）
PUT /products
{
  "settings": {
    "number_of_shards": 3,
    "number_of_replicas": 1,
    "refresh_interval": "5s",
    "codec": "best_compression"
  },
  "mappings": {
    "properties": {
      "name": { "type": "text", "analyzer": "ik_max_word" },
      "price": { "type": "scaled_float", "scaling_factor": 100 },
      "created_at": { "type": "date", "format": "yyyy-MM-dd HH:mm:ss" }
    }
  }
}

# 删除索引
DELETE /products

# 查看索引信息
GET /products

# 查看索引 Mapping
GET /products/_mapping

# 查看索引 Settings
GET /products/_settings

# 动态修改副本数
PUT /products/_settings
{
  "index.number_of_replicas": 2
}

# 查看所有索引（含健康状态、文档数、磁盘占用）
GET /_cat/indices?v
```

**注意事项**:
- `number_of_shards` 在索引创建后不可直接修改，可通过 `_shrink`（缩减）或 `_split`（拆分）API 间接变更，但需要将索引设为只读并迁移数据。
- 8.x 默认主分片数为 1（7.x 早期为 5），减少小索引的过度分片问题。
- `mapping.total_fields.limit` 默认 1000，若动态 Mapping 导致字段爆炸会触发异常，需显式定义 Mapping 或调高此值。
- 索引命名不支持大写字母，建议使用 `lowercase-with-dash` 风格。

### Document（文档）

**概念定义**:
Document 是 Elasticsearch 中最小数据单元，以 JSON 格式表示。每个 Document 属于一个 Index，由唯一 `_id` 标识，包含一组 Field（字段）及对应的值。Document 是不可变的（immutable）—— 更新操作本质上是"标记删除旧文档 + 写入新文档"。

**核心参数**:

| 参数 | 说明 |
|------|------|
| `_index` | 所属索引名称 |
| `_id` | 文档唯一标识（可自定义或自动生成） |
| `_version` | 乐观锁版本号（每次更新 +1） |
| `_seq_no` | 写入序列号（递增，用于并发控制） |
| `_primary_term` | 主分片任期号，配合 `_seq_no` 做乐观锁 |
| `_source` | 原始 JSON 文档（默认存储） |
| `_routing` | 路由值，控制文档分配到哪个分片（默认 `_id`） |

**REST API 示例**:

```bash
# 创建文档（指定 ID）
POST /products/_doc/1001
{
  "name": "机械键盘",
  "price": 299.00,
  "brand": "Cherry",
  "created_at": "2026-07-01 10:00:00"
}

# 创建文档（自动生成 ID）
POST /products/_doc
{
  "name": "无线鼠标",
  "price": 149.00
}

# 部分更新（update API）
POST /products/_update/1001
{
  "doc": {
    "price": 259.00
  }
}

# 获取文档
GET /products/_doc/1001

# 获取文档（仅 _source）
GET /products/_source/1001

# 删除文档
DELETE /products/_doc/1001

# 批量写入（Bulk API）
POST /_bulk
{ "index": { "_index": "products", "_id": "2001" } }
{ "name": "显示器", "price": 1999.00 }
{ "index": { "_index": "products", "_id": "2002" } }
{ "name": "鼠标垫", "price": 29.00 }

# 乐观锁更新（CAS）
PUT /products/_doc/1001?if_seq_no=5&if_primary_term=1
{
  "name": "机械键盘 Pro",
  "price": 399.00
}
```

**注意事项**:
- 8.x 中所有文档 API 路径统一为 `/_doc/`，不再包含 Type 层级（如 `/_doc/` 而非 `/type/`）。
- `_id` 长度为 512 字节上限，过长 ID 会影响 Lucene 性能。
- `_source` 默认存储原始 JSON，若不需要可在 Mapping 中设置 `"_source": { "enabled": false }`，但会丢失 reindex、高亮、部分更新能力。
- 单个 Document 不建议超过 100MB（HTTP 默认上限），建议将大对象拆分为多个 Document 或使用 `stored_fields` 外挂。
- Bulk API 中每个子操作独立执行，一个失败不影响其他，响应中需逐条检查 `errors` 字段。

### Shard（分片）

**概念定义**:
Shard 是 Elasticsearch 数据分片的物理单元，底层是一个完整的 Lucene 索引实例。一个 Index 的数据被水平切分到多个 Shard 中，每个 Shard 独立承担索引、搜索和聚合任务。Shard 是 ES 实现水平扩展和并行化的基础。

**核心参数**:

| 参数 | 说明 |
|------|------|
| 主分片 (Primary Shard) | 数据写入的"第一落点"，每个 Index 创建时确定，数量不可变 |
| 副本分片 (Replica Shard) | 主分片的完整拷贝，提供高可用和读吞吐 |
| `number_of_shards` | 主分片数，创建时设定，不可直接修改 |
| `number_of_replicas` | 副本数，可动态调整 |
| 单分片容量上限 | 建议 50GB 以内（受 Lucene 段合并开销影响） |
| 单分片文档数上限 | 建议 2^31 ≈ 21 亿（Lucene 硬限制） |

**REST API 示例**:

```bash
# 查看分片分布
GET /_cat/shards/products?v

# 查看分片分配详情
GET /_cluster/allocation/explain?pretty

# 手动移动分片
POST /_cluster/reroute
{
  "commands": [
    {
      "move": {
        "index": "products",
        "shard": 0,
        "from_node": "node-1",
        "to_node": "node-2"
      }
    }
  ]
}

# 查看 Index 分片分布
GET /_cat/shards/products?v&h=index,shard,prirep,state,docs,store,node

# 查看未分配分片原因
GET /_cat/shards?v&h=index,shard,prirep,state,unassigned.reason
```

**注意事项**:
- 主分片数一旦确定无法修改，需在创建索引时充分评估数据量增长。补救方案：`_split` API（增加分片）或 `_shrink` API（减少分片），但都需重建索引。
- 8.x 默认主分片数为 1，适合中小规模索引。日志场景建议 1-3 个分片配合按天/按小时 Rollover。
- 分片数量过多会导致 Master 节点压力增大（每个分片占用集群状态内存），建议集群总分片数控制在 3 万以内。
- 单分片容量超过 50GB 时，段合并会成为性能瓶颈，建议通过 ILM Rollover 控制单索引大小。
- 副本分片与主分片永远不在同一节点上（ES 自动保证），否则失去容灾意义。

### Replica（副本）

**概念定义**:
Replica 是主分片（Primary Shard）的完整拷贝，提供数据冗余和读负载分担。当主分片所在节点故障时，副本分片可被提升为主分片，保证集群高可用。副本分片数与主分片数一一对应。

**核心参数**:

| 参数 | 说明 |
|------|------|
| `number_of_replicas` | 每个主分片的副本数量，默认 1 |
| 副本分配策略 | ES 自动保证副本与主分片不在同一节点 |
| 同步方式 | 异步复制（从主分片同步到副本分片） |
| 读负载 | 副本分片可参与搜索，分担读请求 |

**REST API 示例**:

```bash
# 动态调整副本数
PUT /products/_settings
{
  "index.number_of_replicas": 2
}

# 关闭副本（用于 Bulk 导入加速）
PUT /products/_settings
{
  "index.number_of_replicas": 0
}

# 导入完成后恢复副本
PUT /products/_settings
{
  "index.number_of_replicas": 1
}

# 查看副本同步状态
GET /_cat/shards/products?v&h=index,shard,prirep,state,docs,store
```

**注意事项**:
- 副本数 + 1 = 数据总份数。例如 3 主分片 + 1 副本 = 6 个分片（3 主 + 3 副）。
- 副本数越多，读吞吐越高，但写入延迟会增加（需等待副本确认）。
- 集群节点数必须 >= 副本数 + 1，否则副本分片会处于 UNASSIGNED 状态（黄色健康）。
- Bulk 大批量导入时，建议先将副本设为 0，导入完成后再恢复，可提升 30%-50% 写入性能。
- 副本分片的段合并独立进行，可能导致主副分片磁盘占用短暂不一致（最终一致）。

### Node（节点）

**概念定义**:
Node 是 Elasticsearch 集群中的一个运行实例，每个节点通过 `cluster.name` 加入同一集群。节点承担数据存储、索引、搜索、聚合等任务，可配置不同角色实现职责分离。

**核心参数**:

| 参数 | 说明 |
|------|------|
| `node.name` | 节点名称，集群内唯一，默认随机生成 |
| `node.roles` | 节点角色列表（8.x 语法） |
| `cluster.name` | 集群名称，同集群节点必须一致 |
| `node.attr` | 自定义属性，用于分片分配感知（如 `rack_id`、`zone`） |
| `path.data` | 数据存储路径 |
| `path.logs` | 日志存储路径 |
| `network.host` | 绑定地址 |
| `http.port` | HTTP 端口，默认 9200 |
| `transport.port` | 节点间通信端口，默认 9300 |

**REST API 示例**:

```bash
# 查看集群节点列表
GET /_cat/nodes?v

# 查看节点详细信息
GET /_nodes?pretty

# 查看特定节点统计信息
GET /_nodes/node-1/stats?pretty

# 查看节点线程池
GET /_nodes/stats/thread_pool?pretty

# 查看节点 JVM 信息
GET /_nodes/stats/jvm?pretty

# 查看节点磁盘使用情况
GET /_cat/allocation?v
```

**注意事项**:
- 8.x 中节点角色通过 `node.roles` 数组配置，不再是旧版的 `node.master: true` 布尔值写法。
- 8.x 安全默认开启，节点间 transport 通信必须走 TLS，需配置证书。
- 生产环境禁止将 `path.data` 放在系统盘，应使用独立 SSD。
- 单节点建议内存不超过 64GB（受 JVM 堆压缩指针限制），超大内存机器可部署多实例或多个节点。
- Java 17 为 8.x 最低基线，ES 自带 bundled JDK，无需额外安装。

---

### Cluster（集群）

**概念定义**:
Cluster 是由一个或多个 Elasticsearch 节点组成的集合，通过 `cluster.name` 标识。集群对外提供统一的索引和搜索能力，对内自动管理分片分配、故障转移和负载均衡。集群状态由 Master 节点维护，包括元数据（Index Mapping、Setting）和路由表（Index Routing Table）。

**核心参数**:

| 参数 | 说明 |
|------|------|
| `cluster.name` | 集群名称（默认 `elasticsearch`），同集群节点必须一致 |
| `discovery.seed_hosts` | 种子节点列表，用于集群发现 |
| `cluster.initial_master_nodes` | 首次启动时指定候选 Master 节点 |
| 集群状态 (Green / Yellow / Red) | Green=全部分配, Yellow=主分片 OK 副本未分配, Red=部分主分片未分配 |
| 分裂脑 (Split Brain) | 最少 Master 节点数 `(N/2)+1` 防止 |

**REST API 示例**:

```bash
# 查看集群健康
GET /_cluster/health

# 查看集群健康（详细级别）
GET /_cluster/health?level=indices&pretty

# 查看集群状态
GET /_cluster/state?pretty

# 查看集群设置
GET /_cluster/settings?include_defaults=true&pretty

# 修改集群持久化设置
PUT /_cluster/settings
{
  "persistent": {
    "cluster.routing.allocation.disk.watermark.low": "85%",
    "cluster.routing.allocation.disk.watermark.high": "90%",
    "cluster.routing.allocation.disk.watermark.flood_stage": "95%"
  }
}

# 查看集群统计信息
GET /_cluster/stats?pretty

# 查看未分配分片
GET /_cat/shards?v&h=index,shard,prirep,state,unassigned.reason
```

**注意事项**:
- 8.x 中 `discovery.seed_hosts` 替代了旧版 `discovery.zen.ping.unicast.hosts`。
- 集群最小 Master 候选节点数建议为 3（奇数），通过 `discovery.zen.minimum_master_nodes`（7.x）或自动引导（8.x）避免脑裂。
- 8.x 使用新的集群引导方式，首次启动时通过 `cluster.initial_master_nodes` 指定候选节点，集群形成后此参数不再需要。
- 磁盘水位线（watermark）是集群级保护机制：达到 `low`（85%）停止向该节点分配新分片，达到 `high`（90%）尝试迁移分片，达到 `flood_stage`（95%）将索引设为只读。
- 集群状态 (Cluster State) 是所有节点共享的元数据，Master 节点负责维护和广播，频繁变更（如大量索引创建/删除）会导致 Master 节点 CPU 飙升。

## 分布式架构

### 主分片与副本分片

**概念定义**:
主分片（Primary Shard）是数据写入的第一入口，每个 Index 的每个主分片负责一部分数据（由 routing 算法决定）。副本分片（Replica Shard）是主分片的完整拷贝，不参与写入决策，仅用于数据冗余和读负载分担。当主分片所在节点宕机时，ES 自动将副本分片提升为主分片，保证集群可用。

**核心参数**:

| 参数 | 说明 |
|------|------|
| Primary Shard | 写入入口，创建索引时确定，不可变 |
| Replica Shard | 主分片的同步拷贝，可动态增删 |
| 写入流程 | Primary → Replica（同步复制） |
| 读请求 | 轮询主分片和副本分片（负载均衡） |
| 故障转移 | 副本提升为主分片，ES 自动重建缺失副本 |

**REST API 示例**:

```bash
# 创建索引（指定主分片和副本数）
PUT /orders
{
  "settings": {
    "number_of_shards": 3,
    "number_of_replicas": 1
  }
}

# 查看分片分布（prirep=p=主分片, r=副本分片）
GET /_cat/shards/orders?v

# 提升副本为主分片（ES 自动执行，无需手动干预）
# 仅当节点宕机时触发，可观察过程：
GET /_cat/recovery/orders?v&active_only=true

# 手动触发副本同步（正常情况下不需要）
POST /orders/_flush/synced
```

**注意事项**:
- 写入请求到达主分片后，主分片先执行写入，再并行转发到所有副本分片。默认等待多数分片（quorum）确认后返回。
- 副本分片越多，写入延迟越高（需要同步到更多副本），但读吞吐越大。
- 生产环境建议：主分片 3 个 + 副本 1 个 = 6 个分片，部署在 3 个以上节点，容忍单节点故障。
- 副本分片和主分片绝对不在同一节点，ES 分配算法自动保证。
- 副本分片独立执行段合并，可能导致主副分片磁盘占用差异。

---

### 路由算法（routing）

**概念定义**:
路由算法决定 Document 被分配到哪个主分片。ES 默认使用 `_id` 的哈希值取模分片数来确定目标分片：`shard_num = hash(_routing) % number_of_primary_shards`。路由值可自定义，确保相同路由值的文档分配到同一分片。

**核心参数**:

| 参数 | 说明 |
|------|------|
| 默认路由值 | `_id`（文档 ID） |
| 自定义路由值 | 通过 `routing` 参数指定 |
| 哈希算法 | `hash` 函数（基于 MurmurHash3） |
| 取模基数 | 主分片数（`number_of_shards`） |
| 分片不可变 | 主分片数不可变，意味着路由算法不可变 |

**REST API 示例**:

```bash
# 写入时指定路由值
POST /orders/_doc/1001?routing=user_123
{
  "user_id": "user_123",
  "amount": 299.00,
  "product": "机械键盘"
}

# 查询时指定路由值（避免广播到所有分片）
GET /orders/_search?routing=user_123
{
  "query": {
    "term": { "user_id": "user_123" }
  }
}

# 批量写入时指定路由值
POST /_bulk
{ "index": { "_index": "orders", "_id": "2001", "routing": "user_123" } }
{ "amount": 100.00 }
{ "index": { "_index": "orders", "_id": "2002", "routing": "user_123" } }
{ "amount": 200.00 }

# 查看文档所属分片
GET /orders/_search?routing=user_123
{
  "query": { "term": { "user_id": "user_123" } },
  "explain": true
}
```

**注意事项**:
- 路由值相同的文档一定落在同一分片，这可用于实现"按用户隔离"或"父子文档同分片"。
- 自定义路由可能导致数据倾斜（热点分片），需评估路由值的分布均匀性。
- 不指定 `routing` 时，查询请求会广播到所有分片，增加集群负载。若已知目标分片，显式指定 `routing` 可大幅提升查询性能。
- `_routing` 默认开启（Mapping 中 `_routing: { required: false }`），设为 `required: true` 后写入必须指定路由值。
- 主分片数不可变，因此路由算法不可变 —— 这是 `number_of_shards` 创建后不可修改的根本原因。

---

### 写一致性（quorum）

**概念定义**:
写一致性（Write Consistency）定义了写入操作需获得多少个分片确认后才返回成功。ES 默认使用 quorum 机制（多数原则）：`int( (primary + number_of_replicas) / 2 ) + 1`。例如 1 主 + 1 副本 = 2 分片，quorum = `int(2/2)+1 = 2`，即需要主分片和副本分片都确认。

**核心参数**:

| 参数 | 说明 |
|------|------|
| `wait_for_active_shards` | 写入前需等待多少分片处于 active 状态，默认 1（仅主分片） |
| quorum 计算 | `int( (primary + replicas) / 2 ) + 1` |
| 超时 | `timeout` 参数，默认 1 分钟 |
| 写入失败处理 | 主分片写入成功 + 副本同步失败 → 副本标记为 stale → 后台自动修复 |

**REST API 示例**:

```bash
# 写入时要求所有分片确认（all = 主分片 + 所有副本）
POST /orders/_doc/1001?wait_for_active_shards=all
{
  "amount": 299.00
}

# 写入时要求至少 2 个分片确认
POST /orders/_doc/1002?wait_for_active_shards=2&timeout=30s
{
  "amount": 199.00
}

# 查看分片 active 状态
GET /_cat/shards/orders?v&h=index,shard,prirep,state

# 索引级设置默认 wait_for_active_shards
PUT /orders/_settings
{
  "index.write.wait_for_active_shards": "all"
}
```

**注意事项**:
- `wait_for_active_shards` 仅检查分片是否 active，不检查副本数据是否与主分片一致。
- 若 `wait_for_active_shards` > 集群中可用分片数，写入会超时失败。
- 默认 `wait_for_active_shards=1` 意味着只要主分片 active 即可写入，此时若副本分片不可用，数据仅存在于主分片，存在单点故障风险。
- 生产环境建议设置为 `all` 或至少 `quorum`，确保数据可靠性。
- 写入超时不会自动回滚已写入主分片的数据（ES 无事务回滚），需业务层处理。

---

### 节点角色（Master / Data / Ingest / Coordinating / ML）

**概念定义**:
节点角色定义了节点在集群中的职责。8.x 中通过 `node.roles` 数组配置，支持多角色组合。合理分配角色可避免资源竞争，提升集群稳定性。

**核心参数**:

| 角色 | 配置值 | 职责 |
|------|--------|------|
| **Master** | `master` | 管理集群元数据（Index 创建/删除、分片分配、节点加入/离开） |
| **Data** | `data` | 存储数据、执行索引和搜索操作 |
| **Data Content** | `data_content` | 存储常规内容数据（日志、搜索数据） |
| **Data Hot** | `data_hot` | 热数据节点（频繁写入/查询） |
| **Data Warm** | `data_warm` | 温数据节点（较少查询） |
| **Data Cold** | `data_cold` | 冷数据节点（很少查询） |
| **Data Frozen** | `data_frozen` | 冷冻数据节点（几乎不查询，searchable snapshot） |
| **Ingest** | `ingest` | 执行 Ingest Pipeline（预处理管道） |
| **ML** | `ml` | 机器学习作业（异常检测、分类） |
| **Remote Cluster Client** | `remote_cluster_client` | 跨集群搜索（CCS） |
| **Transform** | `transform` | 执行 Transform 作业 |
| **Coordinating** | 无显式角色（去掉所有角色） | 仅做请求路由和结果合并（不存数据、不 master） |

**REST API 示例**:

```bash
# 查看节点角色
GET /_cat/nodes?v&h=name,node.role

# 查看节点角色详情
GET /_nodes?filter_path=nodes.*.roles

# 查看节点角色统计
GET /_nodes/stats?filter_path=nodes.*.roles,nodes.*.name
```

**elasticsearch.yml 配置示例**:

```yaml
# --- 专用 Master 节点 ---
node.name: master-1
node.roles: [ master ]
cluster.initial_master_nodes: [ "master-1", "master-2", "master-3" ]

# --- 热数据节点 ---
node.name: data-hot-1
node.roles: [ data_hot, data_content, ingest ]

# --- 温数据节点 ---
node.name: data-warm-1
node.roles: [ data_warm ]

# --- 协调节点（仅请求路由） ---
node.name: coordinating-1
node.roles: [ ]  # 空角色 = 仅协调

# --- Ingest 节点 ---
node.name: ingest-1
node.roles: [ ingest ]

# --- ML 节点 ---
node.name: ml-1
node.roles: [ ml, remote_cluster_client ]
```

**注意事项**:
- 8.x 中角色配置使用 `node.roles` 数组，不再使用旧版 `node.master: true` / `node.data: false` 布尔值。
- Master 节点建议 3 个（奇数），专用 Master 节点不存数据（`node.roles: [ master ]`），内存 4-8GB 即可。
- Data 节点必须是集群中资源最充裕的节点（CPU、内存、磁盘），建议 SSD 存储。
- Coordinating 节点无数据无状态，可横向扩展，适合作为客户端请求入口。
- 生产环境务必分离 Master 和 Data 角色，避免 Data 节点 OOM 或 GC 导致 Master 功能不可用。
- 9.x 中节点角色模型基本延续 8.x，但 ML 角色功能增强（LLM 可观测性、语义搜索推理）。

## 近实时搜索

### 近实时（NRT）机制

**概念定义**:
近实时（Near Real-Time，NRT）指文档写入后不能立即被搜索到，需等待 Refresh 操作将内存中的 Segment 刷到文件系统缓存后才能被检索。默认 `refresh_interval` 为 1 秒，即写入后最多 1 秒可被搜索到。这是 ES 在"写入性能"和"搜索可见性"之间的权衡。

**核心参数**:

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `refresh_interval` | 1s | Refresh 间隔，-1 表示禁用自动 Refresh |
| NRT 延迟 | ~1s | 写入后最晚被搜索到的延迟 |
| 写入路径 | Buffer → Refresh → Segment（文件系统缓存）→ 可搜索 |
| 持久化路径 | Buffer → Translog → Flush → 磁盘 |

**REST API 示例**:

```bash
# 查看索引 refresh 间隔
GET /products/_settings?filter_path=*.settings.index.refresh_interval

# 修改 refresh 间隔（Bulk 导入时设为 -1）
PUT /products/_settings
{
  "index.refresh_interval": "-1"
}

# 手动触发 Refresh
POST /products/_refresh

# 导入完成后恢复
PUT /products/_settings
{
  "index.refresh_interval": "1s"
}

# 写入时强制 Refresh（影响性能，仅调试用）
POST /products/_doc/1001?refresh=true
{
  "name": "急用商品"
}

# 等待 Refresh（wait_for 模式）
POST /products/_doc/1001?refresh=wait_for
{
  "name": "等刷新后再返回"
}
```

**注意事项**:
- `refresh_interval` 设为 -1 后，文档写入后完全不可搜索，需手动调用 `_refresh` 或恢复间隔。
- Bulk 大量导入时建议 `refresh_interval: -1` + `number_of_replicas: 0`，导入完成后恢复，可提升 3-5 倍写入吞吐。
- `refresh=wait_for` 会阻塞请求直到下一次 Refresh 完成，适用于需要"写入后立即可见"的场景，但会显著拖慢写入速度。
- 频繁 Refresh 会产生大量小 Segment，增加段合并开销，不建议设置过短间隔（如 < 1s）。

---

### Refresh

**概念定义**:
Refresh 是将内存 Buffer 中的文档写入新的 Segment 并打开（使其可被搜索）的过程。Refresh 不涉及磁盘写入，仅将 Segment 写入文件系统缓存（Page Cache），因此速度快于 Flush。Refresh 是 NRT 机制的核心。

**核心参数**:

| 参数 | 说明 |
|------|------|
| 触发时机 | 定时（`refresh_interval`）或手动（`_refresh` API） |
| 写入目标 | 文件系统缓存（Page Cache），非磁盘 |
| 数据结构 | 新 Segment（不可变） |
| 性能影响 | 频繁 Refresh 产生大量小 Segment，增加段合并开销 |

**REST API 示例**:

```bash
# 手动 Refresh 整个索引
POST /products/_refresh

# Refresh 多个索引
POST /products,orders/_refresh

# Refresh 所有索引
POST /_refresh

# 查看 Refresh 统计
GET /products/_stats/refresh?pretty
```

**注意事项**:
- Refresh 不会将数据持久化到磁盘，断电后文件系统缓存中的数据会丢失（需通过 Translog 恢复）。
- 每次 Refresh 生成一个新的 Segment，大量小 Segment 会降低搜索性能，最终由段合并（Merge）自动合并。
- 不建议在写入高峰期频繁手动 Refresh，会影响写入性能。
- Refresh 的频率由 `refresh_interval` 控制，设得越短，搜索可见性越高，但写入吞吐越低。

---

### Flush

**概念定义**:
Flush 是将文件系统缓存中的 Segment 持久化到磁盘，并同步清空 Translog 的过程。Flush 确保数据在断电后不会丢失。与 Refresh 不同，Flush 涉及磁盘 I/O，成本较高，因此不频繁执行（默认 30 分钟或 Translog 达到 512MB 时触发）。

**核心参数**:

| 参数 | 说明 |
|------|------|
| 触发条件 | 定时（默认 30min）或 Translog 大小达到阈值（默认 512MB） |
| 写入目标 | 磁盘 |
| 操作步骤 | 1. Refresh → 2. fsync 磁盘 → 3. 清空 Translog（创建新 Translog） |
| 性能影响 | 写入磁盘 I/O，较 Refresh 重得多 |

**REST API 示例**:

```bash
# 手动 Flush 索引
POST /products/_flush

# Flush 时等待（同步）
POST /products/_flush?wait_if_ongoing=true

# Flush 并强制（即使没有必要）
POST /products/_flush?force=true

# 查看 Flush 统计
GET /products/_stats/flush?pretty
```

**注意事项**:
- Flush 后数据才真正持久化到磁盘，之前的 Refresh 仅保证数据在文件系统缓存中可见。
- 不建议频繁手动 Flush，会触发大量磁盘 I/O，影响写入性能。
- `force=true` 会强制 Flush 即使没有数据需要持久化，通常用于冷索引或备份前。
- 节点宕机恢复时，ES 通过重放 Translog 恢复未 Flush 的数据，因此 Translog 的完整性至关重要。

---

### Translog

**概念定义**:
Translog（事务日志）是 Elasticsearch 的 Write-Ahead Log（WAL），记录所有尚未 Flush 到磁盘的写入操作。当节点宕机后重启，ES 通过重放 Translog 恢复丢失的数据。每个 Shard 拥有独立的 Translog，是 ES 数据可靠性的核心保障。

**核心参数**:

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `index.translog.durability` | `request` | 持久化策略：`request`（每次请求后 fsync）或 `async`（异步） |
| `index.translog.sync_interval` | 5s | 异步模式下 fsync 间隔 |
| `index.translog.flush_threshold_size` | 512MB | Translog 达到此大小时触发 Flush |
| `index.translog.retention.age` | 12h | Translog 保留时长（用于副本同步） |
| `index.translog.retention.size` | 512MB | Translog 保留大小上限 |

**REST API 示例**:

```bash
# 查看 Translog 设置
GET /products/_settings?filter_path=*.settings.index.translog

# 修改 Translog 持久化策略（异步模式，性能更高但断电有丢失风险）
PUT /products/_settings
{
  "index.translog.durability": "async",
  "index.translog.sync_interval": "10s"
}

# 查看 Translog 统计
GET /products/_stats/translog?pretty

# 恢复默认持久化策略
PUT /products/_settings
{
  "index.translog.durability": "request"
}
```

**注意事项**:
- `request` 模式（默认）：每次写入后强制 fsync Translog 到磁盘，保证数据不丢失，但写入延迟较高。适合数据可靠性要求高的场景。
- `async` 模式：按 `sync_interval` 定期 fsync，写入吞吐更高，但断电可能丢失最近一个间隔内的数据。适合日志类可容忍少量丢失的场景。
- Translog 大小达到 `flush_threshold_size` 时触发 Flush，Flush 成功后清空 Translog。
- 如果 Translog 所在磁盘写满，写入请求会失败，需确保 Translog 路径有充足磁盘空间（`path.data` 下的 translog 子目录）。
- Translog 保留策略：副本同步延迟较大时，需保留更长时间的 Translog 以便副本追赶。

---

### Segment 与段合并

**概念定义**:
Segment 是 Lucene 的最小索引单元，每个 Segment 是一个不可变的倒排索引文件。每次 Refresh 生成一个新的 Segment，随着时间推移，大量小 Segment 会降低搜索性能并浪费文件句柄。段合并（Segment Merge）是将多个小 Segment 合并为一个大 Segment 的后台过程，合并后删除旧 Segment。

**核心参数**:

| 参数 | 说明 |
|------|------|
| 合并策略 | TieredMergePolicy（8.x 默认） |
| `index.merge.policy.max_merged_segment` | 合并后最大段大小，默认 5GB |
| `index.merge.policy.segments_per_tier` | 每层允许的段数量，默认 10 |
| `index.merge.scheduler.max_thread_count` | 合并线程数，默认 `Math.max(1, Math.min(4, CPU/2))` |
| `index.merge.policy.floor_segment` | 小于此大小的段优先合并，默认 2MB |

**REST API 示例**:

```bash
# 强制段合并（合并为 1 个段，仅用于不再写入的索引）
POST /products/_forcemerge?max_num_segments=1

# 查看段信息
GET /products/_segments?pretty

# 查看段合并统计
GET /products/_stats/merge?pretty

# 限制合并线程数（降低对写入的影响）
PUT /products/_settings
{
  "index.merge.scheduler.max_thread_count": 1
}
```

**注意事项**:
- 段合并是 I/O 密集型操作，合并过程中会占用额外的磁盘空间（旧段 + 新段同时存在），需预留 50% 以上磁盘冗余。
- 不要在写入活跃的索引上执行 `_forcemerge`（强制合并为 1 个段），会严重影响写入性能，且合并后新写入仍会产生新段。
- `_forcemerge` 仅适用于不再有写入的"静态"索引（如按天切分的日志索引归档后），可减少段数量、释放磁盘空间。
- 合并线程数不宜设置过高，默认值 `max(1, min(4, CPU核数/2))` 已较为合理，过大会挤占搜索和写入的 CPU 资源。
- 每个 Segment 都需要一个文件句柄，段数量过多会导致 "too many open files" 错误，通过段合并或调高系统 `ulimit` 解决。

## 版本差异

### 8.x 关键变化（Type 移除、安全默认开启、新 Java Client）

**Type 移除**:

| 维度 | 7.x | 8.x |

| Index Template | 兼容旧版 `_template` API | 建议 Composable Index Template |

**安全默认开启**:

| 维度 | 7.x | 8.x |
|------|-----|-----|
| `xpack.security.enabled` | 默认 `false` | 默认 `true` |
| HTTP 协议 | 默认 HTTP | 默认 HTTPS（自签证书） |
| 节点间通信 | 默认未加密 | 默认 TLS 加密 |
| 认证方式 | 需手动配置 | 自动生成 `elastic` 用户密码 + enrollment token |
| 内置用户 | 需手动创建 | 自动创建 `elastic`、`kibana_system` 等 |

**Java Client 变更**:

| 维度 | 7.x | 8.x |
|------|-----|-----|
| 官方推荐客户端 | High Level REST Client | **Java API Client** (`co.elastic.clients:elasticsearch-java`) |
| HLRC 状态 | 正常使用 | **已移除**（7.17 废弃） |
| Low Level REST Client | 可用 | 仍可用（作为 Transport 层） |
| 依赖坐标 | `org.elasticsearch.client:elasticsearch-rest-high-level-client` | `co.elastic.clients:elasticsearch-java` |
| JSON 序列化 | Jackson | Jackson（默认）或 JSON-B |
| Builder 模式 | 方法链 Builder | Lambda Builder（`e -> e.index("xxx").id("1")`） |
| 最低 Java 版本 | Java 8 | **Java 17** |

**其他关键变化**:

| 变化 | 说明 |
|------|------|
| 默认分片数 | 从 5 调整为 1（减少小索引过度分片） |
| `action.destructive_requires_name` | 默认 `true`，防止误删全索引（`DELETE /*` 被禁止） |
| `indices.query.bool.max_clause_count` | 从 1024 调整为 4096 |
| Data Stream | 正式 GA，与 ILM/Fleet 深度集成 |
| 原生 kNN | `dense_vector` 字段类型支持 HNSW 索引，原生 kNN 检索 |
| RRF | Reciprocal Rank Fusion，混合 BM25 + 向量结果排序 |
| ES\|QL | 引入管道式查询语言，持续增强 |

**注意事项**:
- 从 7.x 升级到 8.x 前，必须通过 Kibana Upgrade Assistant 扫描所有废弃用法，尤其是多 Type 索引。
- 8.x 安全默认开启意味着所有客户端（包括 Kibana、Logstash、Beats、Java 应用）都必须配置 TLS 证书和认证凭据。
- HLRC 在 8.x 中已完全不可用，Java 项目必须迁移至 Java API Client 或继续使用 Low Level REST Client + 手写 JSON 序列化。
- 8.x 要求 Java 17，ES 安装包自带 bundled JDK，无需系统安装 Java。
- 跨 Major 升级路径：7.17 → 8.0 → 8.x 最新版本，不支持 8.x 降级回 7.x。

### 9.x 新特性（Lucene 10、ES\|QL 增强、semantic_text）

**Lucene 10 升级**:

| 维度 | 8.x (Lucene 9.x) | 9.x (Lucene 10.1.0) |
|------|-------------------|----------------------|
| 并行处理 | 传统线程模型 | 更好的并行处理能力 |
| 索引机制 | 传统索引写入 | 更智能的索引写入机制 |
| 硬件优化 | 通用优化 | 针对现代硬件深度优化 |
| Segment 存储 | 传统格式 | 优化后的存储格式 |
| 发布年份 | 2022-2025 | 2025.04 |

**ES\|QL 增强**:

| 特性 | 说明 | 状态 |
|------|------|------|
| INLINESTATS | 内联统计命令，简化统计查询语法 | 9.0 GA |
| 语义搜索支持 | 支持对 `semantic_text` 字段类型进行语义查询 | 9.0 GA |
| KQL 函数支持 | 在 ES\|QL 查询中使用 KQL (Kibana Query Language) 函数 | 9.0 GA |
| _score 字段 | 支持根据相关性评分对结果排序 | 9.0 GA |
| LOOKUP JOIN | 跨索引 JOIN 查询（关联参考数据） | 8.18 技术预览，9.0 增强 |

**semantic_text 字段类型**:

| 维度 | 说明 |
|------|------|
| 定义 | 自动处理文本嵌入（embedding）的字段类型，简化语义搜索配置 |
| 8.x 状态 | 8.18 起 GA（正式发布） |
| 9.x 状态 | 持续增强，与 ES\|QL 深度集成 |
| 优势 | 无需手动管理 embedding 模型推理管道，ES 自动完成 |
| 底层 | 依赖 inference endpoint（需配置推理模型，如 ELSER、E5 等） |

**semantic_text 使用示例**:

```bash
# 创建索引（使用 semantic_text 字段）
PUT /articles
{
  "mappings": {
    "properties": {
      "title": { "type": "text" },
      "content": { 
        "type": "semantic_text",
        "inference_id": "my-elser-model"
      }
    }
  }
}

# 语义搜索
GET /articles/_search
{
  "query": {
    "semantic": {
      "field": "content",
      "query": "如何优化 Elasticsearch 的写入性能"
    }
  }
}
```

**Better Binary Quantization (BBQ)**:

| 维度 | 说明 |
|------|------|
| 定义 | Elastic 自研的向量量化技术，将每个向量维度压缩为单个位（bit） |
| 优势 | 大幅减少存储空间和内存占用，保持高质量搜索结果 |
| 性能 | 官方宣称比 OpenSearch 快 5 倍 |
| 状态 | 9.0 GA |

**其他 9.x 新特性**:

| 特性 | 说明 |
|------|------|
| EDOT | Elastic Distributions of OpenTelemetry，原生 OpenTelemetry 架构支持 |
| LLM 可观测性 | 对 Bedrock / Vertex AI / Azure OpenAI / OpenAI 的性能、提示、成本全面监控 |
| 攻击发现 | AI 驱动的安全分析，自动识别潜在安全威胁 |
| `rank_vectors` | 多向量 late-interaction 排序字段（支持 ColBERT / ColPali 模型） |
| `dense_vector` dims 类型 | 9.x 中 `dims` 从 `int` 调整为 `integer` 类型 |

**注意事项**:
- 9.x 于 2025 年 4 月 15 日发布，基于 Lucene 10.1.0，底层存储格式可能与 8.x 不兼容，升级前需做全量快照。
- `semantic_text` 字段类型在 8.18 已 GA，但 9.x 中与 ES\|QL 的集成更完善，建议在 9.x 中作为语义搜索首选方案。
- BBQ 是向量搜索场景的重要优化，如果 8.x 中使用了 `dense_vector` + HNSW，升级到 9.x 后可考虑启用 BBQ 减少内存占用。
- 9.x 的 LLM 可观测性需要配合 Elastic APM Agent 使用，对 Java 应用通过 `elastic-apm-agent` 自动检测。
- 8.x 升级到 9.x 的路径：8.18 → 9.0 → 9.x 最新。跨 Major 升级前务必执行 Upgrade Assistant 检查。
- 9.x 文档结构变化较大，官方文档域名从 `elastic.co/guide` 改为 `elastic.co/docs`，搜索时注意版本选择。
