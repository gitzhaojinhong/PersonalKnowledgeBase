
## 向量搜索概述

### Embedding 与向量

**概念定义**

Embedding 是将非结构化数据（文本、图像、音频）映射到高维连续向量空间的过程。一个 Embedding 是一个固定维度的浮点数数组 `[0.12, -0.34, 0.78, ...]`，语义相近的内容在向量空间中距离更近。

在 Elasticsearch 中，向量以 `dense_vector` 字段类型存储，每个文档可携带一个或多个向量，用于后续的 kNN 检索。

**核心参数（Embedding 模型侧）**

| 参数 | 含义 | 典型值 |
|------|------|--------|
| `dimensions` | 向量维度 | 384 / 768 / 1024 / 1536 |
| `normalize` | 是否 L2 归一化 | true（cosine 场景） |
| `model` | 生成模型名称 | text-embedding-ada-002 / all-MiniLM-L6-v2 |
| `max_seq_length` | 最大输入 token 数 | 512 / 8192 |

**REST API 示例**

```bash
# 查看集群中已部署的 Embedding 模型
curl -X GET "localhost:9200/_ml/trained_models?filter_path=trained_model_config_info.model_id" \
  -H "Authorization: ApiKey ${ES_API_KEY}"

# 使用 Inference API 生成向量
curl -X POST "localhost:9200/_inference/text_embedding/my-embedding-model" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "input": "Elasticsearch 向量搜索"
  }'
```

**注意事项**

- 向量维度一旦设定不可修改，需在建模阶段确定。
- 不同模型生成的向量不可混用（余弦空间不兼容），更换模型需全量重建索引。
- 建议在写入前对向量做 L2 归一化，以兼容 cosine 相似度计算。

---

### 向量相似度

**概念定义**

向量相似度衡量两个向量在多维空间中的距离或方向差异，是 kNN 检索的数学基础。Elasticsearch 支持三种相似度度量：

| 度量 | 公式 | 适用场景 | 值域 |
|------|------|----------|------|
| `cosine` | cos(theta) = (A dot B) / (|A| * |B|) | 语义搜索（方向敏感） | [-1, 1] |
| `dot_product` | A dot B = sum(A_i * B_i) | 已归一化向量的高效计算 | (-inf, +inf) |
| `l2_norm` | sqrt(sum((A_i - B_i)^2)) | 图像/特征匹配（绝对距离） | [0, +inf) |

**核心参数**

| 参数 | 含义 | 可选值 | 默认值 |
|------|------|--------|--------|
| `similarity` | 相似度度量函数 | `cosine` / `dot_product` / `l2_norm` | `cosine` |
| `index` | 是否建立向量索引 | `true` / `false` | `true` |

**REST API 示例**

```bash
# 创建使用 cosine 相似度的索引
curl -X PUT "localhost:9200/my-vector-index" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "mappings": {
      "properties": {
        "my_vector": {
          "type": "dense_vector",
          "dims": 768,
          "similarity": "cosine"
        }
      }
    }
  }'
```

**注意事项**

- `cosine` 是默认值，Elasticsearch 内部会对向量做归一化以优化计算。
- 当向量已归一化时，`dot_product` 与 `cosine` 等价，但 `dot_product` 计算更快。
- `l2_norm` 适合需要绝对距离的场景，对向量量级敏感，需注意特征缩放。
- 相似度选择影响索引结构（HNSW 图构建），建索引后不可更改。

### 应用场景

**概念定义**

向量搜索在 Elasticsearch 中主要覆盖三大场景：语义搜索、图片搜索、RAG（检索增强生成）。

**语义搜索**

传统 BM25 基于词频匹配，无法理解"新能源车"与"电动汽车"的语义等价关系。向量搜索通过 Embedding 将查询和文档映射到同一语义空间，实现"理解含义"的检索。

```
传统搜索："新能源车" → 仅匹配包含"新能源车"的文档
向量搜索："新能源车" → 匹配"电动汽车""清洁能源汽车""Tesla Model 3"等语义相关文档
```

**图片搜索**

将图片编码为向量（通过 CLIP 等视觉模型），在向量空间中以图搜图。ES 中存储图片向量，查询时输入图片向量进行 kNN 检索。

**RAG（检索增强生成）**

RAG 是 LLM 应用的核心范式：用户提问 → 向量检索召回相关文档片段 → 将片段作为上下文注入 LLM Prompt → 生成带引用的回答。Elasticsearch 作为 RAG 的检索后端，提供向量存储、混合检索、RRF 融合等能力。

**核心参数（RAG 场景）**

| 参数 | 含义 | 典型值 |
|------|------|--------|
| `k` | 召回 Top-K 文档数 | 10 ~ 50 |
| `chunk_size` | 文档分块大小（字符） | 512 ~ 2048 |
| `chunk_overlap` | 分块重叠字符数 | 50 ~ 200 |
| `num_candidates` | 每个分片的候选数 | k * 10 ~ k * 20 |

**REST API 示例**

```bash
# RAG 检索：语义搜索召回 Top-5
curl -X POST "localhost:9200/knowledge-base/_search" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "knn": {
      "field": "content_vector",
      "query_vector": [0.12, -0.34, 0.78, ...],
      "k": 5,
      "num_candidates": 100
    },
    "_source": ["title", "content", "chunk_id"],
    "size": 5
  }'
```

**注意事项**

- 文档分块策略直接影响 RAG 召回质量：块太小丢失上下文，块太大稀释语义。
- 建议结合 BM25 做混合检索，弥补向量检索对精确关键词匹配的不足。
- 图片搜索需确保 Embedding 模型与图片特征对齐（如 CLIP 模型输出 768 维）。
- RAG 场景需关注延迟：向量检索 + 重排序 + LLM 推理的总延迟应在 2~5 秒内。

## dense_vector 字段

### 字段定义

**概念定义**

`dense_vector` 是 Elasticsearch 中存储稠密向量的字段类型。每个字段存储一个固定维度的浮点数数组，支持 kNN 搜索和精确向量检索。它是向量搜索的存储基础。

**核心参数**

| 参数 | 含义 | 可选值 | 默认值 | 版本要求 |
|------|------|--------|--------|----------|
| `dims` | 向量维度，必填 | 1 ~ 4096（8.x）/ 1 ~ 16384（部分版本） | 无 | 7.6+ |
| `index` | 是否建立 HNSW 索引 | `true` / `false` | `true` | 8.0+ |
| `similarity` | 相似度度量 | `cosine` / `dot_product` / `l2_norm` | `cosine` | 8.0+ |
| `index_options` | 索引配置对象 | `{type, m, ef_construction}` | `{}` | 8.0+ |
| `index_options.type` | 索引算法类型 | `hnsw` / `int8_hnsw` / `int4_hnsw` / `bbq` | `hnsw` | 8.0+ |
| `index_options.m` | HNSW 每层最大连接数 | 4 ~ 256 | 16 | 8.0+ |
| `index_options.ef_construction` | 构建时的动态候选列表大小 | 100 ~ 2000 | 100 | 8.0+ |

**REST API 示例**

```bash
# 创建带 dense_vector 的索引
curl -X PUT "localhost:9200/products" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "mappings": {
      "properties": {
        "name": { "type": "text" },
        "description": { "type": "text" },
        "name_vector": {
          "type": "dense_vector",
          "dims": 768,
          "index": true,
          "similarity": "cosine",
          "index_options": {
            "type": "hnsw",
            "m": 16,
            "ef_construction": 200
          }
        }
      }
    }
  }'

# 写入携向量文档
curl -X POST "localhost:9200/products/_doc" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "name": "无线蓝牙耳机",
    "description": "降噪 续航30小时 IPX5防水",
    "name_vector": [0.12, -0.34, 0.78, "..."]
  }'
```

**注意事项**

- `dims` 必填且不可动态修改。如需变更维度，需 Reindex。
- `index: false` 时字段只存储不索引，无法 kNN 搜索，只能用于 `script_score` 精确计算。
- `index_options.type` 从 8.10+ 开始支持 `int8_hnsw`，8.13+ 支持 `int4_hnsw`，8.16+ 支持 `bbq`。
- 每个 `dense_vector` 字段都会独立建立 HNSW 图，多向量字段会增加显著内存开销。

### 索引结构

**概念定义**

Elasticsearch 基于 HNSW（Hierarchical Navigable Small World）图算法构建向量索引。HNSW 是一种多层图结构，通过贪婪搜索在近似对数时间内找到最近邻。ES 在此基础上支持多种量化变体以降低内存占用。

**HNSW 图结构**

```
层级 2（顶层）:  ○───○        ← 少量节点，长距离连接
                  │
层级 1（中层）:  ○───○───○    ← 中等节点，中等距离连接
                  │   │
层级 0（底层）:  ○─○─○─○─○─○  ← 全部节点，短距离连接
```

搜索从顶层入口点开始，逐层下降到目标区域，在底层找到最近邻。

**核心参数**

| 参数 | 含义 | 可选值 | 默认值 |
|------|------|--------|--------|
| `index_options.type` | 索引/量化算法 | `hnsw` / `int8_hnsw` / `int4_hnsw` / `bbq` | `hnsw` |
| `index_options.m` | 每层每个节点的最大连接数 | 4 ~ 256 | 16 |
| `index_options.ef_construction` | 构建时的动态候选列表大小 | 100 ~ 2000 | 100 |

**各索引类型对比**

| 类型 | 存储方式 | 内存占用 | 召回率 | 适用场景 |
|------|----------|----------|--------|----------|
| `hnsw` | 全精度 float32 | 100%（基准） | ~100% | 高精度优先 |
| `int8_hnsw` | 8-bit 标量量化 | ~25% | ~99.5% | 内存敏感的生产环境 |
| `int4_hnsw` | 4-bit 标量量化 | ~12.5% | ~95%-98% | 大规模低精度场景 |
| `bbq` | 二进制量化（1-bit） | ~3% | ~90%-95% | 超大规模、极致降本 |

**REST API 示例**

```bash
# 使用 int8_hnsw 量化索引
curl -X PUT "localhost:9200/products-large" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "mappings": {
      "properties": {
        "desc_vector": {
          "type": "dense_vector",
          "dims": 768,
          "index": true,
          "similarity": "cosine",
          "index_options": {
            "type": "int8_hnsw",
            "m": 16,
            "ef_construction": 200
          }
        }
      }
    }
  }'
```

**注意事项**

- `m` 越大，图越稠密，召回率越高，但内存和构建时间也越大。`m=16` 是大多数场景的合理默认值。
- `ef_construction` 越大，构建时探索越充分，图质量越高，但构建时间线性增长。生产环境建议 `ef_construction=200~500`。
- `bbq` 提供极致压缩，但会显著降低召回率，建议配合 `oversampling` 和 `rerank` 使用。
- 量化类型在建索引时锁定，变更需 Reindex。

---

### 量化方式对比

**概念定义**

量化是将 float32 向量压缩为更低精度表示的技术，以大幅降低内存占用和存储成本，同时尽可能保持检索质量。Elasticsearch 提供标量量化（int8/int4）和二进制量化（bbq）两种策略。

**核心参数**

| 参数 | 含义 | 量化类型 | 压缩比 |
|------|------|----------|--------|
| `int8_hnsw` | 8-bit 标量量化：每个维度 1 字节 | 标量量化 | 4:1 |
| `int4_hnsw` | 4-bit 标量量化：每个维度 0.5 字节 | 标量量化 | 8:1 |
| `bbq` | 二进制量化：每个维度 1 bit | 二进制量化 | 32:1 |

**量化机制**

```
float32: [0.1234, -0.5678, 0.9012, -0.3456, ...] → 每维 4 bytes

int8:    将 float32 线性映射到 [-128, 127]
         [  31,    -145,    230,    -88, ...] → 每维 1 byte

int4:    将 float32 线性映射到 [-8, 7]
         [   2,      -7,      7,     -4, ...] → 每维 0.5 bytes

bbq:     按符号转换为 0/1
         [   1,       0,      1,      0, ...] → 每维 1 bit
```

**REST API 示例**

```bash
# 对比三种量化类型的内存占用
# 方式一：int8_hnsw
curl -X PUT "localhost:9200/idx-int8" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "mappings": {
      "properties": {
        "vec": {
          "type": "dense_vector",
          "dims": 768,
          "index_options": { "type": "int8_hnsw", "m": 16, "ef_construction": 200 }
        }
      }
    }
  }'

# 方式二：bbq（二进制量化）
curl -X PUT "localhost:9200/idx-bbq" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "mappings": {
      "properties": {
        "vec": {
          "type": "dense_vector",
          "dims": 768,
          "index_options": { "type": "bbq", "m": 16, "ef_construction": 200 }
        }
      }
    }
  }'
```

**注意事项**

- 量化会损失精度，建议在非生产环境先做召回率基准测试（@k=10, @k=100）。
- `bbq` 适合十亿级向量库，但需预期 5%~10% 的召回率下降。
- 量化类型与 `similarity` 参数兼容：`cosine` 和 `dot_product` 在所有量化类型下均可用。
- 8.x 中 `int4_hnsw` 和 `bbq` 为技术预览，9.x 中已成熟。

## sparse_vector 与 ELSER

### ELSER 模型

**概念定义**

ELSER（Elastic Learned Sparse EncodeR）是 Elastic 自研的稀疏向量检索模型。与稠密向量不同，ELSER 将文本映射为高维稀疏向量——大部分维度为 0，只有少数维度有非零权重，每个非零维度对应一个可解释的词项权重。ELSER 天然支持词汇扩展（如 "car" 自动扩展为 "automobile"、"vehicle"），无需同义词词典。

**核心参数**

| 参数 | 含义 | 可选值 | 默认值 |
|------|------|--------|--------|
| `model_id` | 模型 ID | `.elser_model_2` / `.elser_model_2_linux-x86_64` | — |
| `input` | 输入文本 | string / string[] | — |
| `max_token_length` | 最大 token 长度 | — | 512 |

**模型版本**

| 模型 | 说明 | 维度 |
|------|------|------|
| `.elser_model_1` | 初版（已废弃） | ~30,000 |
| `.elser_model_2` | 当前推荐版本，支持多语言 | ~30,000 |
| `.elser_model_2_linux-x86_64` | 优化版，本地部署 | ~30,000 |

**REST API 示例**

```bash
# 1. 下载并部署 ELSER 模型
curl -X PUT "localhost:9200/_ml/trained_models/.elser_model_2_linux-x86_64" \
  -H "Authorization: ApiKey ${ES_API_KEY}"

# 2. 启动模型部署
curl -X POST "localhost:9200/_ml/trained_models/.elser_model_2_linux-x86_64/deployment/_start" \
  -H "Authorization: ApiKey ${ES_API_KEY}"

# 3. 使用 ELSER 生成稀疏向量
curl -X POST "localhost:9200/_ml/trained_models/.elser_model_2_linux-x86_64/_infer" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "docs": [{ "text_field": "弹性搜索的向量搜索功能" }]
  }'
```

**注意事项**

- ELSER 模型部署需要至少 4GB 堆外内存，生产环境建议 8GB+。
- 模型首次下载约 500MB，需确保集群有外网访问权限。
- ELSER 是稀疏向量，存储开销远小于同维度的 dense_vector，但检索精度在特定领域（如专业术语）可能不如专用稠密模型。
- 9.x 中 ELSER 可通过 `semantic_text` 字段自动调用，简化配置。

### 稀疏向量搜索

**概念定义**

稀疏向量（sparse_vector）是大部分维度为 0 的向量，每个非零维度（特征）具有可解释的权重。与 dense_vector 的"语义黑盒"相比，稀疏向量每个维度对应一个具体的词项，兼具语义扩展和可解释性。`sparse_vector` 字段类型在 Elasticsearch 8.x 中引入，专为 ELSER 等稀疏编码模型设计。

**核心参数**

| 参数 | 含义 | 可选值 | 默认值 |
|------|------|--------|--------|
| `type` | 字段类型 | `sparse_vector` | — |
| `index` | 是否建立索引 | `true` / `false` | `true` |

**sparse_vector vs dense_vector**

| 特性 | sparse_vector | dense_vector |
|------|---------------|--------------|
| 维度 | ~30,000（大部分为 0） | 384 ~ 1536（全非零） |
| 存储效率 | 高（仅存非零项） | 低（全量存储） |
| 可解释性 | 强（词项级权重） | 弱（黑盒向量） |
| 语义扩展 | 原生支持 | 依赖模型 |
| 跨语言 | ELSER 支持多语言 | 依赖多语言模型 |

**REST API 示例**

```bash
# 创建 sparse_vector 索引
curl -X PUT "localhost:9200/sparse-search" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "mappings": {
      "properties": {
        "title": { "type": "text" },
        "title_sparse": { "type": "sparse_vector" }
      }
    }
  }'

# 使用 ELSER 推理管道写入
curl -X PUT "localhost:9200/_ingest/pipeline/elser-pipeline" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "processors": [{
      "inference": {
        "model_id": ".elser_model_2_linux-x86_64",
        "target_field": "title_sparse",
        "field_map": { "title": "text_field" }
      }
    }]
  }'

# 通过管道写入文档
curl -X POST "localhost:9200/sparse-search/_doc?pipeline=elser-pipeline" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{"title": "Elasticsearch 向量搜索最佳实践"}'

# 稀疏向量检索
curl -X POST "localhost:9200/sparse-search/_search" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "query": {
      "sparse_vector": {
        "field": "title_sparse",
        "inference_id": ".elser_model_2_linux-x86_64",
        "query": "如何优化搜索性能"
      }
    }
  }'
```

**注意事项**

- `sparse_vector` 字段仅支持 `sparse_vector` 查询，不支持 `knn` 查询。
- 写入时必须通过 Ingest Pipeline 或手动调用 `_infer` API 生成稀疏向量。
- ELSER 的 `sparse_vector` 查询天然支持词汇扩展，查询 "跑步" 可匹配 "慢跑"、"马拉松" 等。
- 稀疏向量查询可与 `bool` 查询组合，实现过滤 + 语义检索。

## kNN 搜索

### knn query

**概念定义**

`knn` query 是 Elasticsearch 8.0 引入的顶层查询类型，用于在 `dense_vector` 字段上执行 k-最近邻检索。与 `script_score` 查询不同，`knn` query 直接利用 HNSW 图索引进行近似搜索，速度远快于暴力扫描。

**核心参数**

| 参数 | 含义 | 类型 | 必填 |
|------|------|------|------|
| `field` | 目标 dense_vector 字段名 | string | 是 |
| `query_vector` | 查询向量（float 数组） | float[] | 是 |
| `k` | 返回的最近邻数量 | int | 是 |
| `num_candidates` | 每个分片的候选池大小 | int | 是 |
| `filter` | 预过滤条件 | query object | 否 |
| `similarity` | 覆盖索引的相似度设置 | float | 否 |
| `boost` | 查询权重（混合搜索用） | float | 否 |

**REST API 示例**

```bash
# 基础 kNN 查询
curl -X POST "localhost:9200/products/_search" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "knn": {
      "field": "name_vector",
      "query_vector": [0.12, -0.34, 0.78, 0.56, ...],
      "k": 10,
      "num_candidates": 100
    },
    "_source": ["name", "description"],
    "size": 10
  }'

# 带过滤条件的 kNN（仅搜索"电子产品"分类）
curl -X POST "localhost:9200/products/_search" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "knn": {
      "field": "name_vector",
      "query_vector": [0.12, -0.34, 0.78, 0.56, ...],
      "k": 10,
      "num_candidates": 100,
      "filter": {
        "term": { "category": "electronics" }
      }
    }
  }'
```

**注意事项**

- `knn` query 是顶层查询，不能嵌套在 `bool` 的 `must/should` 子句中。
- 如需与 `bool` 查询组合，使用 `knn` 作为独立子句，或使用混合搜索（RRF）。
- `knn` 查询返回的 `_score` 基于相似度值，不同相似度度量下的分数不可直接比较。
- 8.x 中 `knn` 查询支持 `filter` 参数做预过滤，但过滤条件会先执行，可能影响召回率。

### num_candidates 参数

**概念定义**

`num_candidates` 是 kNN 搜索中控制精度与速度平衡的核心参数。它定义了每个分片在执行 HNSW 图搜索时需要探索的候选节点数量。值越大，搜索越精确但越慢；值越小，搜索越快但可能漏掉真正的最近邻。

**工作原理**

```
kNN 搜索流程：
1. 从 HNSW 顶层入口点开始搜索
2. 逐层下降，每层维护一个大小为 ef 的动态候选列表
3. 在底层，候选列表大小 = num_candidates
4. 从 num_candidates 个候选中返回 Top-K 个结果
```

**核心参数**

| 参数 | 含义 | 推荐值 | 影响 |
|------|------|--------|------|
| `num_candidates` | 每分片候选池大小 | k * 10 ~ k * 50 | 精度 vs 延迟 |
| `k` | 返回结果数 | 10 ~ 100 | 业务需求 |
| 比值 `num_candidates / k` | 探索系数 | 10 ~ 20 | 越大召回率越高 |

**REST API 示例**

```bash
# 高精度模式（num_candidates = k * 50）
curl -X POST "localhost:9200/products/_search" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "knn": {
      "field": "name_vector",
      "query_vector": [0.12, -0.34, 0.78, ...],
      "k": 10,
      "num_candidates": 500
    }
  }'

# 低延迟模式（num_candidates = k * 5）
curl -X POST "localhost:9200/products/_search" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "knn": {
      "field": "name_vector",
      "query_vector": [0.12, -0.34, 0.78, ...],
      "k": 10,
      "num_candidates": 50
    }
  }'
```

**注意事项**

- `num_candidates` 不能小于 `k`，否则无法返回 k 个结果。
- 多分片场景下，`num_candidates` 是每个分片的候选数，总探索量 = `num_candidates * num_shards`。
- 推荐 `num_candidates = k * 10` 作为默认起点，根据召回率和延迟调优。
- `num_candidates` 越大，HNSW 图探索越充分，但内存中的临时候选列表也越大，需关注 GC 压力。

### 近似搜索 vs 精确搜索

**概念定义**

Elasticsearch 支持两种向量检索模式：**近似搜索（approximate）** 和 **精确搜索（exact）**。近似搜索通过 HNSW 图索引在亚线性时间内返回近似最近邻，精确搜索通过暴力扫描所有向量返回精确的 Top-K。

**对比**

| 特性 | 近似搜索（approximate） | 精确搜索（exact） |
|------|------------------------|-------------------|
| 实现方式 | `knn` query（HNSW 图） | `script_score` 查询 |
| 时间复杂度 | O(log N) | O(N) |
| 百万级数据延迟 | 10 ~ 50ms | 500ms ~ 数秒 |
| 召回率 | 95% ~ 99.9% | 100% |
| 索引要求 | `index: true` | `index: false` 也可 |
| 适用场景 | 生产环境实时搜索 | 离线评估、基准测试 |

**REST API 示例**

```bash
# 近似搜索（knn query）
curl -X POST "localhost:9200/products/_search" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "knn": {
      "field": "name_vector",
      "query_vector": [0.12, -0.34, 0.78, ...],
      "k": 10,
      "num_candidates": 100
    }
  }'

# 精确搜索（script_score）
curl -X POST "localhost:9200/products/_search" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "query": {
      "script_score": {
        "query": { "match_all": {} },
        "script": {
          "source": "cosineSimilarity(params.query_vector, '\''name_vector'\'') + 1.0",
          "params": {
            "query_vector": [0.12, -0.34, 0.78, ...]
          }
        }
      }
    }
  }'
```

**召回率评估**

**注意事项**

- 生产环境始终使用近似搜索（`knn` query），`script_score` 仅用于离线评估。
- 精确搜索在百万级数据量下延迟可能超过 1 秒，不可用于在线服务。
- 近似搜索的召回率可以通过增大 `num_candidates` 和 `ef_construction` 提升。
- 如果 `index: false`，只能使用 `script_score` 精确搜索。

### HNSW 算法原理

**概念定义**

HNSW（Hierarchical Navigable Small World）是一种基于图的近似最近邻搜索算法，由 Y. Malkov 和 D. Yashunin 于 2016 年提出。Elasticsearch 使用 HNSW 作为默认的向量索引算法。HNSW 通过构建多层可导航小世界图，在 O(log N) 时间内完成近邻搜索。

**核心数据结构**

```
层级结构（概率分配，类似跳表）：

层 2:  [N1]──────────────[N5]        ← 长距离边，快速跳跃
         │                │
层 1:  [N1]──[N2]──[N3]──[N5]       ← 中距离边
         │    │     │     │
层 0:  [N1]──[N2]──[N3]──[N4]──[N5]  ← 所有节点，短距离边（精确搜索）
```

**搜索流程（贪婪搜索）**

```
1. 从顶层随机入口点开始
2. 在当前层，维护候选列表，贪婪地向距离查询点更近的邻居移动
3. 当无法找到更近的邻居时，下降到下一层
4. 重复步骤 2-3，直到底层
5. 在底层返回 Top-K 个最近邻
```

**核心参数**

| 参数 | 含义 | 影响 | 推荐值 |
|------|------|------|--------|
| `M` | 每层每个节点的最大连接数 | 图密度 → 召回率 ↑ 内存 ↑ | 16 ~ 64 |
| `ef_construction` | 构建时的动态候选列表大小 | 图质量 ↑ 构建时间 ↑ | 100 ~ 500 |
| `ef_search` | 搜索时的动态候选列表大小（即 `num_candidates`） | 召回率 ↑ 延迟 ↑ | k * 10 ~ k * 50 |
| `level` | 节点的层级（随机分配，概率 1/M） | 高层节点少，低层节点多 | 自动 |

**注意事项**

- HNSW 图在构建时一次性生成，`M` 和 `ef_construction` 在建索引时确定，不可在线修改。
- `M` 每增加 1 倍，内存占用约增加 1 倍，召回率提升趋于平缓（边际递减）。
- Elasticsearch 的 HNSW 实现支持增量更新：新文档直接加入图，无需全量重建。
- HNSW 图在 Segment Merge 时需要重新构建，大 Segment 合并会导致显著的 CPU 开销。

## 混合搜索

### RRF

**概念定义**

RRF（Reciprocal Rank Fusion，倒数排名融合）是一种无监督的排名融合算法。它将多个独立排序列表（如 BM25 排序列表和 kNN 排序列表）合并为一个统一的排序结果。RRF 不依赖原始分数的量级，仅基于文档在各子列表中的排名位置计算融合分数。

**RRF 公式**

```
RRF_score(d) = sum_over_queries( 1 / (k + rank_i(d)) )

其中：
- rank_i(d)：文档 d 在第 i 个查询下的排名（从 1 开始）
- k：排名常数（默认 60），用于平滑排名差异
```

**核心参数**

| 参数 | 含义 | 可选值 | 默认值 |
|------|------|--------|--------|
| `rank_constant` | 排名常数 k | 1 ~ 1000 | 60 |
| `rank_window_size` | 参与融合的窗口大小 | 1 ~ 10000 | 100 |
| `retriever` | 子检索器 | `standard` / `knn` | — |

**REST API 示例**

```bash
# RRF 混合搜索：BM25 + kNN
curl -X POST "localhost:9200/products/_search" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "retriever": {
      "rrf": {
        "retrievers": [
          {
            "standard": {
              "query": {
                "multi_match": {
                  "query": "无线降噪耳机",
                  "fields": ["name^3", "description"]
                }
              }
            }
          },
          {
            "knn": {
              "field": "name_vector",
              "query_vector": [0.12, -0.34, 0.78, ...],
              "k": 10,
              "num_candidates": 100
            }
          }
        ],
        "rank_constant": 60,
        "rank_window_size": 100
      }
    },
    "size": 10
  }'
```

**注意事项**

- RRF 不依赖原始分数的绝对值，因此 BM25 分数和余弦相似度分数可以直接融合。
- `rank_constant` 默认 60 是经验值，减小该值会放大排名差异（头名权重更大），增大则更平滑。
- `rank_window_size` 限制了每个子检索器参与融合的文档数，超过窗口的文档不会被融合。
- 8.x 中 RRF 是 `retriever` 框架的一部分，需要 8.8+ 版本。
- 对于简单场景，可以直接在 `knn` 查询中加 `boost` 参数，然后使用 `bool` 查询组合。

### BM25 + 向量混合

**概念定义**

BM25 + 向量混合搜索结合了两种互补的检索范式：BM25 擅长精确关键词匹配和稀有词召回，向量搜索擅长语义理解和同义词扩展。混合搜索在实际应用中通常比单一检索方式提升 10%~30% 的召回率。

**组合方式**

```
方式一：RRF 融合（推荐）
  ┌──────────┐   ┌──────────┐
  │ BM25 查询 │   │ kNN 查询  │
  └────┬─────┘   └────┬─────┘
       │               │
       ▼               ▼
  ┌─────────────────────────┐
  │    RRF 融合排序          │
  └───────────┬─────────────┘
              ▼
       ┌──────────┐
       │ 最终结果  │
       └──────────┘

方式二：boost 加权（简单场景）
  ┌──────────────────────────────┐
  │  bool.should:                │
  │    - BM25 (boost: 1.0)      │
  │    - knn   (boost: 2.0)     │
  └──────────────────────────────┘
```

**核心参数**

| 参数 | 含义 | 典型值 |
|------|------|--------|
| `bm25_boost` | BM25 子查询权重 | 0.5 ~ 2.0 |
| `knn_boost` | kNN 子查询权重 | 0.5 ~ 3.0 |
| `rank_constant` | RRF 排名常数 | 60 |
| `rank_window_size` | RRF 融合窗口 | 100 ~ 200 |

**REST API 示例**

```bash
# 方式二：boost 加权混合（8.x 早期版本兼容）
curl -X POST "localhost:9200/products/_search" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "query": {
      "bool": {
        "should": [
          {
            "multi_match": {
              "query": "无线降噪耳机",
              "fields": ["name^3", "description"],
              "boost": 1.0
            }
          }
        ]
      }
    },
    "knn": {
      "field": "name_vector",
      "query_vector": [0.12, -0.34, 0.78, ...],
      "k": 10,
      "num_candidates": 100,
      "boost": 2.0
    },
    "size": 10
  }'
```

**注意事项**

- RRF 融合是推荐方式，避免 BM25 和向量分数的量级不匹配问题。
- `boost` 加权方式中，BM25 分数和向量相似度分数的量级不同，调优需反复试验。
- 混合搜索中，建议 kNN 的 `k` 值略大于最终返回数，以提供更多候选给 RRF 融合。
- 对于纯精确匹配场景（如 SKU 搜索），可降低向量权重，反之对于问答式搜索可提高向量权重。

### 权重调优

**概念定义**

权重调优是混合搜索中调整 BM25 和向量搜索贡献比例的过程。目标是在不同业务场景下找到最优的权重组合，以最大化目标指标（如 NDCG@10、MRR、点击率）。

**权重调优策略**

```
调优流程：
1. 建立标注数据集（Query → 相关文档列表）
2. 定义评估指标（NDCG@10 / Recall@10 / MRR）
3. 网格搜索权重组合（BM25: 0.0 ~ 3.0, kNN: 0.0 ~ 3.0）
4. 选择最优权重
5. 在线 A/B 验证
```

**核心参数**

| 参数 | 含义 | 典型值 | 调优方向 |
|------|------|--------|----------|
| `bm25_weight` | BM25 贡献权重 | 0.5 ~ 2.0 | 关键词精确匹配重要时增大 |
| `knn_weight` | 向量搜索贡献权重 | 0.5 ~ 3.0 | 语义理解重要时增大 |
| `total_weight` | 总权重（归一化） | 1.0 | 保持相对比例 |

**REST API 示例**

```bash
# 权重调优实验：BM25 权重 1.0, kNN 权重 2.0
curl -X POST "localhost:9200/products/_search" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "query": {
      "bool": {
        "should": [
          { "multi_match": { "query": "无线耳机", "fields": ["name^3", "description"], "boost": 1.0 } }
        ]
      }
    },
    "knn": {
      "field": "name_vector",
      "query_vector": [0.12, -0.34, 0.78, ...],
      "k": 10,
      "num_candidates": 100,
      "boost": 2.0
    },
    "size": 10
  }'
```

**注意事项**

- 权重调优应基于业务标注数据，而非直觉判断。
- 不同查询类型可能需要不同权重（如导航类查询增大 BM25，探索类查询增大 kNN）。
- 使用 RRF 时无需手动调权重，RRF 自动处理排名融合，这是 8.8+ 推荐的方式。
- 权重调优结果与环境相关，切换 Embedding 模型后需重新调优。

## semantic_text 字段（9.x）

### 自动 Embedding 生成

**概念定义**

`semantic_text` 是 Elasticsearch 9.x 引入的新字段类型，它将文本 Embedding 的生成过程完全自动化。开发者只需声明一个 `semantic_text` 字段并指定推理端点，ES 会在写入时自动调用 Inference API 生成向量，查询时自动将查询文本转为向量并执行 kNN 搜索。这消除了手动管理 Embedding 管道的复杂性。

**与 Ingest Pipeline 方式的对比**

```
传统方式（dense_vector + Pipeline）：
  写入: 文档 → Ingest Pipeline → Inference API → 向量 → dense_vector 字段
  查询: 查询文本 → 手动调用 Inference API → 向量 → knn query

semantic_text 方式（9.x）：
  写入: 文档 → 自动 Embedding → semantic_text 字段
  查询: 查询文本 → 自动 Embedding → 自动 kNN 搜索
```

**核心参数**

| 参数 | 含义 | 可选值 | 默认值 |
|------|------|--------|--------|
| `type` | 字段类型 | `semantic_text` | — |
| `inference_id` | 推理端点 ID | 已部署的推理模型 ID | 必填 |
| `search_inference_id` | 查询时使用的推理端点（可与写入不同） | 推理端点 ID | 同 `inference_id` |

**REST API 示例**

```bash
# 1. 创建推理端点（使用 ELSER 或 E5 等模型）
curl -X PUT "localhost:9200/_inference/text_embedding/my-e5-endpoint" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "service": "elasticsearch",
    "service_settings": {
      "model_id": ".multilingual-e5-small",
      "num_allocations": 1,
      "num_threads": 2
    }
  }'

# 2. 创建 semantic_text 索引
curl -X PUT "localhost:9200/semantic-products" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "mappings": {
      "properties": {
        "name": { "type": "text" },
        "description": {
          "type": "semantic_text",
          "inference_id": "my-e5-endpoint"
        }
      }
    }
  }'

# 3. 写入文档（无需手动生成向量）
curl -X POST "localhost:9200/semantic-products/_doc" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "name": "无线降噪耳机",
    "description": "主动降噪 续航30小时 IPX5防水 蓝牙5.3"
  }'

# 4. 语义搜索（查询文本自动转换为向量）
curl -X POST "localhost:9200/semantic-products/_search" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "query": {
      "semantic": {
        "field": "description",
        "query": "长续航的蓝牙耳机"
      }
    }
  }'
```

**注意事项**

- `semantic_text` 是 9.x 核心特性，8.x 中不可用，8.x 需使用 `dense_vector` + Ingest Pipeline。
- 写入时自动 Embedding 会增加写入延迟（取决于模型推理速度），高吞吐写入需评估性能。
- `search_inference_id` 允许写入和查询使用不同模型（如写入用大模型，查询用小模型降本）。
- 自动生成的向量存储在 `_source` 之外，不影响 `_source` 的可读性。

### 配置与使用

**概念定义**

`semantic_text` 的配置涉及两个步骤：创建推理端点（Inference Endpoint）和定义 `semantic_text` 字段映射。推理端点指定了 Embedding 模型的部署信息，`semantic_text` 字段引用该端点完成自动向量化。

**支持的推理服务**

| 服务类型 | 说明 | 配置示例 |
|----------|------|----------|
| `elasticsearch` | 内置 ELSER/E5 模型 | `service: "elasticsearch"` |
| `openai` | OpenAI Embedding API | `service: "openai"` |
| `hugging_face` | HuggingFace 推理端点 | `service: "hugging_face"` |
| `cohere` | Cohere Embed API | `service: "cohere"` |
| `mistral` | Mistral AI Embed API | `service: "mistral"` |

**核心参数**

| 参数 | 含义 | 必填 |
|------|------|------|
| `inference_id` | 推理端点 ID，在语义文本字段中引用 | 是 |
| `service` | 推理服务类型 | 是 |
| `model_id` | 模型 ID（elasticsearch 服务） | 是 |
| `num_allocations` | 模型部署分配数 | 否 |
| `num_threads` | 每个分配的推理线程数 | 否 |
| `chunk_size` | 文本分块大小（字符），长文本自动分块 | 否 |

**REST API 示例**

```bash
# 配置一：使用 E5 多语言模型
curl -X PUT "localhost:9200/_inference/text_embedding/e5-endpoint" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "service": "elasticsearch",
    "service_settings": {
      "model_id": ".multilingual-e5-small",
      "num_allocations": 2,
      "num_threads": 4
    }
  }'

# 配置二：使用 OpenAI Embedding
curl -X PUT "localhost:9200/_inference/text_embedding/openai-endpoint" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "service": "openai",
    "service_settings": {
      "api_key": "sk-xxxxxx",
      "model_id": "text-embedding-3-small",
      "dimensions": 1536
    }
  }'

# 创建多字段 semantic_text 索引
curl -X PUT "localhost:9200/multi-semantic" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "mappings": {
      "properties": {
        "title":   { "type": "semantic_text", "inference_id": "e5-endpoint" },
        "content": { "type": "semantic_text", "inference_id": "e5-endpoint" },
        "tags":    { "type": "keyword" }
      }
    }
  }'
```

**注意事项**

- 推理端点必须先于索引创建，否则索引创建会失败。
- `num_allocations` 决定模型的并发处理能力，生产环境建议 2+。
- 使用第三方服务（OpenAI/Cohere）需确保集群有外网访问权限。
- `semantic_text` 字段在查询时使用 `semantic` 查询，而非 `knn` 查询。

### 与 dense_vector 对比

**概念定义**

`semantic_text` 是 `dense_vector` 的更高层抽象，两者核心区别在于：`dense_vector` 需要开发者自行管理 Embedding 管道的全生命周期，`semantic_text` 将向量生成和检索过程完全自动化。

**全面对比**

| 维度 | semantic_text（9.x） | dense_vector（8.x/9.x） |
|------|----------------------|--------------------------|
| **向量生成** | 自动（写入时透明） | 手动（Ingest Pipeline / 应用层） |
| **查询方式** | `semantic` 查询（输入文本） | `knn` 查询（输入向量） |
| **配置复杂度** | 低（仅需推理端点） | 高（Pipeline + 映射 + 查询向量） |
| **写入延迟** | 略高（写入时推理） | 取决于 Pipeline 设计 |
| **灵活性** | 低（黑盒自动化） | 高（完全控制向量生成和查询） |
| **混合搜索** | 可与 BM25 通过 RRF 组合 | 可与 BM25 通过 RRF 组合 |
| **版本要求** | 9.0+ | 8.0+ |
| **适用场景** | 快速接入、标准语义搜索 | 定制化需求、复杂 Pipeline |

**REST API 示例**

```bash
# dense_vector 方式（8.x）
curl -X POST "localhost:9200/dense-products/_search" \
  -H "Content-Type: application/json" \
  -d '{
    "knn": {
      "field": "desc_vector",
      "query_vector": [0.12, -0.34, 0.78, ...],
      "k": 10, "num_candidates": 100
    }
  }'

# semantic_text 方式（9.x）
curl -X POST "localhost:9200/semantic-products/_search" \
  -H "Content-Type: application/json" \
  -d '{
    "query": {
      "semantic": {
        "field": "description",
        "query": "长续航蓝牙耳机"
      }
    }
  }'
```

**注意事项**

- 8.x 用户应使用 `dense_vector` + Ingest Pipeline，但可提前规划 9.x 的 `semantic_text` 迁移路径。
- `semantic_text` 底层仍使用 `dense_vector` 存储，只是自动化了 Embedding 流程。
- 如果需要在写入前对文本做预处理（如清洗、翻译），`dense_vector` 更灵活。
- 9.x 中 `dense_vector` 并未废弃，仍可用于需要完全控制向量生命周期的场景。

## Inference API

### 内置模型

**概念定义**

Elasticsearch 内置了一系列可直接部署的机器学习模型，涵盖文本 Embedding、稀疏向量编码、文本分类、NER 等任务。这些模型经过 Elastic 优化，可在本地集群中高性能运行，无需外部服务依赖。

**内置模型清单**

| 模型 ID | 任务类型 | 维度 | 语言 | 大小 |
|---------|----------|------|------|------|
| `.elser_model_2` | 稀疏向量编码 | ~30,000 | 多语言 | ~500MB |
| `.multilingual-e5-small` | 文本 Embedding | 384 | 多语言 | ~470MB |
| `.multilingual-e5-base` | 文本 Embedding | 768 | 多语言 | ~1.1GB |
| `.all-MiniLM-L6-v2` | 文本 Embedding | 384 | English | ~90MB |
| `.all-mpnet-base-v2` | 文本 Embedding | 768 | English | ~440MB |

**核心参数**

| 参数 | 含义 | 可选值 |
|------|------|--------|
| `model_id` | 模型 ID | 见上表 |
| `num_allocations` | 部署分配数 | 1 ~ N |
| `num_threads` | 每分配推理线程数 | 1 ~ N |
| `cache_size` | 推理缓存大小 | 视内存而定 |

**REST API 示例**

```bash
# 1. 下载 E5 多语言模型
curl -X PUT "localhost:9200/_ml/trained_models/.multilingual-e5-small" \
  -H "Authorization: ApiKey ${ES_API_KEY}"

# 2. 部署模型
curl -X POST "localhost:9200/_ml/trained_models/.multilingual-e5-small/deployment/_start" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "number_of_allocations": 2,
    "threads_per_allocation": 4
  }'

# 3. 创建推理端点
curl -X PUT "localhost:9200/_inference/text_embedding/e5-inference" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "service": "elasticsearch",
    "service_settings": {
      "model_id": ".multilingual-e5-small",
      "num_allocations": 2,
      "num_threads": 4
    }
  }'

# 4. 查看部署状态
curl -X GET "localhost:9200/_ml/trained_models/.multilingual-e5-small/_stats" \
  -H "Authorization: ApiKey ${ES_API_KEY}"
```

**注意事项**

- 内置模型首次下载需要外网访问，下载后缓存在集群本地。
- 模型部署需要占用 JVM 堆外内存，E5-small 约需 1GB，E5-base 约需 2.5GB。
- 同一模型可部署多个 Allocation 以提升并发能力，但会增加内存开销。
- 模型部署后可通过 `_infer` API 直接调用，无需创建推理端点（但端点方式更便于管理）。

### 第三方模型集成

**概念定义**

Elasticsearch Inference API 支持集成第三方 Embedding 服务，包括 HuggingFace、OpenAI、Cohere、Mistral 等。通过创建推理端点指向外部服务，ES 可在写入和查询时自动调用第三方 API 生成向量。

**支持的第三方服务**

| 服务 | 必填参数 | 向量维度 |
|------|----------|----------|
| `openai` | `api_key`, `model_id` | 1536 / 3072 |
| `hugging_face` | `api_key`, `url` | 取决于模型 |
| `cohere` | `api_key`, `model_id` | 1024 / 4096 |
| `mistral` | `api_key`, `model_id` | 1024 |
| `google_ai_studio` | `api_key`, `model_id` | 768 |

**核心参数**

| 参数 | 含义 | 适用服务 |
|------|------|----------|
| `api_key` | API 密钥（支持安全存储） | 全部 |
| `model_id` | 模型名称 | OpenAI / Cohere / Mistral |
| `url` | 自定义推理 URL | HuggingFace |
| `dimensions` | 输出向量维度 | OpenAI（text-embedding-3） |
| `rate_limit` | 请求速率限制 | 全部 |

**REST API 示例**

```bash
# 集成 OpenAI
curl -X PUT "localhost:9200/_inference/text_embedding/openai-emb" \

  -H "Authorization: ApiKey ${ES_API_KEY}" \

    "service": "openai",
    "service_settings": {
      "api_key": "sk-xxxxxxxxxxxxx",
      "model_id": "text-embedding-3-small",
      "dimensions": 1536
    }
  }'

# 集成 HuggingFace 推理端点
curl -X PUT "localhost:9200/_inference/text_embedding/hf-emb" \

    "service": "hugging_face",
    "service_settings": {
      "api_key": "hf_xxxxxxxxxxxxx",

# 集成 Cohere
curl -X PUT "localhost:9200/_inference/text_embedding/cohere-emb" \
  -H "Content-Type: application/json" \

    "service": "cohere",
```

**注意事项**

- API Key 建议使用 Elasticsearch 安全存储（Keystore），避免明文写入配置。
- 第三方服务调用有网络延迟，P99 延迟通常在 100~500ms，需评估对写入吞吐的影响。
- 建议配置 `rate_limit` 避免超出第三方 API 的速率限制。
- HuggingFace 推理端点支持自定义 URL，可对接自部署的 TEI（Text Embeddings Inference）服务。
- 9.x 中 `semantic_text` 字段可直接引用第三方推理端点，实现全自动向量化。

### 推理处理器

**概念定义**

推理处理器（Inference Processor）是 Elasticsearch Ingest Pipeline 中的一种处理器，用于在文档写入时自动调用推理服务（内置模型或第三方 API）生成向量、分类标签或其他推理结果。它是 8.x 中 `dense_vector` 字段自动向量化的核心组件。

**核心参数**

| 参数 | 含义 | 必填 |
|------|------|------|
| `model_id` | 推理模型 ID（trained model 或 inference endpoint） | 是 |
| `target_field` | 推理结果写入的目标字段 | 是 |
| `field_map` | 源字段到模型输入字段的映射 | 是 |
| `inference_config` | 推理配置（如 classification 的阈值） | 否 |
| `on_failure` | 失败处理策略 | 否 |

**REST API 示例**

```bash
# 创建 Ingest Pipeline（使用推理处理器）
curl -X PUT "localhost:9200/_ingest/pipeline/vector-embedding-pipeline" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "description": "自动生成文本向量",
    "processors": [
      {
        "inference": {
          "model_id": ".multilingual-e5-small",
          "target_field": "content_vector",
          "field_map": {
            "content": "text_field"
          },
          "inference_config": {
            "text_embedding": {}
          }
        }
      },
      {
        "remove": {
          "field": "content_raw",
          "ignore_missing": true
        }
      }
    ]
  }'

# 通过 Pipeline 写入文档
curl -X POST "localhost:9200/docs/_doc?pipeline=vector-embedding-pipeline" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "title": "Elasticsearch 向量搜索",
    "content": "Elasticsearch 8.x 支持基于 HNSW 的 kNN 向量检索..."
  }'

# 查看 Pipeline 执行结果（模拟测试）
curl -X POST "localhost:9200/_ingest/pipeline/vector-embedding-pipeline/_simulate" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "docs": [{
      "_source": {
        "title": "测试文档",
        "content": "Elasticsearch kNN 搜索"
      }
    }]
  }'
```

**注意事项**

- Pipeline 中的推理处理器按顺序执行，一个文档可经过多个推理处理器。
- 推理失败默认会阻塞文档写入，可通过 `on_failure` 配置跳过或写入死信索引。
- 推理处理器在协调节点上执行，高吞吐场景需确保协调节点有足够的 CPU/内存。
- 9.x 中 `semantic_text` 字段内部自动使用推理处理器，开发者无需手动配置 Pipeline。
- 对于长文本，建议在 Pipeline 中先做分块处理，再送入推理处理器。

## 向量搜索性能

### 量化

**概念定义**

向量量化是通过降低向量精度来减少内存占用和加速检索的技术。量化在索引构建时应用，将 float32 向量压缩为更低精度表示。Elasticsearch 支持标量量化（int8/int4）和二进制量化（bbq），在内存节省和召回率之间提供多级选择。

**100万条 768维向量的内存估算**

| 量化类型 | 每向量大小 | 索引内存 | 相对节省 |
|----------|-----------|----------|----------|
| 无量化（float32） | 3.07 KB | ~3.1 GB | 基准 |
| int8_hnsw | 0.77 KB | ~770 MB | 75% |
| int4_hnsw | 0.38 KB | ~385 MB | 87.5% |
| bbq | 0.096 KB | ~96 MB | 97% |

**核心参数**

| 参数 | 含义 | 值 |
|------|------|-----|
| `index_options.type` | 量化类型 | `hnsw` / `int8_hnsw` / `int4_hnsw` / `bbq` |
| `confidence_interval` | BBQ 重排序置信度 | `0.9` ~ `1.0` |

**REST API 示例**

```bash
# 量化对比测试：创建三个索引，分别使用不同量化策略
# 基准：无量化 hnsw
curl -X PUT "localhost:9200/bench-hnsw" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "mappings": {
      "properties": {
        "vec": {
          "type": "dense_vector",
          "dims": 768,
          "index_options": { "type": "hnsw", "m": 16, "ef_construction": 200 }
        }
      }
    }
  }'

# BBQ 极致量化（配合 oversampling 和 rerank）
curl -X PUT "localhost:9200/bench-bbq" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "mappings": {
      "properties": {
        "vec": {
          "type": "dense_vector",
          "dims": 768,
          "index_options": {
            "type": "bbq",
            "m": 16,
            "ef_construction": 200
          }
        }
      }
    }
  }'
```

**注意事项**

- 量化后召回率会下降，但通常可通过增大 `num_candidates` 部分补偿。
- BBQ 量化建议配合 `oversampling`（取更多候选）和 `rerank`（用原始向量重排序）使用。
- 量化类型变更需 Reindex，建议在数据导入前确定量化策略。
- 非量化 hnsw 的向量数据存储在 page cache 之外（off-heap），量化后存储方式类似。

### 索引类型选择

**概念定义**

索引类型选择是在精度、内存、延迟之间权衡的决策过程。Elasticsearch 提供 `hnsw`（全精度）、`int8_hnsw`、`int4_hnsw`、`bbq` 四种索引类型，不同场景适用不同选择。

**选择决策树**

```
数据规模 < 100万？
  ├── 是 → 精度敏感？
  │   ├── 是 → hnsw（m=16, ef_construction=200）
  │   └── 否 → int8_hnsw
  └── 否 → 数据规模 < 1000万？
      ├── 是 → 内存充足？
      │   ├── 是 → hnsw 或 int8_hnsw
      │   └── 否 → int4_hnsw
      └── 否 → 十亿级？
          ├── 是 → bbq + oversampling + rerank
          └── 否 → int4_hnsw
```

**核心参数**

| 参数 | 全精度生产 | 平衡生产 | 低内存大规模 |
|------|-----------|----------|-------------|
| `type` | `hnsw` | `int8_hnsw` | `bbq` |
| `m` | 16 ~ 32 | 16 | 16 |
| `ef_construction` | 200 ~ 500 | 100 ~ 200 | 100 ~ 200 |
| `num_candidates` | k * 10 | k * 20 | k * 30 ~ 50 |
| 推荐 `nlist`（IVF 替代） | N/A | N/A | N/A |

**REST API 示例**

```bash
# 场景一：高精度 RAG 检索（10 万文档）
curl -X PUT "localhost:9200/rag-knowledge" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "mappings": {
      "properties": {
        "chunk_vector": {
          "type": "dense_vector",
          "dims": 768,
          "index_options": {
            "type": "hnsw",
            "m": 32,
            "ef_construction": 500
          }
        }
      }
    }
  }'

# 场景二：中等规模电商搜索（500 万文档）
curl -X PUT "localhost:9200/ecommerce" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "mappings": {
      "properties": {
        "product_vector": {
          "type": "dense_vector",
          "dims": 768,
          "index_options": {
            "type": "int8_hnsw",
            "m": 16,
            "ef_construction": 200
          }
        }
      }
    }
  }'
```

**注意事项**

- 没有一种索引类型适合所有场景，应在自己的数据集上做基准测试。
- 非量化 `hnsw` 的 `m=32` 和 `ef_construction=500` 可提供接近 100% 的召回率。
- 高并发搜索场景下，`int8_hnsw` 通常是最佳性价比选择。
- 变更索引类型需要 Reindex，建议在数据量还小时进行测试和决策。

### 内存管理

**概念定义**

向量搜索的内存管理涉及 HNSW 图结构的内存占用、向量数据的存储方式以及 JVM 堆的合理配置。向量搜索是内存密集型操作，合理的配置可避免 OOM 和频繁 GC。

**内存构成**

```
向量搜索内存 = 向量数据 + HNSW 图结构 + 推理模型 + 查询临时数据

各组件占比（768 维，100 万向量，hnsw m=16）：
- 向量数据（float32）：~3.1 GB
- HNSW 图结构（连接边）：~0.8 GB
- 推理模型（E5-small）：~1 GB
- 查询临时数据：~0.2 GB
- 总计：~5.1 GB
```

**核心参数**

| 参数 | 含义 | 推荐值 |
|------|------|--------|
| `es.xpack.ml.max_machine_memory_percent` | ML 最大内存占比 | 30% |
| `es.xpack.ml.max_model_memory_limit` | 单模型最大内存 | 视模型而定 |
| `-Xmx` / `-Xms` | JVM 堆大小 | 总内存的 50%（不超过 31GB） |
| `index_options.type` | 量化类型（控制向量内存） | 视规模而定 |
| `index_options.m` | HNSW 连接数（控制图内存） | 16 |

**REST API 示例**

```bash
# 查看向量字段的内存占用
curl -X GET "localhost:9200/_stats/field_data?fields=*&filter_path=indices.*.fields" \
  -H "Authorization: ApiKey ${ES_API_KEY}"

# 查看集群节点内存使用
curl -X GET "localhost:9200/_nodes/stats/os,process,jvm?filter_path=nodes.*.name,nodes.*.os.mem,nodes.*.process.mem,nodes.*.jvm.mem" \
  -H "Authorization: ApiKey ${ES_API_KEY}"

# 查看 ML 模型内存使用
curl -X GET "localhost:9200/_ml/trained_models/_stats?filter_path=trained_model_stats.*.model_id,trained_model_stats.*.deployment_stats.nodes.*.routing_state.*.memory_usage" \

# 动态调整 ML 模型内存限制
curl -X POST "localhost:9200/_ml/trained_models/.multilingual-e5-small/deployment/_update" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "number_of_allocations": 1
  }'
```

**注意事项**

- 向量数据存储在堆外内存（off-heap），不受 JVM `-Xmx` 限制，但受操作系统限制。
- 每个 Segment 独立维护 HNSW 图，Force Merge 可减少 Segment 数量从而降低总内存。
- 推理模型的内存占用在 `elasticsearch.yml` 中通过 `xpack.ml` 相关参数控制。
- 建议预留 30% 系统内存给 OS page cache 和其他系统进程。
- 9.x 中 `semantic_text` 自动管理向量，但内存占用原理与 `dense_vector` 相同。

### 批量索引优化

**概念定义**

批量索引优化是在大量向量数据写入 Elasticsearch 时，通过调整批量大小、并发度、刷新策略等参数，最大化写入吞吐和最小化索引构建时间的技术手段。

**写入流程**

```
应用层 → Bulk API → 协调节点 → 主分片 → 副本分片
                                    ↓
                            HNSW 图增量构建
```

**核心参数**

| 参数 | 含义 | 推荐值 | 影响 |
|------|------|--------|------|
| `bulk_size` | 每批文档数 | 500 ~ 2000 | 吞吐 vs 内存 |
| `bulk_bytes` | 每批字节数 | 5MB ~ 15MB | 吞吐 vs 延迟 |
| `concurrent_requests` | 并发批量请求数 | CPU 核心数 * 2 | 吞吐 vs CPU |
| `refresh_interval` | 刷新间隔 | `-1`（导入时）/ `30s`（正常） | 写入性能 vs 可见性 |
| `number_of_replicas` | 副本数 | `0`（导入时）/ `1`（正常） | 写入性能 vs 可靠性 |
| `translog.durability` | Translog 持久化策略 | `async`（导入时） | 写入性能 vs 安全性 |

**REST API 示例**

```bash
# 导入前：关闭刷新和副本
curl -X PUT "localhost:9200/products/_settings" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "index": {
      "refresh_interval": "-1",
      "number_of_replicas": 0,
      "translog": {
        "durability": "async"
      }
    }
  }'

# 批量写入（使用 Bulk API）
curl -X POST "localhost:9200/_bulk" \
  -H "Content-Type: application/x-ndjson" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  --data-binary @bulk_data.json

# 写入完成后：恢复设置 + Force Merge
curl -X PUT "localhost:9200/products/_settings" \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey ${ES_API_KEY}" \
  -d '{
    "index": {
      "refresh_interval": "30s",
      "number_of_replicas": 1,
      "translog": {
        "durability": "request"
      }
    }
  }'

# Force Merge 到 1 个 Segment（减少 HNSW 图重建开销）
curl -X POST "localhost:9200/products/_forcemerge?max_num_segments=1" \
  -H "Authorization: ApiKey ${ES_API_KEY}"
```

**注意事项**

- 导入时关闭 `refresh_interval` 可提升 2~3 倍写入性能，但数据在导入期间不可搜索。
- 导入时设置 `number_of_replicas=0`，导入完成后改为 1 并等待副本同步。
- Force Merge 到 1 个 Segment 可显著减少 HNSW 图的内存开销，但会消耗大量 CPU 和 I/O。
- 向量数据的 Bulk 写入建议每批不超过 1000 条，过大的批次会导致协调节点内存压力。
- 对于十亿级向量导入，建议使用 `_reindex` 或分批导入策略，避免单次 Force Merge 超时。
