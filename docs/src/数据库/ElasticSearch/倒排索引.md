## 倒排索引数据结构

### Term Dictionary

**概念定义**

Term Dictionary（词项词典）是倒排索引的"目录"，它存储了文档集合中所有**去重后的词项（Term）**及其到 Posting List 的映射指针。每个 Term 在 Term Dictionary 中只出现一次，按字典序（UTF-8 字节序）排序存储。

**核心原理说明**

1. **排序存储**：Term Dictionary 中的 Term 按字典序严格排序，这使得二分查找成为可能。对于规模在数百 MB 到数 GB 的 Term Dictionary，Elasticsearch 不会直接对整个词典做内存二分查找，而是借助 Term Index（FST）做前缀加速。

2. **Term 粒度**：在 Elasticsearch 中，一个 Term 由 `field_name` + `token` 组成。例如 `"title:elasticsearch"` 就是一个 Term。同一个 token 出现在不同字段中，会形成不同的 Term 条目。

3. **存储映射**：每个 Term 条目最终指向一个 Posting List 的起始位置（文件偏移量），包含该 Term 出现在哪些文档、出现频率、位置偏移等信息。

4. **压缩优化**：Term Dictionary 在磁盘上采用前缀压缩（Prefix Compression / Block Compression），将相邻 Term 的公共前缀去重，大幅减少磁盘占用。

**注意事项**

- Term Dictionary 的大小与字段基数（Cardinality）正相关，`keyword` 类型字段若基数过高（如 UUID），会显著增大词典体积。
- 分词后的 `text` 字段进入 Term Dictionary，未分词的 `keyword` 字段原样进入。
- 在 8.x 中，`wildcard` 字段类型也有独立的 Term Dictionary，但使用了不同的内部结构（n-gram 索引）。

---

### Term Index（FST）

**概念定义**

Term Index（词项索引）是 Term Dictionary 的"加速索引"，其核心实现是 **FST（Finite State Transducer，有限状态转换器）**。它本质是一个前缀树（Trie）的压缩有向图，将 Term Dictionary 中所有 Term 的前缀信息编码为一个**最小化的确定性有限状态自动机**，并支持在图上快速定位 Term 在磁盘上的大致位置（Block 范围）。

**核心原理说明**

1. **前缀定位**：Term Index 不存储完整的 Term，而是将 Term 的公共前缀节点合并为共享边。查询时从根节点出发，沿字符边行走，最终到达的节点携带一个 Block 指针，指向 Term Dictionary 中对应前缀所在的 Block。

2. **两级查找**：查询流程为 `Term Index（FST）→ 定位 Block → Block 内二分查找 → 找到 Term → 获取 Posting List 指针`。Term Index 将 O(log N) 的全局二分优化为 O(len(term)) 的前缀树遍历 + O(log block_size) 的小范围二分。

3. **内存常驻**：FST 结构极为紧凑，通常可以完全加载到 JVM 堆内存中。即使 Term Dictionary 有数百万个 Term，FST 的堆内存占用也通常在几十 MB 量级。

4. **共享前缀/后缀**：FST 同时支持前缀共享和后缀共享（通过最小化 DFA），这种双向压缩使得存储效率极高，比普通的 Trie 小 5~10 倍。

**注意事项**

- FST 构建后不可变（immutable），一旦 Segment 写入磁盘，其 FST 结构就固定了。这也是为什么 Segment 是只读的。
- 前缀查询（`prefix query`）在 FST 中非常高效，因为只需沿前缀边走到对应节点，然后遍历该节点下的所有叶子。
- 通配符查询（`wildcard`）和正则查询（`regexp`）在 FST 上的效率取决于模式的前缀锚定程度，越多前缀锚定越快。
- 8.x 中 FST 的实现位于 Lucene 的 `org.apache.lucene.util.fst` 包。

---

### Posting List

**概念定义**

Posting List（倒排列表）是倒排索引的"数据体"，记录了**某个 Term 出现在哪些文档中，以及在每个文档中的出现频率、位置和偏移量**。它是倒排查询最终要读取和计算的数据结构。

**核心原理说明**

1. **结构组成**：对于每个 Term，Posting List 包含以下信息：
   - **Doc ID 列表**：包含该 Term 的所有文档 ID（按升序排列）。
   - **Term Frequency（TF）**：每个文档中该 Term 的出现次数。
   - **Position 列表**：该 Term 在文档中的每个出现位置（用于短语查询 / 邻近查询）。
   - **Offset 列表**：每个出现的起始和结束字符偏移（用于高亮）。
   - **Payload（可选）**：每个出现的自定义附加数据。

2. **压缩编码**：Posting List 使用多种压缩策略：
   - **Delta 编码**：Doc ID 存储差值而非绝对值（如 `[100, 105, 110]` 存为 `[100, 5, 5]`），大幅减少数值范围。
   - **Frame of Reference（FOR）**：将 Delta 值分组，每组用最小的 bit 宽度表示。
   - **PForDelta / SIMD**：Lucene 8.x 起使用 `Lucene90PostingsFormat`，采用更高效的块压缩编码。

3. **SkipList 加速**：Posting List 内部嵌入了 SkipList 跳表，用于在合并多个 Posting List 时快速跳过不需要的 Doc ID 区间。

4. **按需加载**：Es 的 Posting List 支持按需加载，基本的布尔查询只需 Doc ID 和 TF，而短语查询则需要 Position 数据，高亮查询才需要 Offset 数据。

**注意事项**

- Posting List 的磁盘体积通常远大于 Term Dictionary，尤其是高频词（如 "the", "a"）的 Posting List 可能包含数百万个 Doc ID。
- 删除文档不会立即从 Posting List 中移除，而是通过 `.del` 文件标记删除，在段合并时真正清理。
- 8.x 中的 `index_options` 映射参数可以控制 Posting List 存储哪些信息（`docs` / `freqs` / `positions` / `offsets`），减少不必要的数据存储。

### 倒排索引构建过程

**概念定义**

倒排索引的构建过程是指将原始文档经过**分词、排序、去重、归并**等一系列步骤，最终生成 Term Dictionary、Term Index、Posting List 等核心数据结构的过程。

**核心原理说明**

1. **文档分析（Analysis）**：原始文档中的每个字段经过 Analyzer 处理，包括 Character Filter、Tokenizer、Token Filter 三个阶段，最终生成 token 流。

2. **倒排生成（Inversion）**：对每个 token 生成 `(Term, DocID, Position, Offset)` 元组，按 Term 分组，同一 Term 下的多个文档记录按 Doc ID 排序，形成 Posting。

3. **内存缓冲（Buffer）**：构建过程在内存中逐步进行。Lucene 使用 `DocumentsWriterPerThread` 为每个线程分配独立的内存 buffer，避免锁竞争。

4. **排序归并（Sort & Merge）**：当内存 buffer 达到阈值（`indexing_buffer_size`，默认 10% 堆内存）时，将 buffer 中的 Term 排序后刷入一个临时的 Segment。多个 Segment 在后台通过段合并（Merge）归并，最终生成完整的倒排索引。

5. **两阶段构建**：
   - **Phase 1**：内存中构建（`InMemoryPostingsFormat`），生成 FST 和 Posting List 的中间表示。
   - **Phase 2**：刷盘时将内存中的中间表示序列化为最终的磁盘格式（`Lucene90PostingsFormat` 等）。

**注意事项**

- 刷盘频率受 `refresh_interval`（默认 1s）控制，高写入场景可适当调大以减少 IO。
- 每个 Segment 都有独立的倒排索引，查询时需要跨所有 Segment 读取并合并结果。
- 构建过程是 CPU 密集型操作，尤其是在分词和压缩编码阶段。8.x 中引入了更高效的 SIMD 指令加速压缩。

## Lucene 核心原理

### Segment

**概念定义**

Segment（段）是 Lucene 索引的**最小不可变存储单元**，每个 Segment 内部包含一套完整的倒排索引数据结构（Term Dictionary、Term Index、Posting List、DocValues、Stored Fields 等）。Elasticsearch 的 Shard 由一个或多个 Segment 组成。

**核心原理说明**

1. **不可变性（Immutability）**：Segment 一旦写入磁盘，就不再修改。文档的更新和删除通过追加新 Segment + 标记删除来实现，而非原地修改。

2. **文件组成**：每个 Segment 包含以下核心文件（以 8.x 为例）：
   - `.tim`：Term Dictionary（词项词典）
   - `.tip`：Term Index（FST 索引）
   - `.doc`：Posting List（DocID + TF）
   - `.pos`：Position 信息
   - `.pay`：Payload 和 Offset 信息
   - `.dvd/.dvm`：DocValues 数据与元数据
   - `.fdt/.fdx/.fdm`：Stored Fields（原始 `_source`）
   - `.nvd/.nvm`：Norms（字段长度归一化值）
   - `.dvd/.dvm`：DocValues
   - `.kdd/.kdi/.kdm`：BKD Tree（数值/地理/日期范围索引）
   - `.del`：已删除文档位图
   - `.si`：Segment 元数据（SegmentInfo）

3. **提交点（Commit Point）**：每个 Shard 维护一个 `segments_N` 文件，记录当前所有活跃 Segment 的列表。当 `flush` 发生时，新 Segment 被添加到提交点；当 `merge` 完成后，旧 Segment 从提交点移除。

4. **并发控制**：多个 Segment 的不可变性带来了天然的并发优势——读操作无需加锁，写操作只需追加新 Segment。

**注意事项**

- Segment 数量过多会严重影响查询性能（每个 Segment 都需要被搜索），需通过段合并策略控制。
- 每个 Segment 内部 Doc ID 从 0 开始递增，但全局 Doc ID 是 Segment 内部 Doc ID + Segment 偏移量。
- 8.x 中单个 Segment 的默认最大文档数为 `2^31 - 128`（约 21.4 亿），由 LUCENE-8663 引入。
- 通过 `_cat/segments` API 可以查看当前索引的 Segment 详情。

---

### SkipList 跳表

**概念定义**

SkipList（跳表）是嵌入在 Posting List 内部的一种**多级索引结构**，用于加速多 Term 查询时的 Posting List 合并（交集/并集）操作。它允许查询引擎在合并 Posting List 时跳过大量不需要比较的 Doc ID。

**核心原理说明**

1. **分层结构**：Lucene 中的 SkipList 将 Posting List 按固定间隔（如每 128 个 Doc ID）划分为多个 Block，每个 Block 记录其起始 Doc ID 和对应的文件偏移量。上层 Skip Level 再以更大的间隔（如每 8 个 Block）建立更高层级的跳表。

2. **合并加速**：假设查询 `"termA AND termB"`，termA 的 Posting List 有 100 万个 Doc ID，termB 只有 100 个。通过 SkipList，可以在 termA 的 Posting List 上快速跳过中间大量不匹配的 Doc ID，直接定位到与 termB 的 Doc ID 接近的 Block。

3. **实现细节**：
   - SkipList 的层级数由 Posting List 大小决定，越大的 Posting List 有越多的 Skip Level。
   - 每个 Skip Level 存储 `(docID, filePointer)` 二元组。
   - 跳跃间隔（skipInterval）在 Lucene 中默认是 128。

4. **时间复杂度**：在没有 SkipList 时，合并两个 Posting List 的时间复杂度是 O(N+M)。使用 SkipList 后，对于 `termA AND termB`（M << N），复杂度可降至 O(M * log N)。

**注意事项**

- SkipList 仅对合并操作有加速效果，对单 Term 查询（只需遍历 Posting List）无帮助。
- SkipList 占用额外磁盘空间，但通常不到 Posting List 总大小的 5%。
- 8.x 中 SkipList 的实现在 `org.apache.lucene.codecs.lucene90` 包下的 `Lucene90PostingsWriter` 中。
- 高频词（如 "the"）的 Posting List 极大，SkipList 的加速效果也最明显。

---

### FST（有限状态转换器）

**概念定义**

FST（Finite State Transducer，有限状态转换器）是 **Term Index 的核心实现**，它是一种特殊的有向无环图（DAG），每个节点代表一个状态，每条边带有一个输入字符标签和一个输出值（在本场景中输出值为 Block 索引或文件偏移量）。FST 同时是一个最小化的确定型有限状态自动机（DFA），能够以极高的压缩率存储所有 Term 的前缀信息。

**核心原理说明**

1. **与 Trie 的区别**：普通 Trie 树只存储 key，而 FST（Transducer）同时存储 key 和 value。FST 是 Trie 的"双向压缩"版本——既共享前缀又共享后缀。

2. **构建算法**：FST 使用增量构建算法，将 Term 按字典序逐个插入。新 Term 与之前 Term 的公共前缀复用已有节点，不匹配的部分创建新节点。当一个节点的所有出边都确定后，该节点被"冻结"（frozen），成为最小化 FST 的一部分。

3. **查找过程**：查询时从根节点出发，沿输入字符的边行走，每一步累加边上的输出值。到达目标节点后，节点中存储的输出值即为最终结果。时间复杂度为 O(len(term))。

4. **Lucene 中的实现**：
   - `org.apache.lucene.util.fst.FST`：核心 FST 实现，支持 `Builder` 模式构建。
   - `org.apache.lucene.util.fst.BytesStore`：FST 的字节级存储，支持内存映射。
   - 支持 `FST.INPUT_TYPE.BYTE1`（单字节）、`BYTE2`（双字节）、`BYTE4`（四字节）三种弧标签类型。

5. **压缩率**：FST 的典型压缩率是 10:1 到 20:1（相对于原始 Term 集），主要是因为前缀/后缀共享和节点最小化。

**注意事项**

- FST 是单向的（只能从根到叶），不支持反向遍历。这意味着后缀查询（`*suffix`）无法利用 FST 加速。
- FST 的构建需要按字典序插入 Term，乱序插入会导致构建失败或产生非最小化的结果。
- 在 8.x 中，FST 默认使用 `BYTE2` 输入类型，支持最多 65535 种不同的出边标签，满足大多数场景。
- 非常大的 FST（如包含数千万 Term）可能导致 JVM OOM，因为 FST 常驻堆内存。此时需要考虑字段类型优化或使用 `wildcard` 字段替代。

### Roaring Bitmap

**概念定义**

Roaring Bitmap 是一种**高效的压缩位图数据结构**，用于在 Lucene/Elasticsearch 中存储和操作文档 ID 集合。它广泛应用于过滤器缓存（Filter Cache）、已删除文档标记、聚合结果集等场景，能够在保持快速位运算（AND/OR/NOT）的同时大幅压缩内存占用。

**核心原理说明**

1. **分层存储策略**：Roaring Bitmap 将 32 位整数空间（0 ~ 2^32-1）按高 16 位划分为 65536 个"桶"（chunk），每个桶内的 Doc ID 使用低 16 位表示。根据桶内数据密度，采用不同的存储方式：
   - **稀疏桶（Sparse）**：当桶内元素个数 <= 4096 时，使用有序 `short[]` 数组存储（ArrayContainer）。
   - **稠密桶（Dense）**：当桶内元素个数 > 4096 时，使用 65536 位的位图（BitmapContainer，即 8KB）。
   - **连续桶（Run）**：当桶内元素是连续区间时，使用 RunContainer（Run-Length Encoding），仅存储 `[start, length]` 对。

2. **位运算优化**：两个 Roaring Bitmap 的 AND/OR/NOT 操作在桶级别进行，根据两个桶的 Container 类型选择最优算法：
   - BitmapContainer AND BitmapContainer → 使用 CPU 的 SIMD 指令做位运算（极快）。
   - ArrayContainer AND ArrayContainer → 双指针归并。
   - 混合类型 → 动态选择转换策略。

3. **Lucene 中的使用**：
   - `org.apache.lucene.util.RoaringDocIdSet`：Lucene 的 Roaring Bitmap 适配器。
   - 过滤器缓存（`query_cache`）：缓存频繁使用的 Filter 查询结果。
   - `.del` 文件：标记已删除的文档 ID。
   - 聚合（Aggregation）中的文档集合。

4. **内存对比**：对于 100 万个 Doc ID：
   - 普通 `int[]`：4 MB
   - 普通位图：125 KB（但需要连续 ID 空间）
   - Roaring Bitmap：根据分布，通常 10-200 KB

**注意事项**

- Roaring Bitmap 仅适用于非负整数集合，Doc ID 天然满足这个条件。
- 在 Elasticsearch 8.x 中，`terms` 聚合和 `filter` 查询的结果集默认使用 Roaring Bitmap 缓存。
- 密集的 Doc ID 范围（如全量匹配）下 Roaring Bitmap 使用 BitmapContainer，稀疏的（如低频词）使用 ArrayContainer，二者之间自动切换，无需手动干预。
- 不要将 Roaring Bitmap 与 DocValues 混淆——前者用于 Doc ID 集合的压缩与位运算，后者用于字段值的列式存储与快速访问。

---

### DocValues（列式存储）

**概念定义**

DocValues 是 Lucene 的**列式存储（Columnar Storage）**机制，它在文档写入时为每个字段构建**文档 ID 到字段值**的正向映射，使得按 Doc ID 读取字段值的操作达到 O(1) 时间复杂度。它是排序、聚合、函数评分（Function Score）、父子文档 Join 等操作的基础设施。

**核心原理说明**

1. **与倒排索引的互补**：倒排索引是"Term → Doc ID"的映射（适合搜索），DocValues 是"Doc ID → Value"的映射（适合聚合/排序）。两者互补，覆盖了搜索和分析的所有场景。

2. **存储结构**：DocValues 按字段独立存储，每个字段的 DocValues 数据按 Doc ID 顺序排列，类似于数据库中的列式存储。主要编码方式包括：
   - **Delta 编码**：对于数值类型，存储相邻值的差值。
   - **GCD 编码**：对于数值类型，找出所有值的最大公约数，存储 `value / gcd`。
   - **Table 编码**：对于低基数离散值，使用字典表 + 索引。
   - **Prefix 编码**：对于字符串类型，使用前缀压缩（类似 Term Dictionary）。
   - **Sorted Set**：对于多值 keyword 字段，使用 DocValues 的 Sorted Set 变体。

3. **文件结构**：
   - `.dvd`：DocValues 数据文件（Data file）
   - `.dvm`：DocValues 元数据文件（Metadata file），包含每个字段的编码类型、偏移量、DocValues 类型等。

4. **加载策略**：DocValues 的数据可以按需加载到堆外内存（off-heap），通过 `mmap` 映射磁盘文件，避免 GC 压力。8.x 中默认使用 `MMapDirectory` 加载 DocValues。

5. **DocValues 类型**：
   - `NumericDocValues`：数值类型（long, int, double, float, date, boolean）
   - `SortedNumericDocValues`：多值数值类型
   - `BinaryDocValues`：二进制类型（包括 keyword 的序列化形式）
   - `SortedDocValues`：排序后的字符串类型（keyword，ordinal 编码）
   - `SortedSetDocValues`：多值排序字符串类型

**注意事项**

- DocValues 默认对所有非 `text` 且非 `annotated_text` 的字段启用。`text` 字段的分析结果不建立 DocValues（因为 `fielddata` 默认禁用，8.x 中已彻底移除 `fielddata` 对 text 字段的支持）。
- DocValues 是**列式且稠密**的——即使某个文档的某字段为空，也需要在 DocValues 中占用一个槽位（值为 0 或空标记）。
- 在 8.x 中，`keyword` 字段的 DocValues 采用 `SortedDocValues`，通过 ordinal 映射实现，查询时需要进行 `ord → value` 的转换。
- 列式存储使得聚合操作可以顺序扫描磁盘，效率远高于逐文档读取 `_source` 再解析。
- 写入会同时构建倒排索引和 DocValues，因此启用 DocValues 会增加索引时间和磁盘空间。

## 相关性评分

### TF-IDF 原理

**概念定义**

TF-IDF（Term Frequency - Inverse Document Frequency）是信息检索领域的经典相关性评分算法，它基于两个核心假设：**一个词在文档中出现次数越多，文档与该词越相关（TF）**；**一个词在整个文档集合中出现次数越少，该词越具有区分度（IDF）**。

**核心原理说明**

1. **TF（词频）**：衡量一个 Term 在单个文档中的重要程度。
   ```
   TF(t, d) = sqrt(freq(t, d))
   ```
   Lucene 使用平方根抑制高频词的影响，避免出现 100 次比出现 10 次相关性高 10 倍的情况。

2. **IDF（逆文档频率）**：衡量一个 Term 在整个文档集合中的稀缺程度。
   ```
   IDF(t) = 1 + log((docCount + 1) / (docFreq(t) + 1))
   ```
   出现在越多文档中的词，IDF 值越低（如 "的"、"是" 等停用词的 IDF 接近 0）。

3. **Field-Length Norm**：字段长度归一化，短文档中词的权重更高。
   ```
   norm(d) = 1 / sqrt(numTerms(field))
   ```

4. **最终评分公式**：
   ```
   score(q, d) = coord(q, d) * queryNorm(q) * Σ (TF(t, d) * IDF(t)^2 * boost(t) * norm(t, d))
   ```
   其中 `coord` 是协调因子（匹配的查询词越多分数越高），`queryNorm` 是查询归一化因子。

**注意事项**

- TF-IDF 在 Elasticsearch 5.x 之前是默认评分算法，5.x 起默认改为 BM25。8.x 中 TF-IDF 仅作为 `classic` 相似度保留，不再推荐使用。
- TF-IDF 不惩罚长文档，对字段长度不敏感（只有简单的 `norm` 归一化），这在某些场景下会偏向长文档。
- 可以通过 `similarity` 映射配置指定字段使用 TF-IDF：`"similarity": { "my_similarity": { "type": "classic" } }`。

---

### BM25 算法（8.x 默认）

**概念定义**

BM25（Best Matching 25）是 Elasticsearch 8.x 的**默认相关性评分算法**，它是 TF-IDF 的概率模型改进版，引入了**词频饱和度（TF Saturation）**和**字段长度归一化（Field Length Normalization）**两个关键改进，使得评分更加合理。

**核心原理说明**

1. **BM25 公式**：
   ```
   score(q, d) = Σ IDF(t) * (TF(t, d) * (k1 + 1)) / (TF(t, d) + k1 * (1 - b + b * (|d| / avgdl)))
   ```
   其中：
   - `IDF(t) = log(1 + (docCount - docFreq(t) + 0.5) / (docFreq(t) + 0.5))`
   - `|d|`：文档字段长度
   - `avgdl`：所有文档的平均字段长度
   - `k1`：词频饱和度控制参数（默认 1.2）
   - `b`：长度归一化控制参数（默认 0.75）

2. **TF 饱和度**：通过 `k1` 参数控制。当 TF 增大时，BM25 的评分增量递减（非线性饱和），避免了 TF-IDF 中高频词对评分的过度影响。

3. **字段长度归一化**：通过 `b` 参数控制。`b=0` 时不考虑字段长度；`b=1` 时完全按字段长度惩罚；默认 `b=0.75` 是折中值。这使得短文档中出现的匹配词比长文档中更"值钱"。

4. **与 TF-IDF 的关键差异**：
   - BM25 的 TF 有上限（饱和效应），TF-IDF 的 TF 无上限。
   - BM25 的长度归一化是可调的（`b` 参数），TF-IDF 是固定的平方根归一化。
   - BM25 在长文档和短文档混合的场景下表现更优。

**注意事项**

- 8.x 中 BM25 是默认相似度，无需显式配置。如需自定义参数，可在索引映射中指定：
  ```json
  "similarity": {
    "my_bm25": {
      "type": "BM25",
      "k1": 1.2,
      "b": 0.75
    }
  }
  ```
- `k1` 和 `b` 的调整需要在索引创建时通过 `similarity` 配置，已创建的索引不能修改。
- 对于 `boolean` 字段、`keyword` 字段（未分词的精确匹配），`TF` 始终为 0 或 1，BM25 退化为纯 IDF 评分。
- 8.x 支持 `scripted similarity`，允许通过 Painless 脚本自定义评分逻辑。

### Explain API

**概念定义**

Explain API 是 Elasticsearch 提供的**评分透明化工具**，它能够详细展示某个文档对某个查询的**评分计算过程**，包括每个查询子句的分数、TF、IDF、字段长度归一化值等细节，是调试相关性问题的核心手段。

**核心原理说明**

1. **API 形式**：
   ```
   GET /my-index/_explain/{doc_id}
   {
     "query": { "match": { "title": "elasticsearch" } }
   }
   ```

2. **输出结构**：
   ```json
   {
     "_index": "my-index",
     "_id": "1",
     "matched": true,
     "explanation": {
       "value": 1.3862944,
       "description": "weight(title:elasticsearch in 0) [PerFieldSimilarity], result of:",
       "details": [
         {
           "value": 1.3862944,
           "description": "score(freq=3.0), computed as boost * idf * tf from:",
           "details": [
             { "value": 2.2, "description": "boost" },
             { "value": 0.6931472, "description": "idf, computed as log(1 + (N - n + 0.5) / (n + 0.5)) from: ..." },
             { "value": 0.90909094, "description": "tf, computed as freq / (freq + k1 * (1 - b + b * dl / avgdl)) from: ..." }
           ]
         }
       ]
     }
   }
   ```

3. **score 命令**：在 `_search` 请求中添加 `"explain": true` 可以对所有命中文档返回评分详情，但会显著增加响应体积和计算开销，仅在调试时使用。

4. **调试价值**：通过 Explain API 可以直观地发现：
   - 哪个查询子句贡献了最多的分数。
   - 字段长度归一化对评分的影响程度。
   - boost 权重是否生效。
   - 同义词/分词对评分的影响。

**注意事项**

- Explain API 是**诊断工具**而非**生产工具**，每个请求只对单个文档返回结果，不应在生产环境大量使用。
- Explain 输出中的 `description` 是 Lucene 内部的评分描述，格式可能因版本而变化，但核心数值（`value`）是准确的。
- 8.x 中 Explain API 的输出比 7.x 更详细，尤其是在 `bool` 查询和 `function_score` 查询中。
- 如果文档未被匹配，Explain API 会返回 `"matched": false` 并尝试解释为什么没有匹配（如 Term 不在文档中）。

### Boosting（权重提升）

**概念定义**

Boosting（权重提升）是指在查询时**人为调整某些查询子句或字段的权重**，使得匹配特定条件的文档获得更高的相关性评分。它是搜索结果调优（precision/recall 权衡）的常用手段。

**核心原理说明**

1. **查询时 Boost**：在查询 DSL 中通过 `boost` 参数对子查询设置权重。
   ```json
   {
     "bool": {
       "should": [
         { "match": { "title": { "query": "elasticsearch", "boost": 2.0 } } },
         { "match": { "content": { "query": "elasticsearch", "boost": 1.0 } } }
       ]
     }
   }
   ```
   上述查询中 `title` 字段匹配的文档得分权重是 `content` 字段的 2 倍。

2. **索引时 Boost**（已废弃）：Elasticsearch 5.0 起，索引时文档级 Boost 已被移除。在 8.x 中，文档级权重应通过 `function_score` 查询中的 `field_value_factor` 或 `script_score` 实现。

3. **Boost 的作用机制**：Boost 值在评分计算中作为乘法因子作用于查询子句的评分。对于 BM25 评分，Boost 乘在 `IDF * TF` 的结果上。

4. **Boost 归一化**：在 `bool` 查询中，多个 `should` 子句的总分是所有匹配子句的分数之和，每个子句的 Boost 直接影响其贡献比例。

5. **Negative Boost**：Boost 值可以小于 1（但不为负），用于降低某些子句的权重。配合 `boosting` 查询，还可以对匹配某些条件的文档得分做惩罚（negative_boost）。

**注意事项**

- Boost 值不是绝对的，而是相对的——在同一个查询中，Boost 为 2.0 的子句比 Boost 为 1.0 的子句权重更高，但两个不同查询之间的 Boost 值不可比较。
- 过度使用 Boost 可能导致评分语义混乱，建议先通过 Explain API 验证效果。
- 8.x 中 `function_score` 查询提供了更灵活的 Boost 机制，包括 `weight`（静态权重）、`field_value_factor`（基于字段值）、`random_score`（随机评分）和 `script_score`（自定义脚本）。
- `index-time boosting` 在生产环境中会导致索引膨胀，8.x 中已完全移除，请勿尝试使用。

## 写入与读取流程

### 写入流程（内存 buffer → segment → 磁盘）

**概念定义**

写入流程是指文档从 Elasticsearch 的 REST API 接收后，经过**验证、路由、分析、缓冲、刷新、刷盘、提交**等一系列步骤，最终持久化到磁盘 Segment 的完整过程。

**核心原理说明**

1. **协调节点路由**：写入请求首先到达协调节点（Coordinating Node），根据 `_routing`（默认 `_id`）计算 `shard = hash(_routing) % num_primary_shards`，将请求转发到对应的主分片所在的节点。

2. **主分片写入（Primary Shard）**：
   - **Step 1 - 文档验证**：校验 Mapping 结构，类型转换，拒绝不合法字段。
   - **Step 2 - 写入 Translog**：将原始操作记录写入 Translog（Write-Ahead Log），保证数据不丢失。Translog 每 5 秒或每次请求后 fsync 到磁盘（由 `index.translog.durability` 控制）。
   - **Step 3 - 写入内存 Buffer**：文档进入内存中的 `Indexing Buffer`，同时更新内存中的倒排索引和 DocValues。
   - **Step 4 - Refresh**：每 `refresh_interval`（默认 1s），内存 buffer 中的文档被写入一个新的 Segment 并打开，使其对搜索可见。**Refresh 不触发 fsync**，Segment 仍在 OS Cache 中。
   - **Step 5 - Flush**：当 Translog 达到阈值（默认 512MB）或超过 30 分钟，执行 `flush` 操作：
     - 执行 Refresh。
     - 调用 `fsync` 将所有 Segment 文件刷入磁盘。
     - 生成新的 `Commit Point`。
     - 清空 Translog。

3. **副本分片写入（Replica Shard）**：主分片写入完成后，将操作转发到所有副本分片。副本分片执行相同的写入流程。当至少 `wait_for_active_shards` 个副本确认后，写入被认为成功。

4. **文档可见性**：写入成功（HTTP 200）后，文档在 Translog 中已持久化，但需要等到下一次 Refresh（默认 1s）后才能被搜索到。可以通过 `refresh=wait_for` 参数强制同步等待 Refresh。

**注意事项**

- 内存 buffer 的大小由 `indices.memory.index_buffer_size` 控制，默认 10% 堆内存，所有 Shard 共享。
- Translog 有截断机制：Flush 完成后清空 Translog，避免 Translog 无限增长。
- 8.x 中的 Translog 默认使用 `NIOFSDirectory`，支持 `async` 和 `request`（同步）两种持久化策略。
- 高吞吐写入场景下，增大 `refresh_interval`（如 30s 或 60s）可显著减少 Segment 数量，降低 IO 开销。
- 写入流程中，分词（Analysis）是 CPU 最密集的步骤，复杂的 Analyzer（如 IK 分词器）会显著影响写入吞吐。

---

### 读取流程（协调节点路由 → 分片查询 → 合并排序）

**概念定义**

读取流程是指查询请求从 Elasticsearch 的 REST API 接收后，经过**解析、路由、分片分发、并行查询、结果合并、排序、高亮**等一系列步骤，最终返回排序后的文档列表的完整过程。

**核心原理说明**

1. **Query Phase（查询阶段）**：
   - **Step 1 - 协调节点解析**：协调节点接收查询请求，解析 DSL，确定目标索引和分片。
   - **Step 2 - 分片分发**：将查询请求广播到所有相关分片（主分片或副本分片，优先选择负载较低的副本）。
   - **Step 3 - 分片本地查询**：每个分片独立执行查询：
     - 遍历所有 Segment 的 FST，查找匹配的 Term。
     - 读取 Posting List，合并（AND/OR）得到候选 Doc ID 集合。
     - 对候选 Doc ID 计算 BM25 评分。
     - 排序并截取 `from + size` 条结果。
     - 返回结果给协调节点（包含 Doc ID + Score + Sort Values）。
   - **Step 4 - 协调节点合并**：协调节点将所有分片的结果合并，重新排序，截取最终的 `from` 到 `from + size` 条。

2. **Fetch Phase（获取阶段）**：
   - 协调节点根据 Query Phase 得到的 Top N 文档 ID，向对应分片发起 Fetch 请求。
   - 分片从 Stored Fields（`_source`）中读取文档的完整内容。
   - 如果请求中包含高亮（Highlight），分片在此时根据 Offset 信息生成高亮片段。
   - 返回完整文档给协调节点。

3. **两阶段设计的原因**：
   - 如果 Query Phase 就返回完整文档，当分片数量多时，协调节点需要传输和处理大量数据。
   - 分离 Query 和 Fetch 后，Query Phase 只传输 Doc ID 和 Score，数据量极小；Fetch Phase 只传输最终需要显示的文档。

4. **分片选择策略**（8.x 优化）：
   - 优先选择副本分片以减轻主分片压力。
   - 使用 Adaptive Replica Selection（ARS）算法，根据请求排队时间、服务时间等指标动态选择最快的副本。

**注意事项**

- 深分页（Deep Pagination）问题：`from` 越大，每个分片需要排序和传输的文档越多。超过 10000 条建议使用 `search_after` 或 `scroll` API。
- `track_total_hits` 默认在 8.x 中为 `10000`，超过该阈值不再精确计数，以节省计算资源。
- 协调节点合并阶段在内存中完成，如果分片数过多且 `size` 很大，可能导致协调节点 OOM。
- 8.x 中引入了 `preference` 参数，可以控制查询路由到特定分片（如 `_local`、`_shards`、自定义字符串），用于调试和缓存利用。

---

### 段合并（Segment Merge）

**概念定义**

段合并（Segment Merge）是 Lucene 的后台**索引优化过程**，它将多个小 Segment 合并为一个大 Segment，在此过程中**真正删除被标记为删除的文档、合并重复的倒排数据、减少 Segment 数量**，从而提升查询性能。

**核心原理说明**

1. **合并触发条件**：由 `MergePolicy` 控制，8.x 默认使用 `TieredMergePolicy`：
   - 根据 Segment 的"评分"（size + 删除文档比例）决定合并优先级。
   - 当索引中的 Segment 数量超过 `floor_segment`（默认 2）时，触发合并。
   - 大 Segment 不会被频繁合并（`segments_per_tier` 控制每层允许的 Segment 数，默认 10）。
   - 最大合并 Segment 大小由 `max_merged_segment` 控制（默认 5GB）。

2. **合并过程**：
   - **Step 1 - 选择候选 Segment**：MergePolicy 选择一组 Segment 作为合并源。
   - **Step 2 - 归并排序**：对每个字段，将多个 Segment 的倒排索引通过归并排序合成为一个：
     - Term Dictionary：合并多个 FST，生成新的 FST。
     - Posting List：合并多个 Posting List，真正删除已标记删除的文档。
     - DocValues：按新 Doc ID 顺序重排 DocValues。
     - Stored Fields：复制并重排文档。
   - **Step 3 - 原子切换**：新 Segment 写完后，在 Commit Point 中原子地将旧 Segment 替换为新 Segment。
   - **Step 4 - 删除旧 Segment**：旧 Segment 文件在引用计数归零后被删除。

3. **合并与 IO**：合并是 I/O 密集型操作，需要读取多个旧 Segment 并写入新 Segment。合并期间的读写请求不受影响（旧 Segment 仍可读，新 Segment 完成后才可见）。

4. **合并调度**：合并操作由 `ConcurrentMergeScheduler` 管理，默认使用独立的线程池，最大合并线程数由 `max_thread_count` 控制。

**注意事项**

- 合并会消耗大量 I/O 和 CPU，在写入高峰期可能导致性能抖动。可通过 `indices.store.throttle.max_bytes_per_sec` 限制合并的 I/O 速率。
- 8.x 中可以通过 `_forcemerge` API 强制触发合并：
  ```
  POST /my-index/_forcemerge?max_num_segments=1
  ```
  但 `forcemerge` 仅应在低峰期执行，且之后应执行 `_cache/clear` 清除缓存。
- `forcemerge` 到 1 个 Segment 后，索引的 `_version` 检查会失效，因为每个操作都变成了"对该 Segment 的修改"。
- 删除大量文档后，建议执行 `forcemerge` 以回收磁盘空间（合并会物理删除已标记删除的文档）。
- 8.x 中 `_ilm`（索引生命周期管理）的 `warm` 和 `cold` 阶段通常包含 `forcemerge` 操作。

---

### 缓存机制（Query Cache / Field Data Cache / Shard Request Cache）

**概念定义**

Elasticsearch 的缓存机制是提升查询性能的关键基础设施，主要包括三种缓存：**Node Query Cache（过滤器缓存）、Field Data Cache（字段数据缓存）、Shard Request Cache（分片请求缓存）**。三者分别缓存不同粒度和类型的查询结果，协同工作以最小化磁盘 I/O 和 CPU 计算。

**核心原理说明**

#### Node Query Cache（节点级查询缓存）

- **缓存内容**：缓存 `filter` 上下文中的查询结果，即匹配某个 Filter 的 Doc ID 集合（以 Roaring Bitmap 存储）。
- **缓存 Key**：Filter 查询的 DSL 序列化 + 索引名称 + 分片 ID。
- **缓存粒度**：Segment 级别，每个 Segment 独立缓存。因此当 Segment 合并后，相应的缓存条目自动失效。
- **适用场景**：频繁重复的 Filter 查询（如 `term` 查询、`range` 查询在 `filter` 上下文中）。
- **配置**：`indices.queries.cache.size` 控制缓存大小（默认 10% 堆内存）。
- **缓存策略**：LRU（最近最少使用）淘汰策略。只有被频繁使用的 Filter 才会被缓存，Lucene 使用频率统计自动决定是否缓存某个查询。

#### Field Data Cache（字段数据缓存）

- **缓存内容**：缓存字段的全局值列表（Global Ordinals），用于 `text` 字段的聚合和排序（`fielddata=true`）。
- **重要变更**：Elasticsearch 8.x 中，`text` 字段的 `fielddata` 已**彻底移除**。聚合和排序必须使用 `keyword` 字段（走 DocValues），不再支持在 `text` 字段上开启 `fielddata`。
- **当前用途**：Principal 上仅用于 `join` 字段（父子文档关系）的 global ordinals 缓存。
- **配置**：`indices.fielddata.cache.size`（默认无限制，但 8.x 中已不推荐使用）。

#### Shard Request Cache（分片请求缓存）

- **缓存内容**：缓存整个分片级查询的完整结果（Top N 的 Doc ID 列表）。
- **缓存 Key**：完整的查询 DSL JSON 字符串 + 索引名称 + 分片 ID。
- **刷新策略**：当分片发生 Refresh（新 Segment 产生）时，该分片的请求缓存**全部失效**。因此它适合数据变化不频繁（Refresh 间隔长）的索引。
- **缓存粒度**：分片级别。缓存的是 Query Phase 的结果（Doc ID + Score），不包含 Fetch Phase 的完整文档。
- **适用场景**：日志分析、Dashboard 等 `size=0` 的聚合查询，或数据变化不频繁的搜索场景。
- **配置**：`indices.requests.cache.size` 控制缓存大小（默认 1% 堆内存）。
- **控制**：请求级别通过 `request_cache=true/false` 参数控制是否使用缓存。

**注意事项**

- Node Query Cache 和 Shard Request Cache 容易混淆：前者缓存的是 Filter 的 Doc ID 集合（Roaring Bitmap），后者缓存的是整个查询请求的 Top N 结果。
- 频繁 Refresh 的索引（如实时写入场景）不宜使用 Shard Request Cache，因为每次 Refresh 都会清空缓存。
- 8.x 中 `fielddata` 已从 `text` 字段移除，如果遇到 `fielddata` 相关的错误，说明 Mapping 设计有问题，应改用 `keyword` 字段进行聚合。
- 缓存大小受堆内存限制，过大的缓存会触发 GC，建议根据实际查询模式监控并调整。
- 可以通过 `_stats` API 或 `_nodes/stats/indices` 查看各缓存的命中率、驱逐量等指标。
