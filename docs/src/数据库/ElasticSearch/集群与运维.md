## 集群规划

### 节点角色

**概念定义**

Elasticsearch 8.x 中，节点角色（Node Role）决定了节点在集群中承担的职责。通过 `node.roles` 配置，可将节点指定为单一角色或组合角色。角色分离是生产环境的核心原则，避免单一节点承担过多职责导致资源争抢。

#### 角色分类

| 角色 | 配置值 | 职责 | 资源倾向 |
|------|--------|------|----------|
| **Master** | `master` | 管理集群元数据（索引创建/删除、分片分配、节点加入/离开），不处理请求 | CPU 中等、内存中等 |
| **Data** | `data` | 存储分片数据，执行数据相关操作（CRUD、搜索、聚合） | 磁盘 I/O 高、内存高、CPU 高 |
| **Data Content** | `data_content` | 存储时序/日志类数据（8.x 细分角色） | 同 Data |
| **Data Hot** | `data_hot` | 热节点，存储频繁访问的索引 | 磁盘 SSD、CPU 高 |
| **Data Warm** | `data_warm` | 温节点，存储不常访问的索引 | 磁盘 HDD 可接受 |
| **Data Cold** | `data_cold` | 冷节点，存储几乎不访问的索引 | 磁盘 HDD、可压缩 |
| **Data Frozen** | `data_frozen` | 冻结节点，存储极少访问的索引（Searchable Snapshot） | 磁盘大容量、低成本 |
| **Ingest** | `ingest` | 执行预处理管道（Pipeline），在索引前转换文档 | CPU 高、内存中等 |
| **Coordinating** | （无特定角色） | 仅作为协调节点，转发请求、合并结果。设置 `node.roles: []` | CPU 高、内存高 |
| **ML** | `ml` | 运行机器学习作业（异常检测、NLP 推理） | CPU 极高、内存极高 |
| **Remote Cluster Client** | `remote_cluster_client` | 作为跨集群搜索的客户端代理 | 网络带宽、CPU 中等 |
| **Transform** | `transform` | 执行 Transform 作业（连续数据透视） | CPU 高、内存高 |
| **Voting-only** | `voting_only` | 仅参与 Master 选举投票，不成为 Master | 资源低 |

**核心参数**

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `node.roles` | `[master, data, ingest, ml, remote_cluster_client, transform]` | 节点角色列表（8.x 默认全角色） |
| `discovery.seed_hosts` | `["127.0.0.1", "[::1]"]` | 集群发现种子节点 |
| `cluster.initial_master_nodes` | - | 首次启动时的 Master 候选节点列表 |
| `discovery.zen.minimum_master_nodes` | 已移除（8.x） | 8.x 使用基于 Quorum 的选举，无需手动配置 |
| `node.attr.box_type` | - | 自定义属性（用于冷热分层路由，如 `hot`/`warm`/`cold`） |

**配置示例**

```yaml
# --- Master 专用节点 ---
cluster.name: my-cluster
node.name: master-01
node.roles: [master]
path.data: /data/elasticsearch
path.logs: /var/log/elasticsearch
network.host: 10.0.0.1
http.port: 9200
transport.port: 9300
discovery.seed_hosts:
  - 10.0.0.1:9300
  - 10.0.0.2:9300
  - 10.0.0.3:9300
cluster.initial_master_nodes:
  - master-01
  - master-02
  - master-03

# --- Data Hot 节点 ---
node.name: data-hot-01
node.roles: [data_hot, data_content]
node.attr.box_type: hot
network.host: 10.0.0.10
discovery.seed_hosts:
  - 10.0.0.1:9300
  - 10.0.0.2:9300
  - 10.0.0.3:9300

# --- Coordinating 专用节点 ---
node.name: coord-01
node.roles: []
network.host: 10.0.0.20
discovery.seed_hosts:
  - 10.0.0.1:9300
  - 10.0.0.2:9300
  - 10.0.0.3:9300
```

**注意事项与最佳实践**

- **Master 节点数量**：生产环境始终保持 3 个 Master 专用节点（奇数），避免脑裂。8.x 使用 Quorum 选举（`N/2 + 1`），3 节点可容忍 1 个故障。
- **Data 节点角色细分**：8.x 引入 `data_content`、`data_hot`、`data_warm`、`data_cold`、`data_frozen` 替代通用 `data` 角色。建议使用细分角色配合 Index Lifecycle Management（ILM）。
- **Coordinating 节点**：在大型集群中，建议部署专用协调节点（`node.roles: []`），负责请求路由和结果合并，减轻 Data 节点负担。协调节点对 CPU 和内存要求高，但不需要大容量磁盘。
- **Voting-only 节点**：在不想增加 Master 资源开销但又需要提高选举容错能力时使用。
- **角色变更**：节点角色变更需要重启节点。8.x 不支持运行时动态修改 `node.roles`。

### 硬件选型

**概念定义**

硬件选型直接影响 Elasticsearch 集群的稳定性、性能和成本。需根据数据量、写入吞吐量（TPS）、查询 QPS、数据保留周期等指标综合评估。

**核心参数**

| 维度 | 推荐配置 | 说明 |
|------|----------|------|
| **CPU 核心数** | 热节点 16-64 核，温/冷节点 8-16 核，Master 节点 4-8 核 | Elasticsearch 使用线程池模型，核心数影响并发处理能力 |
| **CPU 类型** | 2.0 GHz+，推荐 3.0 GHz+ | 单核主频比核心数更重要，Lucene 段合并是单线程密集型 |
| **内存** | 64 GB（生产环境最低），128 GB+ 推荐 | 50% 给 JVM Heap（不超过 32 GB），剩余给 OS Page Cache |
| **JVM Heap** | 推荐 50% 可用内存，上限 31 GB（`-XX:-UseCompressedOops` 边界） | 超过 32 GB 时指针压缩失效，实际内存利用率下降 |
| **磁盘类型** | 热节点 NVMe SSD，温节点 SATA SSD，冷节点 HDD | I/O 是核心瓶颈，SSD 显著提升写入和查询性能 |
| **磁盘容量** | 按 `每日数据量 × 保留天数 × 1.15（压缩比）× 1.5（安全系数）` 计算 | 预留 20% 以上空闲空间，触发 `disk.watermark` 前需扩容 |
| **磁盘 RAID** | RAID 0（性能优先）或 RAID 10（安全+性能），禁用 RAID 5/6 | RAID 5/6 的写入惩罚严重拖慢性能 |
| **网络** | 10 Gbps 节点间通信，1 Gbps 客户端通信 | 节点间数据传输（分片恢复、重平衡）带宽消耗大 |
| **文件系统** | ext4 / XFS，禁用 atime 挂载 | 挂载选项：`noatime,nodiratime` |
| **虚拟内存** | `vm.max_map_count=262144` | 必须设置，否则无法启动 |

**配置示例**

```bash
# /etc/sysctl.conf
vm.max_map_count=262144
vm.swappiness=1
net.core.somaxconn=65535

# /etc/security/limits.conf
elasticsearch  -  nofile  65536
elasticsearch  -  nproc   4096
elasticsearch  -  memlock unlimited

# /etc/fstab（挂载选项）
UUID=xxx /data ext4 defaults,noatime,nodiratime 0 2
```

```yaml
# elasticsearch.yml - JVM 配置
# 在 jvm.options 中设置
-Xms31g
-Xmx31g
# JDK 版本：8.x 捆绑 JDK 21（无需单独安装）
```

**注意事项与最佳实践**

- **JVM Heap 不超过 32 GB**：这是 JVM 指针压缩（Compressed OOPs）的硬边界。设置为 31 GB 是安全值。如果物理内存 128 GB，Heap 设为 31 GB，剩余 97 GB 留给 OS Page Cache 缓存 Lucene 索引文件。
- **禁用 Swap**：`vm.swappiness=1` 或 `bootstrap.memory_lock: true`，防止 JVM Heap 被换出到磁盘，导致 Full GC 时间不可控。
- **文件描述符**：每个段文件、每个网络连接都消耗文件描述符，`nofile 65536` 是基础值，大规模集群建议 131072+。
- **磁盘水位线**：`cluster.routing.allocation.disk.watermark.low`（默认 85%）、`cluster.routing.allocation.disk.watermark.high`（默认 90%）、`cluster.routing.allocation.disk.watermark.flood_stage`（默认 95%）。到达 flood_stage 时所有索引变为只读。

### 分片数量规划

**概念定义**

分片（Shard）是 Elasticsearch 数据分布的最小单位。每个索引由若干主分片（Primary Shard）和副本分片（Replica Shard）组成。分片数量在索引创建时设定，创建后不可修改主分片数。

**核心参数**

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `index.number_of_shards` | 1（7.x+） | 主分片数，创建后不可变 |
| `index.number_of_replicas` | 1 | 副本分片数，可动态修改 |
| `cluster.max_shards_per_node` | 1000 | 单节点最大分片数（含主分片和副本） |
| `cluster.routing.allocation.total_shards_per_node` | -1（无限制） | 单个索引单节点最多分片数 |

#### 分片数计算公式

```
主分片数 = ceil(数据总量(GB) / 单分片目标大小(GB))
          或
主分片数 = ceil(节点数 × 每节点期望分片数)
```

| 场景 | 单分片建议大小 | 说明 |
|------|---------------|------|
| 日志/时序数据 | 30-50 GB | 数据量大，写入密集 |
| 搜索场景 | 10-30 GB | 查询性能敏感 |
| 小数据量 | 1-10 GB | 避免过度分片 |
| 每个节点总分数 | 总 Heap(GB) × 20 | 经验值：每 GB Heap 管理约 20 个分片 |

**配置示例**

```json
## 创建索引时指定分片数
PUT /my_index
{
  "settings": {
    "index.number_of_shards": 5,
    "index.number_of_replicas": 1
  }
}

## 动态修改副本数
PUT /my_index/_settings
{
  "index.number_of_replicas": 2
}

## 查看分片分布
GET /_cat/shards/my_index?v

## 索引模板中预设分片数
PUT /_index_template/logs_template
{
  "index_patterns": ["logs-*"],
  "template": {
    "settings": {
      "index.number_of_shards": 3,
      "index.number_of_replicas": 1,
      "index.routing.allocation.total_shards_per_node": 2
    }
  }
}
```

**注意事项与最佳实践**

- **分片数不可减少**：主分片数在索引创建后无法修改，只能通过 Reindex 重建。因此规划时需预留一定余量。
- **过度分片（Over-sharding）**：每个分片有内存开销（约 50 MB Heap + Lucene 元数据），分片过多会导致集群状态臃肿、Master 压力增大。理想状态是单节点管理 200-600 个分片。
- **分片过少（Under-sharding）**：单分片过大（>100 GB）会导致恢复时间长、重平衡困难、查询并发度不足。
- **副本数权衡**：副本数越多，读性能越好，容错性越高，但写入性能下降（需同步写入副本）且存储成本翻倍。一般生产环境副本数设为 1 或 2。
- **forcemerge 与分片**：对只读索引执行 `_forcemerge` 可减少段数，提升查询性能，但不能减少分片数。

### 集群规模估算

**概念定义**

集群规模估算是在项目启动前，根据业务需求推算出所需的节点数量、规格和拓扑结构，确保集群在容量和性能上满足预期。

#### 估算维度

| 维度 | 输入参数 | 计算方式 |
|------|----------|----------|
| **存储容量** | 每日增量（GB）× 保留天数 × 副本数 | 总存储 = 增量 × 天数 × (1 + 副本数) × 1.15（压缩比） |
| **写入吞吐** | 写入峰值 TPS × 文档平均大小 | 需确保 Data 节点 CPU 和 I/O 不会成为瓶颈 |
| **查询 QPS** | 峰值 QPS × 平均响应时间 | 需确保有足够副本数分散查询负载 |
| **内存容量** | Heap 需求 + OS Page Cache | Page Cache 至少覆盖活跃索引的 30% 数据量 |

#### 估算公式

```
总存储(GB) = 每日数据量(GB) × 保留天数 × (1 + 副本数) × 1.15(压缩比)
节点数     = ceil(总存储(GB) / 单节点可用空间(GB) / 0.85(水位线))
           = ceil(总存储(GB) / (单节点磁盘 × 0.85 × 0.95(RAID/文件系统损耗)))
```

#### 典型场景参考

| 场景 | 数据量 | 推荐配置 | 节点数 |
|------|--------|----------|--------|
| 开发/测试 | < 100 GB | 单节点，4C/16G/200G SSD | 1 |
| 小规模生产 | 100 GB - 1 TB | 3 Master + 3 Data，8C/32G/500G SSD | 6 |
| 中规模生产 | 1 TB - 10 TB | 3 Master + 5-10 Data(Hot+Warm)，16C/64G/2T | 8-13 |
| 大规模生产 | 10 TB - 100 TB | 3 Master + 15+ Data(Hot+Warm+Cold)，32C/128G/4T | 18+ |
| 日志平台 | 1 TB/天 | 3 Master + 10 Hot + 5 Warm + 2 Coordinating | 20+ |

**配置示例**

```yaml
# 中规模生产集群拓扑示例
# 3 × Master（专用）
node.roles: [master]
CPU: 8C | RAM: 16G | Disk: 200G SSD

# 5 × Data Hot（SSD）
node.roles: [data_hot, data_content]
node.attr.box_type: hot
CPU: 16C | RAM: 64G | Disk: 2T NVMe SSD
Heap: 31G

# 3 × Data Warm（HDD）
node.roles: [data_warm]
node.attr.box_type: warm
CPU: 8C | RAM: 32G | Disk: 8T HDD
Heap: 15G

# 2 × Coordinating
node.roles: []
CPU: 8C | RAM: 32G | Disk: 100G SSD
Heap: 15G
```

**注意事项与最佳实践**

- **预留 20% 余量**：无论是存储容量还是计算能力，始终预留 20% 以上的缓冲空间，应对突发流量和数据增长。
- **水平扩展优于垂直扩展**：增加中等规格的 Data 节点比升级单节点配置更灵活，重平衡也更平滑。
- **Master 节点不存数据**：Master 节点仅需中等配置，重点保障其稳定性，与 Data 节点物理隔离。
- **网络拓扑**：所有节点应在同一数据中心（低延迟），跨机房部署需确保延迟 < 10ms，否则会严重影响集群稳定性。

### Docker 部署

**概念定义**

使用 Docker 容器化部署 Elasticsearch 8.x，通过 Docker Compose 编排多节点集群，适用于开发环境和小规模部署。

**核心参数**

| 参数 | 说明 |
|------|------|
| `ES_JAVA_OPTS` | JVM 参数（如 `-Xms2g -Xmx2g`） |
| `discovery.type` | 发现模式：`single-node`（单节点）或 `multi-node`（多节点） |
| `network.publish_host` | 节点对外发布的地址 |
| `xpack.security.enabled` | 是否启用安全认证（8.x 默认 true） |
| `ELASTIC_PASSWORD` | `elastic` 用户密码 |
| `KIBANA_PASSWORD` | `kibana_system` 用户密码 |

**配置示例**

```yaml
# docker-compose.yml — 三节点集群
version: '3.8'
services:
  es01:
    image: docker.elastic.co/elasticsearch/elasticsearch:8.17.0
    container_name: es01
    environment:
      - node.name=es01
      - cluster.name=es-docker-cluster
      - discovery.seed_hosts=es02,es03
      - cluster.initial_master_nodes=es01,es02,es03
      - bootstrap.memory_lock=true
      - "ES_JAVA_OPTS=-Xms2g -Xmx2g"
      - xpack.security.enabled=false
      - xpack.security.enrollment.enabled=false
    ulimits:
      memlock:
        soft: -1
        hard: -1
      nofile:
        soft: 65536
        hard: 65536
    volumes:
      - es01_data:/usr/share/elasticsearch/data
    ports:
      - "9200:9200"
      - "9300:9300"
    networks:
      - elastic

  es02:
    image: docker.elastic.co/elasticsearch/elasticsearch:8.17.0
    container_name: es02
    environment:
      - node.name=es02
      - cluster.name=es-docker-cluster
      - discovery.seed_hosts=es01,es03
      - cluster.initial_master_nodes=es01,es02,es03
      - bootstrap.memory_lock=true
      - "ES_JAVA_OPTS=-Xms2g -Xmx2g"
      - xpack.security.enabled=false
      - xpack.security.enrollment.enabled=false
    ulimits:
      memlock:
        soft: -1
        hard: -1
      nofile:
        soft: 65536
        hard: 65536
    volumes:
      - es02_data:/usr/share/elasticsearch/data
    networks:
      - elastic

  es03:
    image: docker.elastic.co/elasticsearch/elasticsearch:8.17.0
    container_name: es03
    environment:
      - node.name=es03
      - cluster.name=es-docker-cluster
      - discovery.seed_hosts=es01,es02
      - cluster.initial_master_nodes=es01,es02,es03
      - bootstrap.memory_lock=true
      - "ES_JAVA_OPTS=-Xms2g -Xmx2g"
      - xpack.security.enabled=false
      - xpack.security.enrollment.enabled=false
    ulimits:
      memlock:
        soft: -1
        hard: -1
      nofile:
        soft: 65536
        hard: 65536
    volumes:
      - es03_data:/usr/share/elasticsearch/data
    networks:
      - elastic

  kibana:
    image: docker.elastic.co/kibana/kibana:8.17.0
    container_name: kibana
    ports:
      - "5601:5601"
    environment:
      - ELASTICSEARCH_HOSTS=http://es01:9200
    networks:
      - elastic

volumes:
  es01_data:
  es02_data:
  es03_data:

networks:
  elastic:
    driver: bridge
```

**注意事项与最佳实践**

- **`vm.max_map_count`**：Linux 宿主机必须设置 `sysctl -w vm.max_map_count=262144`，否则容器无法启动。
- **`bootstrap.memory_lock`**：启用内存锁，防止 JVM Heap 被 Swap。需配合 `ulimits.memlock: -1`。
- **数据持久化**：使用命名卷（Named Volume）或绑定挂载（Bind Mount），确保容器重启后数据不丢失。
- **8.x 安全默认开启**：生产环境不要禁用 `xpack.security.enabled`，应使用证书或令牌进行节点间认证。
- **网络模式**：生产环境建议使用 `host` 网络模式（`network_mode: host`），避免 Docker 桥接网络的性能损耗。

### K8S 部署（ECK Operator）

**概念定义**

ECK（Elastic Cloud on Kubernetes）是 Elastic 官方提供的 Kubernetes Operator，通过 CRD（Custom Resource Definition）管理 Elasticsearch、Kibana、APM Server、Beats 等组件的生命周期。

**核心参数**

| 参数 | 说明 |
|------|------|
| `spec.version` | Elasticsearch 版本号 |
| `spec.nodeSets[].count` | 该节点集的副本数 |
| `spec.nodeSets[].config` | 节点配置（elasticsearch.yml） |
| `spec.nodeSets[].podTemplate` | Pod 模板（资源限制、亲和性等） |
| `spec.nodeSets[].volumeClaimTemplates` | 持久卷声明模板 |
| `spec.http.tls` | HTTP 层 TLS 配置 |
| `spec.transport.tls` | Transport 层 TLS 配置 |

**配置示例**

```yaml
# elasticsearch.yaml — ECK 部署 Elasticsearch 集群
apiVersion: elasticsearch.k8s.elastic.co/v1
kind: Elasticsearch
metadata:
  name: production
  namespace: elastic
spec:
  version: 8.17.0
  http:
    tls:
      selfSignedCertificate:
        disabled: true  # 生产环境应启用
  nodeSets:
    # Master 节点集
    - name: master
      count: 3
      config:
        node.roles: ["master"]
        node.store.allow_mmap: false
      podTemplate:
        spec:
          containers:
            - name: elasticsearch
              resources:
                requests:
                  cpu: 2
                  memory: 4Gi
                limits:
                  cpu: 4
                  memory: 8Gi
              env:
                - name: ES_JAVA_OPTS
                  value: "-Xms4g -Xmx4g"
          affinity:
            podAntiAffinity:
              requiredDuringSchedulingIgnoredDuringExecution:
                - topologyKey: kubernetes.io/hostname
                  labelSelector:
                    matchLabels:
                      elasticsearch.k8s.elastic.co/cluster-name: production
      volumeClaimTemplates:
        - metadata:
            name: elasticsearch-data
          spec:
            accessModes: [ReadWriteOnce]
            resources:
              requests:
                storage: 100Gi
            storageClassName: ssd

    # Data Hot 节点集
    - name: data-hot
      count: 5
      config:
        node.roles: ["data_hot", "data_content"]
        node.attr.box_type: hot
        node.store.allow_mmap: false
      podTemplate:
        spec:
          containers:
            - name: elasticsearch
```

#### 安装 ECK Operator

```bash
# 安装 CRD 和 Operator
kubectl create -f https://download.elastic.co/downloads/eck/2.17.0/crds.yaml
kubectl apply -f https://download.elastic.co/downloads/eck/2.17.0/operator.yaml

# 查看 Operator 状态
kubectl -n elastic-system get pods

# 部署 Elasticsearch 集群
kubectl apply -f elasticsearch.yaml

# 查看集群状态
kubectl -n elastic get elasticsearch

# 获取 elastic 用户密码
kubectl -n elastic get secret production-es-elastic-user \
  -o go-template='\{\{.data.elastic | base64decode}}'

# 端口转发
kubectl -n elastic port-forward service/production-es-http 9200:9200
```

**注意事项与最佳实践**

- **Pod 反亲和性**：必须配置 `podAntiAffinity`，确保同一节点集的 Pod 分布在不同物理节点上，避免单点故障。
- **存储类选择**：热节点使用 `nvme-ssd` 存储类，温/冷节点使用 `hdd` 存储类，通过 StorageClass 实现。
- **资源 Limit 与 Request**：`request` 和 `limit` 应设为相同值，使用 Guaranteed QoS 类别，避免被 OOM Kill。
- **`node.store.allow_mmap`**：在 K8S 中通常设为 `false`，因为容器内 `vm.max_map_count` 受宿主机限制。ECK 默认使用 NIOFS。
- **升级策略**：ECK 支持滚动升级，通过修改 `spec.version` 触发。ECK 会依次重启节点，确保集群健康。
- **备份**：使用 ECK 的 Snapshot CRD 配合 SLM 实现自动快照。

## 集群健康监控

### _cat API

**概念定义**

`_cat` API 是 Elasticsearch 提供的紧凑、可读性强的集群状态查询接口。所有 `_cat` 端点都支持 `?v`（Verbose 列头）、`?help`（列出字段）、`?h=col1,col2`（指定列）、`?format=json`（JSON 输出）等参数。

**核心参数**

| 通用参数 | 说明 |
|----------|------|
| `?v` | 显示列头（Verbose） |
| `?help` | 显示该端点所有可用字段 |
| `?h=col1,col2` | 仅显示指定列 |
| `?format=json` | 输出 JSON 格式（默认文本表格） |
| `?s=col:desc` | 按指定列排序 |
| `?pretty` | 格式化 JSON 输出 |

#### 常用端点

```bash
# ============ 集群层面 ============

# 集群健康（最常用）
GET /_cat/health?v
# 输出：epoch timestamp cluster status node.total node.data shards pri relo init unassign pending_tasks max_task_wait_time active_shards_percent

# 集群节点列表
GET /_cat/nodes?v&h=name,ip,heap.percent,ram.percent,cpu,load_1m,node.role,master,disk.used_percent
# 关键字段：heap.percent, cpu, load_1m, disk.used_percent

# 主节点信息
GET /_cat/master?v

# 集群分配解释
GET /_cat/allocation?v

# 线程池
GET /_cat/thread_pool?v&h=node_name,name,active,rejected,completed,queue,queue_size

# ============ 索引层面 ============

# 所有索引（含健康状态）
GET /_cat/indices?v&h=index,health,status,pri,rep,docs.count,store.size,pri.store.size

# 索引分片分布
GET /_cat/shards?v&h=index,shard,prirep,state,node,store

# 未分配分片
GET /_cat/shards?v&h=index,shard,prirep,state,unassigned.reason | grep UNASSIGNED

# 恢复中的分片
GET /_cat/recovery?v&active_only=true

# 段信息
GET /_cat/segments?v&h=index,shard,segment,size,size.memory,committed,searchable,version

# ============ 节点层面 ============

# 节点磁盘使用
GET /_cat/nodes?v&h=name,node.role,disk.total,disk.used,disk.avail,disk.used_percent

# 字段数据缓存
GET /_cat/fielddata?v&h=node,field,size

# 待处理任务
GET /_cat/pending_tasks?v

# ============ 模板与策略 ============

# 索引模板
GET /_cat/templates?v

# ILM 策略
GET /_cat/ilm?v

# SLM 策略
GET /_cat/slm?v
```

**注意事项与最佳实践**

- **`_cat/health` 是最快判断集群状态的方式**：`status` 字段 `green`/`yellow`/`red` 直接反映集群健康度。`yellow` 表示有未分配的副本，`red` 表示有未分配的主分片。
- **`active_shards_percent`**：该指标 < 100% 时说明有分片未分配或正在初始化。
- **`_cat/nodes` 监控磁盘**：`disk.used_percent` 超过 85% 会触发水位线，需立即关注。
- **JSON 输出**：脚本化监控时使用 `?format=json`，配合 `jq` 或程序解析。

### _cluster/health

**概念定义**

`_cluster/health` 提供比 `_cat/health` 更详细的集群健康信息，包括分片状态分布、任务队列和超时控制。

**核心参数**

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `level` | `cluster` | 粒度：`cluster` / `indices` / `shards` |
| `wait_for_status` | - | 阻塞等待，直到集群达到指定状态（`green`/`yellow`/`red`） |
| `wait_for_nodes` | - | 阻塞等待，直到指定数量节点可用 |
| `wait_for_no_relocating_shards` | `false` | 阻塞等待，直到无重定位分片 |
| `wait_for_no_initializing_shards` | `false` | 阻塞等待，直到无初始化分片 |
| `wait_for_active_shards` | - | 阻塞等待，直到指定数量活跃分片 |
| `timeout` | `30s` | 阻塞等待超时时间 |

**配置示例**

```bash
# 基础集群健康
GET /_cluster/health
# 响应：
# {
#   "cluster_name": "my-cluster",
#   "status": "green",
#   "timed_out": false,
#   "number_of_nodes": 6,
#   "number_of_data_nodes": 3,
#   "active_primary_shards": 42,
#   "active_shards": 84,
#   "relocating_shards": 0,
#   "initializing_shards": 0,
#   "unassigned_shards": 0,
#   "delayed_unassigned_shards": 0,
#   "number_of_pending_tasks": 0,
#   "number_of_in_flight_fetch": 0,
#   "task_max_waiting_in_queue_millis": 0,
#   "active_shards_percent_as_number": 100.0
# }

# 索引级别（查看各索引分片状态）
GET /_cluster/health?level=indices&pretty

# 分片级别（精确到每个分片）
GET /_cluster/health?level=shards&pretty

# 阻塞等待集群变绿（常用于脚本化部署）
GET /_cluster/health?wait_for_status=green&timeout=60s
```

**注意事项与最佳实践**

- **自动化脚本**：部署后使用 `wait_for_status=yellow&timeout=60s` 等待集群就绪。`yellow` 是单节点集群的正常状态（无副本节点）。
- **`unassigned_shards` > 0**：需立即排查原因，常见原因包括节点不足、磁盘水位线、分片分配过滤等。
- **`number_of_pending_tasks`**：持续 > 0 说明 Master 节点处理能力不足，需检查 Master 节点负载或集群规模。
- **`relocating_shards`**：在节点扩缩容或重平衡期间正常，持续大量重定位需关注。

### _nodes/stats

**概念定义**

`_nodes/stats` 返回每个节点的运行时指标，涵盖 JVM、线程池、文件系统、Transport、HTTP、索引、段合并、GC 等维度的详细统计。

**核心参数**

| 参数 | 说明 |
|------|------|
| `?nodes=node1,node2` | 限定返回指定节点 |
| `?metric=jvm,os,thread_pool` | 限定返回指定指标类别 |
| `?level=indices` | 索引级统计 |
| `?level=shards` | 分片级统计（数据量大，慎用） |

**配置示例**

```bash
# 获取所有节点完整统计
GET /_nodes/stats

# 获取指定节点的 JVM + OS + 线程池统计
GET /_nodes/node-1,node-2/stats/jvm,os,thread_pool

# 获取 JVM 指标（GC + Heap + Buffer Pools）
GET /_nodes/stats/jvm?pretty

# 获取线程池统计
GET /_nodes/stats/thread_pool?pretty

# 获取文件系统统计
GET /_nodes/stats/fs?pretty

# 获取索引级统计（索引/搜索/合并/刷新等）
GET /_nodes/stats/indices?pretty

# 获取 Transport 统计
GET /_nodes/stats/transport?pretty

# 获取 HTTP 统计
GET /_nodes/stats/http?pretty

# 热点指标监控
GET /_nodes/stats/indices,thread_pool,jvm,fs,os,transport,http,breaker
```

#### 关键指标解读

| 指标路径 | 含义 | 告警阈值 |
|----------|------|----------|
| `jvm.mem.heap_used_percent` | JVM Heap 使用率 | > 85% |
| `jvm.gc.collectors.old.collection_time_in_millis` | Old GC 累计耗时 | 增长率异常 |
| `thread_pool.write.rejected` | 写入线程池拒绝数 | > 0 |
| `thread_pool.search.rejected` | 搜索线程池拒绝数 | > 0 |
| `fs.total.free_in_bytes` | 磁盘剩余空间 | 低于水位线 |
| `os.cpu.percent` | CPU 使用率 | > 85% |
| `indices.store.size_in_bytes` | 索引存储大小 | 持续增长 |
| `indices.segments.count` | 段总数 | 单分片 > 1000 |
| `transport.rx_size_in_bytes` / `tx_size_in_bytes` | 节点间收发流量 | 网络带宽占比 |
| `breaker.parent.tripped` | 父熔断器触发次数 | > 0 |

**注意事项与最佳实践**

- **`_nodes/stats` 开销**：`level=shards` 会返回大量数据，生产环境慎用。默认 `level=node` 是安全选择。
- **监控工具集成**：`_nodes/stats` 是 Prometheus Exporter、Metricbeat 等工具的核心数据源。
- **GC 监控**：`jvm.gc.collectors.old.collection_count` 和 `collection_time` 是 JVM 健康度的核心指标。频繁 Full GC 说明 Heap 不足或存在内存泄漏。

### 慢查询日志

**概念定义**

Elasticsearch 慢查询日志记录执行时间超过阈值的查询和索引操作，是排查性能问题的核心手段。分为 **搜索慢日志**（Search Slow Log）和 **索引慢日志**（Index Slow Log）。

**核心参数**

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `index.search.slowlog.threshold.query.warn` | -1（禁用） | 查询阶段慢日志 warn 阈值 |
| `index.search.slowlog.threshold.query.info` | -1 | 查询阶段慢日志 info 阈值 |
| `index.search.slowlog.threshold.query.debug` | -1 | 查询阶段慢日志 debug 阈值 |
| `index.search.slowlog.threshold.query.trace` | -1 | 查询阶段慢日志 trace 阈值 |
| `index.search.slowlog.threshold.fetch.warn` | -1 | Fetch 阶段慢日志 warn 阈值 |
| `index.search.slowlog.threshold.fetch.info` | -1 | Fetch 阶段慢日志 info 阈值 |
| `index.search.slowlog.threshold.fetch.debug` | -1 | Fetch 阶段慢日志 debug 阈值 |
| `index.search.slowlog.level` | - | 日志级别（`info`/`warn`/`debug`/`trace`） |
| `index.indexing.slowlog.threshold.index.warn` | -1 | 索引慢日志 warn 阈值 |
| `index.indexing.slowlog.threshold.index.info` | -1 | 索引慢日志 info 阈值 |
| `index.indexing.slowlog.threshold.index.debug` | -1 | 索引慢日志 debug 阈值 |
| `index.indexing.slowlog.threshold.index.trace` | -1 | 索引慢日志 trace 阈值 |
| `index.indexing.slowlog.source` | `0` | 记录原始文档的最大字符数（0 为不记录） |

**配置示例**

```json
## 为特定索引开启搜索慢日志
PUT /my_index/_settings
{
  "index.search.slowlog.threshold.query.warn": "1s",
  "index.search.slowlog.threshold.query.info": "500ms",
  "index.search.slowlog.threshold.query.debug": "200ms",
  "index.search.slowlog.threshold.fetch.warn": "1s",
  "index.search.slowlog.threshold.fetch.info": "500ms",
  "index.search.slowlog.level": "info"
}

## 开启索引慢日志
PUT /my_index/_settings
{
  "index.indexing.slowlog.threshold.index.warn": "2s",
  "index.indexing.slowlog.threshold.index.info": "1s",
  "index.indexing.slowlog.threshold.index.debug": "500ms",
  "index.indexing.slowlog.source": "0",
  "index.indexing.slowlog.level": "info"
}

## 通过索引模板为所有日志索引预设慢日志
PUT /_index_template/logs_slowlog
{
  "index_patterns": ["logs-*"],
  "template": {
    "settings": {
      "index.search.slowlog.threshold.query.warn": "2s",
      "index.search.slowlog.threshold.query.info": "1s",
      "index.search.slowlog.threshold.fetch.warn": "1s",
      "index.search.slowlog.level": "info",
      "index.indexing.slowlog.threshold.index.warn": "5s",
      "index.indexing.slowlog.threshold.index.info": "2s",
      "index.indexing.slowlog.level": "info"
    }
  }
}
```

#### 慢日志输出示例

```
[2025-01-15T10:22:33,456][WARN ][i.s.slowlog.query] [node-1] [my_index][0]
took[1.2s], took_millis[1200], total_hits[0], types[], stats[],
search_type[QUERY_THEN_FETCH], total_shards[5],
source[{"query":{"match":{"title":"elasticsearch"}}}], id[]
```

**注意事项与最佳实践**

- **阈值分级**：`warn > info > debug > trace`，生产环境建议 `warn` 级别设为 2s-5s，`info` 级别设为 1s-2s。避免所有级别全开，日志量过大。
- **Query 与 Fetch 分阶段**：Query 阶段负责定位文档 ID，Fetch 阶段负责获取完整文档。二者分开监控，便于定位瓶颈。
- **`slowlog.source`**：设为 `1000` 可记录原始文档前 1000 个字符，便于排查问题文档，但会增加磁盘 I/O。
- **动态修改**：慢日志阈值可通过 `_settings` API 动态修改，无需重启或关闭索引。
- **日志文件位置**：慢日志输出到 `{path.logs}/{cluster_name}_index_search_slowlog.log` 和 `{cluster_name}_index_indexing_slowlog.log`。

### 线程池监控

**概念定义**

Elasticsearch 使用线程池（Thread Pool）管理各种操作的并发执行。每种操作类型（搜索、写入、刷新、段合并等）有独立的线程池，线程池饱和会导致请求被拒绝（`EsRejectedExecutionException`）。

**核心参数**

| 线程池 | 类型 | 核心线程数 | 最大线程数 | 队列大小 | 说明 |
|--------|------|-----------|-----------|---------|------|
| `search` | `fixed` | `处理器数 × 3/2 + 1` | - | 1000 | 搜索/计数/建议请求 |
| `write` | `fixed` | `处理器数` | - | 10000 | 索引/删除/更新/Bulk |
| `get` | `fixed` | `处理器数` | - | 1000 | Get-by-ID 请求 |
| `analyze` | `fixed` | 1 | - | 16 | 分词请求 |
| `flush` | `scaling` | `处理器数/2` | 自动 | - | Flush 操作 |
| `refresh` | `scaling` | `处理器数/10` | 自动 | - | Refresh 操作 |
| `force_merge` | `fixed` | `处理器数/8` | - | - | Force Merge |
| `snapshot` | `scaling` | `处理器数/2` | 自动 | - | 快照操作 |
| `management` | `scaling` | 1 | 5 | - | 集群管理操作 |
| `generic` | `scaling` | 4 | 128 | - | 通用操作 |
| `warmer` | `scaling` | `处理器数/4` | 自动 | - | 索引预热 |

**配置示例**

```yaml
# elasticsearch.yml — 自定义线程池大小
thread_pool:
  search:
    size: 30
    queue_size: 1000
  write:
    size: 16
    queue_size: 10000
  force_merge:
    size: 2
```

```bash
# 查看线程池状态
GET /_cat/thread_pool?v&h=node_name,name,active,rejected,completed,queue,queue_size

# 查看特定线程池详情
GET /_cat/thread_pool/search?v&h=node_name,name,active,rejected,completed,queue,queue_size

# 使用 _nodes/stats 查看线程池
GET /_nodes/stats/thread_pool?pretty

# 查看热点线程
GET /_nodes/hot_threads?interval=10s&threads=3&type=cpu
```

#### 关键指标

| 指标 | 含义 | 告警条件 |
|------|------|----------|
| `active` | 当前正在执行的任务数 | 持续接近 `size` |
| `queue` | 当前队列中等待的任务数 | 持续 > 0 |
| `rejected` | 累计拒绝的任务数 | 增长率 > 0 |
| `completed` | 累计完成的任务数 | 用于计算吞吐量 |

**注意事项与最佳实践**

- **`rejected` 是硬指标**：一旦 `rejected > 0`，说明线程池已饱和，客户端会收到 `EsRejectedExecutionException`。需立即扩容或优化查询。
- **`write` 线程池拒绝**：通常是 Bulk 写入量过大，考虑增加 `write.size` 或降低 Bulk 频率。
- **`search` 线程池拒绝**：通常是慢查询堆积，先排查慢查询日志，再考虑增加 `search.size` 或添加协调节点。
- **`hot_threads` API**：`GET /_nodes/hot_threads` 可查看当前耗时最长的线程，是排查 CPU 尖峰的利器。
- **线程池大小不可动态修改**：`size` 参数在 `elasticsearch.yml` 中配置，修改后需重启节点。

### Kibana Stack Monitoring

**概念定义**

Kibana Stack Monitoring 是 Elastic Stack 自带的监控功能，通过 Metricbeat 或 Elastic Agent 采集集群指标，在 Kibana UI 中提供可视化仪表盘、告警和集群拓扑图。

**核心参数**

| 参数 | 说明 |
|------|------|
| `xpack.monitoring.collection.enabled` | 是否启用监控数据采集（默认 true） |
| `xpack.monitoring.collection.interval` | 采集间隔（默认 10s） |
| `xpack.monitoring.elasticsearch.collection.enabled` | 是否采集 ES 指标 |
| `xpack.monitoring.history.duration` | 监控数据保留时间（默认 7d） |

**配置示例**

```yaml
# elasticsearch.yml
xpack.monitoring.collection.enabled: true
xpack.monitoring.collection.interval: 30s
xpack.monitoring.history.duration: 30d

# kibana.yml
xpack.monitoring.enabled: true
xpack.monitoring.kibana.collection.enabled: true
xpack.monitoring.kibana.collection.interval: 30000
```

#### 监控仪表盘内容

| 仪表盘 | 内容 |
|--------|------|
| **集群概览** | 节点数、索引数、分片数、文档数、集群状态 |
| **节点概览** | JVM Heap、CPU、内存、磁盘、负载、网络流量 |
| **索引概览** | 索引速率、搜索速率、查询延迟、索引延迟 |
| **分片概览** | 分片分布、未分配分片、重定位分片 |
| **日志** | 集群日志、慢日志、GC 日志聚合 |

**注意事项与最佳实践**

- **独立监控集群**：生产环境建议使用独立的监控集群（Monitoring Cluster）存储监控数据，避免监控数据影响生产集群性能。
- **数据保留**：默认保留 7 天，生产环境建议调整为 30 天以上，便于趋势分析和容量规划。
- **Metricbeat 替代**：8.x 推荐使用 Elastic Agent + Metricbeat 采集监控数据，相比于直接由 ES 自采集，耦合度更低。
- **告警集成**：Stack Monitoring 支持与 Watcher 集成，可配置自动告警（如 CPU > 90%、磁盘 > 85%）。

## 安全认证

### 8.x 默认安全

**概念定义**

Elasticsearch 8.x 默认启用安全功能（Security），无需额外安装 X-Pack 插件。首次启动时自动生成证书和 `elastic` 用户密码，强制要求 TLS 加密和用户认证。

**核心参数**

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `xpack.security.enabled` | `true` | 安全功能总开关 |
| `xpack.security.enrollment.enabled` | `true` | 节点注册令牌功能 |
| `xpack.security.transport.ssl.enabled` | `true` | Transport 层 TLS 加密 |
| `xpack.security.http.ssl.enabled` | `true` | HTTP 层 TLS 加密 |
| `xpack.security.autoconfiguration.enabled` | `true` | 首次启动自动配置安全 |

**配置示例**

```bash
# 首次启动时自动生成证书和密码，终端输出类似：
# Elasticsearch security features have been automatically configured!
# -> Password for the elastic user: XXXXXXXXXXXX
# -> HTTP CA certificate fingerprint: XXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX

# 重置 elastic 密码
bin/elasticsearch-reset-password -u elastic

# 生成节点注册令牌
bin/elasticsearch-create-enrollment-token -s node

# 生成 Kibana 注册令牌
bin/elasticsearch-create-enrollment-token -s kibana
```

```yaml
# elasticsearch.yml
xpack.security.enabled: true
xpack.security.enrollment.enabled: true

# 传输层 TLS
xpack.security.transport.ssl.enabled: true
xpack.security.transport.ssl.verification_mode: certificate
xpack.security.transport.ssl.keystore.path: certs/transport.p12
xpack.security.transport.ssl.truststore.path: certs/transport.p12

# HTTP 层 TLS
xpack.security.http.ssl.enabled: true
xpack.security.http.ssl.keystore.path: certs/http.p12
xpack.security.http.ssl.truststore.path: certs/http.p12
```

**注意事项与最佳实践**

- **密码保管**：首次启动生成的 `elastic` 密码需妥善保管，丢失后只能通过 `elasticsearch-reset-password` 工具重置。
- **开发环境关闭安全**：仅限本地开发，设置 `xpack.security.enabled: false` 和 `xpack.security.enrollment.enabled: false`。生产环境绝对禁止。
- **HTTP 层 TLS 可选**：内部网络可关闭 HTTP TLS（`xpack.security.http.ssl.enabled: false`），但 Transport 层 TLS 必须保留。
- **客户端连接变化**：8.x 启用安全后，客户端需使用 `https://` 协议并提供认证凭据。

### TLS/HTTPS 配置

**概念定义**

Elasticsearch 8.x 的安全通信分为两层：**Transport 层**（节点间通信，端口 9300）和 **HTTP 层**（客户端 REST API 通信，端口 9200）。TLS 在两层均可独立配置。

**核心参数**

| 参数 | 说明 |
|------|------|
| `xpack.security.transport.ssl.enabled` | Transport 层 TLS 开关 |
| `xpack.security.transport.ssl.verification_mode` | 验证模式：`full` / `certificate` / `none` |
| `xpack.security.transport.ssl.keystore.path` | 密钥库路径（PKCS#12 格式） |
| `xpack.security.transport.ssl.truststore.path` | 信任库路径 |
| `xpack.security.http.ssl.enabled` | HTTP 层 TLS 开关 |
| `xpack.security.http.ssl.keystore.path` | HTTP 密钥库路径 |
| `xpack.security.http.ssl.certificate_authorities` | CA 证书路径 |

**配置示例**

```yaml
# elasticsearch.yml — 手动 TLS 配置
# Transport 层
xpack.security.transport.ssl.enabled: true
xpack.security.transport.ssl.verification_mode: certificate
xpack.security.transport.ssl.keystore.path: /etc/elasticsearch/certs/elastic-certificates.p12
xpack.security.transport.ssl.truststore.path: /etc/elasticsearch/certs/elastic-certificates.p12

# HTTP 层
xpack.security.http.ssl.enabled: true
xpack.security.http.ssl.keystore.path: /etc/elasticsearch/certs/elastic-certificates.p12
xpack.security.http.ssl.truststore.path: /etc/elasticsearch/certs/elastic-certificates.p12
```

```bash
# 使用 elasticsearch-certutil 生成证书（推荐）
# 生成 CA 证书
bin/elasticsearch-certutil ca

# 基于 CA 生成节点证书（PKCS#12 格式）
bin/elasticsearch-certutil cert --ca elastic-stack-ca.p12

# 生成 HTTP 专用证书
bin/elasticsearch-certutil http

# 查看证书内容
bin/elasticsearch-certutil cert --ca elastic-stack-ca.p12 --silent
```

**注意事项与最佳实践**

- **`verification_mode`**：生产环境必须设为 `full`（验证主机名和证书链），`certificate` 仅验证证书不验证主机名，`none` 仅用于调试。
- **证书过期**：Elasticsearch 自签名证书默认有效期 3 年，需提前规划证书轮换。使用 `elasticsearch-certutil` 可指定有效期。
- **证书分发**：所有节点必须使用同一 CA 签发的证书，密钥库密码需一致。
- **客户端 CA 证书**：生产环境客户端应使用 CA 证书验证，而非信任所有证书。

- **禁用不需要的用户**：安全最佳实践，禁用未使用的内置用户。

### 自定义角色（RBAC）

**概念定义**

RBAC（Role-Based Access Control）基于角色的访问控制。通过定义角色（Role）并分配给用户，实现对集群、索引、文档的精细化权限管理。

**核心参数**

| 权限类型 | 说明 |
|----------|------|
| `cluster` | 集群级权限（如 `monitor`、`manage`、`all`、`manage_security`） |
| `indices` | 索引级权限（如 `read`、`write`、`create_index`、`delete_index`） |
| `applications` | 应用级权限（如 Kibana 功能权限） |
| `run_as` | 允许当前用户以其他用户身份执行操作 |

**配置示例**

```json
## 创建只读角色——可读取 logs-* 索引
POST /_security/role/logs_reader
{
  "cluster": ["monitor"],
  "indices": [
    {
      "names": ["logs-*"],
      "privileges": ["read", "view_index_metadata"],
      "allow_restricted_indices": false
    }
  ]
}

## 创建日志写入角色——可写入 logs-* 索引
POST /_security/role/logs_writer
{
  "cluster": ["monitor", "manage_ilm"],
  "indices": [
    {
      "names": ["logs-*"],
      "privileges": ["create_index", "index", "write", "manage"],
      "allow_restricted_indices": false
    }
  ]
}

## 创建应用开发者角色——组合多个权限
POST /_security/role/app_developer
{
  "cluster": ["monitor", "manage_index_templates"],
  "indices": [
    {
      "names": ["app-*"],
      "privileges": ["all"],
      "allow_restricted_indices": false
    },
    {
      "names": [".monitoring-*"],
      "privileges": ["read", "view_index_metadata"],
      "allow_restricted_indices": true
    }
  ],
  "applications": [
    {
      "application": "kibana-.kibana",
      "privileges": ["feature_discover.read", "feature_dashboard.read"],
      "resources": ["space:default"]
    }
  ]
}

## 创建用户并分配角色
POST /_security/user/app_user
{
  "password": "secure_password",
  "roles": ["app_developer", "logs_reader"],
  "full_name": "Application Developer",
  "email": "dev@example.com",
  "metadata": {
    "department": "engineering"
  }
}

## 验证用户权限
POST /_security/user/_has_privileges
{
  "cluster": ["monitor"],
  "index": [
    {
      "names": ["app-2025"],
      "privileges": ["read", "write"]
    }
  ]
}
```

**注意事项与最佳实践**

- **最小权限原则**：仅授予用户完成工作所需的最小权限。避免使用 `superuser` 或 `all` 权限。
- **索引模式匹配**：`names` 支持通配符（`*`），如 `logs-*`、`app-*`。注意避免匹配到系统索引（`.` 开头的索引）。
- **`allow_restricted_indices`**：访问 `.security`、`.monitoring` 等系统索引需显式设为 `true`。
- **权限测试**：使用 `/_security/user/_has_privileges` 验证权限配置是否符合预期。
- **角色模板**：通过 `/_index_template` 预设角色，实现自动化权限管理。

### 字段级安全（FLS）

**概念定义**

字段级安全（Field Level Security，FLS）允许在角色定义中限制用户对特定字段的访问权限（可读/不可读）。适用于敏感字段脱敏场景（如手机号、身份证号、薪资等）。

**核心参数**

| 参数 | 说明 |
|------|------|
| `indices[].field_security.grant` | 允许访问的字段列表（白名单） |
| `indices[].field_security.except` | 排除的字段列表（黑名单） |

`grant` 和 `except` 不能同时使用。使用 `grant` 时，仅指定字段可见；使用 `except` 时，除指定字段外全部可见。

**配置示例**

```json
## 创建角色——隐藏敏感字段
POST /_security/role/hr_restricted
{
  "indices": [
    {
      "names": ["employees"],
      "privileges": ["read"],
      "field_security": {
        "grant": ["name", "department", "position", "email"]
      }
    }
  ]
}

## 排除特定字段（黑名单模式）
POST /_security/role/hr_public
{
  "indices": [
    {
      "names": ["employees"],
      "privileges": ["read"],
      "field_security": {
        "except": ["salary", "ssn", "bank_account", "phone_number"]
      }
    }
  ]
}

## 多索引不同字段权限
POST /_security/role/multi_index_role
{
  "indices": [
    {
      "names": ["public-*"],
      "privileges": ["read"],
      "field_security": {
        "grant": ["*"]
      }
    },
    {
      "names": ["confidential-*"],
      "privileges": ["read"],
      "field_security": {
        "grant": ["title", "summary", "author", "publish_date"]
      }
    }
  ]
}
```

#### 响应行为

```bash
# 查询时，被限制的字段不会出现在 _source 中
# 但可以通过 docvalue_fields 或 stored_fields 访问（如果字段被存储）
# 被限制字段在聚合、排序、高亮等操作中也不可用
```

**注意事项与最佳实践**

- **`grant` 模式下 `_source` 行为**：被限制的字段不会出现在 `_source` 中，但 Elasticsearch 仍会读取整个 `_source` 后过滤，有一定性能开销。
- **`fields` 参数绕过**：即使使用 `fields` 参数请求受限字段，也不会返回其值。
- **与 DLS 组合**：FLS 可与文档级安全（DLS）组合使用，实现行列双向控制。
- **Kibana 兼容性**：FLS 限制的字段在 Kibana Discover 中不可见，但可能导致某些可视化报错，需提前规划。
- **性能影响**：FLS 在查询时过滤字段，额外开销较小（通常 < 5%），但在大文档场景下建议控制 `_source` 大小。

### 文档级安全（DLS）

**概念定义**

文档级安全（Document Level Security，DLS）在角色定义中通过 **查询模板** 限制用户只能访问满足特定条件的文档。本质是在每次查询时自动附加一个过滤查询（Filter Query）。

**核心参数**

| 参数 | 说明 |
|------|------|
| `indices[].query` | 文档级过滤查询（Elasticsearch Query DSL） |
| `indices[].query.template` | 使用 Mustache 模板语法，支持动态变量（如 `\{\{_user.username}}`） |

**配置示例**

```json
## 创建角色——用户只能查看自己部门的文档
POST /_security/role/dept_user
{
  "indices": [
    {
      "names": ["company-*"],
      "privileges": ["read"],
      "query": {
        "template": {
          "source": "{\"term\": {\"department.keyword\": \"\{\{_user.metadata.department}}\"}}"
        }
      }
    }
  ]
}

## 创建用户并设置元数据
POST /_security/user/alice
{
  "password": "password123",
  "roles": ["dept_user"],
  "metadata": {
    "department": "engineering"
  }
}

## 静态查询模板——限制用户只能看已发布文档
POST /_security/role/published_only
{
  "indices": [
    {
      "names": ["articles-*"],
      "privileges": ["read"],
      "query": {
        "bool": {
          "filter": [
            {"term": {"status": "published"}},
            {"range": {"publish_date": {"lte": "now"}}}
          ]
        }
      }
    }
  ]
}

## 多租户场景——按 tenant_id 隔离
POST /_security/role/tenant_user
{
  "indices": [
    {
      "names": ["tenant-*"],
      "privileges": ["read", "write"],
      "query": {
        "template": {
          "source": "{\"term\": {\"tenant_id\": \"\{\{_user.metadata.tenant_id}}\"}}"
        }
      }
    }
  ]
}
```

#### 可用模板变量

| 变量 | 说明 |
|------|------|
| `\{\{_user.username}}` | 当前认证用户名 |
| `\{\{_user.full_name}}` | 用户全名 |
| `\{\{_user.email}}` | 用户邮箱 |
| `\{\{_user.metadata.key}}` | 用户元数据字段 |
| `\{\{_user.realm}}` | 认证域名称 |

**注意事项与最佳实践**

- **DLS 查询必须高效**：DLS 查询在每次请求时执行，复杂查询会显著拖慢性能。建议使用 `term`、`terms` 等高效过滤。
- **与写入权限结合**：DLS 通常与写入权限结合，确保用户只能写入自己有权访问的数据。例如，写入时强制设置 `tenant_id` 字段。
- **Kibana 兼容性**：DLS 对 Kibana Discover 和 Dashboard 透明，用户只能看到被授权的文档。
- **调试 DLS**：使用 `/_security/user/_has_privileges` 验证权限，或使用 `?filter_path` 验证返回结果。
- **性能影响**：DLS 以 `bool.filter` 形式附加到查询中，性能影响取决于过滤条件复杂度，通常 < 10%。

### API Key 管理

**概念定义**

API Key 是 Elasticsearch 8.x 提供的轻量级认证机制，用于替代用户名密码进行 API 调用。API Key 具有独立的权限范围（可小于创建者权限）和过期时间，适合服务间调用和第三方集成。

**核心参数**

| 参数 | 说明 |
|------|------|
| `name` | API Key 名称（唯一标识） |
| `role_descriptors` | 权限范围（角色定义，可小于创建者权限） |
| `expiration` | 过期时间（如 `1d`、`30d`、`1y`），不设则永不过期 |
| `metadata` | 自定义元数据 |

**配置示例**

```bash
# 创建 API Key（基础）
POST /_security/api_key
{
  "name": "my-api-key",
  "expiration": "30d",
  "role_descriptors": {
    "logs_reader_role": {
      "cluster": ["monitor"],
      "indices": [
        {
          "names": ["logs-*"],
          "privileges": ["read", "view_index_metadata"]
        }
      ]
    }
  }
}
# 响应：
# {
#   "id": "VuaCfGcBCXkZ5BpN1234",
#   "name": "my-api-key",
#   "api_key": "ABC123...XYZ",
#   "encoded": "base64(id:api_key)"
# }

# 使用 API Key 发起请求
# 方式一：Authorization Header
curl -H "Authorization: ApiKey base64(id:api_key)" \
  https://localhost:9200/_cluster/health

# 方式二：使用 encoded 值
curl -H "Authorization: ApiKey VuaCfGcBCXkZ5BpN1234:ABC123...XYZ" \
  https://localhost:9200/

# 查看所有 API Key
GET /_security/api_key

# 查询特定 API Key
GET /_security/api_key?name=my-api-key&owner=true

# 吊销 API Key
DELETE /_security/api_key
{
  "name": "my-api-key"
}

# 批量吊销
DELETE /_security/api_key
{
  "ids": ["VuaCfGcBCXkZ5BpN1234", "VuaCfGcBCXkZ5BpN5678"]
}
```

**注意事项与最佳实践**

- **权限最小化**：API Key 的 `role_descriptors` 应遵循最小权限原则，仅授予必要权限。若未指定 `role_descriptors`，则继承创建者的全部权限。
- **过期时间**：生产环境 API Key 必须设置过期时间，建议 30-90 天，到期前自动轮换。
- **密钥保管**：API Key 仅在创建时返回一次，丢失后无法找回，只能吊销后重新创建。
- **审计**：API Key 的操作会被审计日志记录，可通过 `_security/api_key` 查询使用情况。
- **跨集群**：API Key 可用于 CCS（Cross Cluster Search）场景中的远程集群认证。

### Service Account Token

**概念定义**

Service Account（服务账户）是 8.x 引入的机器身份认证机制，专门为 Elastic Stack 内部组件（如 Kibana、Fleet Server、Beats）提供预定义的、范围受限的访问权限。与 API Key 不同，Service Account 的权限由 Elasticsearch 预定义，不可自定义。

**核心参数**

| 参数 | 说明 |
|------|------|
| `namespace` | 服务账户命名空间（如 `elastic`） |
| `service` | 服务名称（如 `kibana`、`fleet-server`） |
| `name` | Token 名称（自定义） |

#### 内置服务账户

| 服务账户 | 命名空间 | 用途 |
|----------|----------|------|
| `elastic/kibana` | `elastic` | Kibana 服务账户 |
| `elastic/fleet-server` | `elastic` | Fleet Server 服务账户 |
| `elastic/enterprise-search-server` | `elastic` | Enterprise Search 服务账户 |

**配置示例**

```bash
# 创建 Service Account Token
POST /_security/service/elastic/kibana/credential/token/kibana-token-1
# 响应：
# {
#   "created": true,
#   "token": {
#     "name": "kibana-token-1",
#     "value": "AAEAAWVsYXN0..."
#   }
# }

# 查看所有 Service Account
GET /_security/service

# 查看特定 Service Account 的 Token 列表
GET /_security/service/elastic/kibana/credential

# 删除 Service Account Token
DELETE /_security/service/elastic/kibana/credential/token/kibana-token-1

# 在 Kibana 中配置 Service Account Token
# kibana.yml
elasticsearch.serviceAccountToken: "AAEAAWVsYXN0..."
```

**注意事项与最佳实践**

- **权限不可自定义**：Service Account 的权限由 Elasticsearch 预定义，无法通过 API 修改。如需自定义权限，使用 API Key。
- **Token 数量限制**：每个 Service Account 最多创建 20 个 Token。
- **Token 保管**：与 API Key 一样，Token 值仅在创建时返回一次。
- **适用场景**：Service Account 适用于 Elastic Stack 内部组件间的认证，不适用于自定义应用程序。

### 审计日志

**概念定义**

审计日志（Audit Logging）记录对 Elasticsearch 集群的所有安全相关事件，包括认证成功/失败、权限拒绝、索引操作、配置变更等。审计日志是安全合规（如 SOC2、HIPAA）的必要组件。

**核心参数**

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `xpack.security.audit.enabled` | `false` | 审计日志开关 |
| `xpack.security.audit.logfile.events.include` | - | 包含的事件类型列表 |
| `xpack.security.audit.logfile.events.exclude` | - | 排除的事件类型列表 |
| `xpack.security.audit.logfile.events.emit_request_body` | `false` | 是否记录请求体 |
| `xpack.security.audit.logfile.emit_node_name` | `true` | 是否记录节点名称 |
| `xpack.security.audit.logfile.emit_node_host_address` | `false` | 是否记录节点主机地址 |
| `xpack.security.audit.logfile.emit_node_host_name` | `false` | 是否记录节点主机名 |
| `xpack.security.audit.logfile.emit_node_id` | `true` | 是否记录节点 ID |

#### 审计事件类型

| 事件类型 | 说明 |
|----------|------|
| `access_denied` | 认证成功但权限不足（即 403） |
| `access_granted` | 认证成功且有权限 |
| `anonymous_access_denied` | 匿名访问被拒绝 |
| `authentication_failed` | 认证失败（错误密码/Token） |
| `authentication_success` | 认证成功 |
| `connection_denied` | 连接被拒绝（IP 过滤） |
| `connection_granted` | 连接被允许 |
| `tampered_request` | 请求被篡改 |
| `run_as_denied` | Run-As 被拒绝 |
| `run_as_granted` | Run-As 被允许 |
| `security_config_change` | 安全配置变更 |

**配置示例**

```yaml
# elasticsearch.yml
xpack.security.audit.enabled: true

# 审计日志输出配置
xpack.security.audit.logfile.events.include:
  - access_denied
  - authentication_failed
  - connection_denied
  - security_config_change
  - tampered_request

xpack.security.audit.logfile.events.exclude:
  - access_granted
  - authentication_success

xpack.security.audit.logfile.events.emit_request_body: true
xpack.security.audit.logfile.emit_node_name: true
xpack.security.audit.logfile.emit_node_host_address: true
xpack.security.audit.logfile.emit_node_id: true

# 日志滚动策略
xpack.security.audit.logfile.rollover.every: daily
xpack.security.audit.logfile.rollover.max_files: 30
xpack.security.audit.logfile.rollover.size: 1gb
```

#### 审计日志格式示例

```
[2025-01-15T10:30:00,123][node-1][access_denied]
origin_type=rest, origin_address=10.0.0.100:54321,
principal=app_user, realm=reserved,
uri=/sales-2025/_search,
request_body={"query":{"match_all":{}}},
indices=[sales-2025], action=indices:data/read/search
```

**注意事项与最佳实践**

- **`emit_request_body`**：设为 `true` 会记录完整请求体，便于排查问题，但会增加磁盘 I/O 和日志体积。生产环境建议选择性开启。
- **日志过滤**：`access_granted` 和 `authentication_success` 事件量大，建议排除，仅记录异常事件（`access_denied`、`authentication_failed`）。
- **日志存储位置**：审计日志默认输出到 `{path.logs}/{cluster_name}_audit.log`。建议使用独立磁盘或输出到外部日志系统（如 ELK、Splunk）。
- **性能影响**：审计日志对性能影响极小（< 1%），但记录大量请求体时可能增加延迟。
- **合规要求**：PCI-DSS、HIPAA 等合规场景要求审计日志保留至少 90 天。

## 快照与恢复

### Snapshot 创建

**概念定义**

快照（Snapshot）是 Elasticsearch 集群数据的备份机制，在索引/集群级别创建一致性副本。快照是增量式的，仅存储自上次快照以来的变更数据。

**核心参数**

| 参数 | 说明 |
|------|------|
| `indices` | 需快照的索引列表（支持通配符），默认所有索引 |
| `ignore_unavailable` | 是否忽略不可用索引（默认 `false`） |
| `include_global_state` | 是否包含集群全局状态（模板、ILM 策略等），默认 `true` |
| `partial` | 是否允许部分分片快照（默认 `false`） |
| `wait_for_completion` | 是否同步等待完成（默认 `false`，异步） |
| `metadata` | 自定义元数据 |

**配置示例**

```bash
# 前置：注册快照仓库
PUT /_snapshot/my_backup
{
  "type": "fs",
  "settings": {
    "location": "/mnt/backups/elasticsearch",
    "compress": true,
    "max_snapshot_bytes_per_sec": "100mb",
    "max_restore_bytes_per_sec": "100mb"
  }
}

# 创建全量快照
PUT /_snapshot/my_backup/snapshot_20250115
{
  "indices": "logs-*,metrics-*,app-*",
  "ignore_unavailable": true,
  "include_global_state": true,
  "metadata": {
    "taken_by": "admin",
    "taken_because": "pre-upgrade backup"
  }
}

# 创建指定索引快照
PUT /_snapshot/my_backup/snapshot_critical
{
  "indices": "orders-*,payments-*",
  "include_global_state": false,
  "partial": false
}

# 查看快照进度
GET /_snapshot/my_backup/snapshot_20250115/_status

# 查看快照详情
GET /_snapshot/my_backup/snapshot_20250115

# 查看所有快照
GET /_snapshot/my_backup/_all?verbose=false

# 删除快照
DELETE /_snapshot/my_backup/snapshot_20250115
```

**注意事项与最佳实践**

- **快照命名规范**：建议使用 `{type}-{date}` 格式，如 `daily-2025-01-15`、`hourly-2025-01-15-14`。
- **快照并发**：默认并发快照数为 `min(5, 数据节点数/2)`，可通过 `max_concurrent_snapshots` 调整。
- **快照频率**：生产环境建议每日全量快照 + 每小时增量快照，关键业务索引可更频繁。
- **快照前 Flush**：快照会自动触发 Flush，确保 Translog 数据写入磁盘。无需手动 Flush。
- **系统索引**：默认包含系统索引（`.security`、`.kibana` 等），可通过 `indices` 排除。

### Restore 恢复

**概念定义**

快照恢复（Restore）将快照中的数据还原到集群中，支持全量恢复和选择性恢复（指定索引、重命名索引、修改副本数等）。

**核心参数**

| 参数 | 说明 |
|------|------|
| `indices` | 需恢复的索引列表，默认快照中所有索引 |
| `rename_pattern` | 索引重命名正则匹配 |
| `rename_replacement` | 索引重命名替换字符串 |
| `include_aliases` | 是否恢复索引别名（默认 `true`） |
| `include_global_state` | 是否恢复全局状态（默认 `false`） |
| `index_settings` | 覆盖索引设置（如副本数、刷新间隔） |
| `ignore_index_settings` | 忽略的索引设置 |
| `partial` | 是否允许恢复部分分片（默认 `false`） |

**配置示例**

```bash
# 恢复全部索引
POST /_snapshot/my_backup/snapshot_20250115/_restore

# 选择性恢复指定索引
POST /_snapshot/my_backup/snapshot_20250115/_restore
{
  "indices": "orders-2025-01-*",
  "ignore_unavailable": true,
  "include_global_state": false,
  "index_settings": {
    "index.number_of_replicas": 0,
    "index.refresh_interval": "-1"
  }
}

# 恢复并重命名索引
POST /_snapshot/my_backup/snapshot_20250115/_restore
{
  "indices": "logs-2025.01.*",
  "rename_pattern": "logs-(.+)",
  "rename_replacement": "restored-logs-$1"
}

# 恢复时忽略特定设置
POST /_snapshot/my_backup/snapshot_20250115/_restore
{
  "indices": "app-*",
  "ignore_index_settings": [
    "index.routing.allocation.require.box_type",
    "index.lifecycle.name"
  ],
  "index_settings": {
    "index.number_of_replicas": 1
  }
}

# 监控恢复进度
GET /_cat/recovery/restored-logs-*?v&active_only=true

# 取消恢复
DELETE /restored-logs-2025.01.15
```

**注意事项与最佳实践**

- **恢复前关闭索引**：目标集群中存在同名索引时，需先关闭或删除，否则恢复失败。
- **`index_settings` 覆盖**：恢复时建议临时设置 `index.number_of_replicas: 0` 和 `index.refresh_interval: -1`，加快恢复速度，恢复完成后再调整。
- **集群状态**：恢复包含全局状态时，会覆盖索引模板、ILM 策略等，需谨慎操作。
- **恢复时间**：恢复时间取决于数据量、网络带宽和磁盘 I/O。可通过 `max_restore_bytes_per_sec` 限速。
- **跨集群恢复**：快照仓库可在不同集群间共享，实现跨集群恢复。

### 存储仓库

**概念定义**

快照仓库（Snapshot Repository）是快照的存储后端。Elasticsearch 支持多种仓库类型，包括本地文件系统、云对象存储和分布式文件系统。

#### 仓库类型对比

| 仓库类型 | 插件 | 适用场景 | 优点 | 缺点 |
|----------|------|----------|------|------|
| **FS** | 内置 | 共享文件系统（NFS） | 配置简单，速度快 | 需共享存储，单点故障 |
| **S3** | `repository-s3` | AWS S3 / MinIO | 高可用，低成本，无限容量 | 网络延迟 |
| **Azure** | `repository-azure` | Azure Blob Storage | 高可用，与 Azure 生态集成 | 仅限 Azure |
| **GCS** | `repository-gcs` | Google Cloud Storage | 高可用，与 GCP 生态集成 | 仅限 GCP |
| **HDFS** | `repository-hdfs` | Hadoop 集群 | 与 Hadoop 生态集成 | 依赖 Hadoop 集群，维护成本高 |
| **Source Only** | 内置 | 去重快照 | 节省空间 | 不推荐生产使用 |

**配置示例**

```bash
# FS 仓库（共享文件系统）
PUT /_snapshot/fs_backup
{
  "type": "fs",
  "settings": {
    "location": "/mnt/nfs/elasticsearch/backups",
    "compress": true,
    "chunk_size": "1g",
    "max_snapshot_bytes_per_sec": "100mb",
    "max_restore_bytes_per_sec": "100mb"
  }
}

# S3 仓库（AWS S3）
PUT /_snapshot/s3_backup
{
  "type": "s3",
  "settings": {
    "bucket": "es-backups-prod",
    "region": "us-east-1",
    "base_path": "cluster-prod",
    "compress": true,
    "chunk_size": "5gb",
    "max_retries": 5,
    "server_side_encryption": true,
    "storage_class": "STANDARD_IA"
  }
}

# S3 仓库（MinIO 兼容）
PUT /_snapshot/minio_backup
{
  "type": "s3",
  "settings": {
    "bucket": "es-backups",
    "endpoint": "http://minio:9000",
    "protocol": "http",
    "region": "us-east-1",
    "path_style_access": true,
    "access_key": "minioadmin",
    "secret_key": "minioadmin"
  }
}

# Azure 仓库
PUT /_snapshot/azure_backup
{
  "type": "azure",
  "settings": {
    "container": "es-backups",
    "base_path": "prod-cluster",
    "compress": true,
    "chunk_size": "512mb",
    "client": "default"
  }
}

# HDFS 仓库
PUT /_snapshot/hdfs_backup
{
  "type": "hdfs",
  "settings": {
    "uri": "hdfs://namenode:8020/",
    "path": "/elasticsearch/backups",
    "compress": true,
    "security.principal": "elasticsearch/_HOST@REALM"
  }
}

# 验证仓库
POST /_snapshot/fs_backup/_verify
```

**注意事项与最佳实践**

- **FS 仓库必须共享**：所有 Master 和 Data 节点必须能访问同一路径。NFS 是常见选择，但需注意 NFS 的稳定性和延迟。
- **S3 仓库最佳选择**：云环境首选 S3（或兼容 S3 的 MinIO），高可用、低成本、无需维护。
- **`chunk_size`**：大文档场景建议增大 `chunk_size`（如 `5gb`），减少快照碎片；小文档场景建议 `1gb`。
- **压缩**：`compress: true` 可节省存储空间，但略微增加 CPU 开销。建议开启。
- **限速**：`max_snapshot_bytes_per_sec` 和 `max_restore_bytes_per_sec` 防止快照/恢复操作影响正常业务。

### 增量快照

**概念定义**

增量快照是 Elasticsearch 快照的核心机制。每次快照仅存储自上次快照以来发生变化的段文件（Segment），未变化的段文件直接引用之前的快照。这使得后续快照的速度和存储开销极低。

**核心参数**

| 参数 | 说明 |
|------|------|
| `indices` | 快照索引列表，仅创建新快照时不同索引会增量 |
| `partial` | 是否允许部分分片快照（默认 `false`） |

**配置示例**

```bash
# 第一次快照（全量）
PUT /_snapshot/s3_backup/full-2025-01-01
{
  "indices": "logs-*",
  "include_global_state": true
}

# 第二次快照（增量——仅存储变更数据）
PUT /_snapshot/s3_backup/incr-2025-01-02
{
  "indices": "logs-*",
  "include_global_state": true
}

# 查看快照增量信息
GET /_snapshot/s3_backup/full-2025-01-01/_status
# total.size_in_bytes: 100GB
GET /_snapshot/s3_backup/incr-2025-01-02/_status
# total.size_in_bytes: 5GB（仅增量）

# 删除中间快照不影响其他快照
# Elasticsearch 仅删除其他快照不再引用的段
DELETE /_snapshot/s3_backup/full-2025-01-01
# incr-2025-01-02 依然完整可用（引用计数机制保证）
```

**注意事项与最佳实践**

- **引用计数**：每个段文件都有引用计数，删除快照时仅减少引用计数，当引用计数为 0 时才真正删除文件。
- **删除快照是安全的**：删除旧快照不会影响依赖它的新快照，因为共享的段文件仍被新快照引用。
- **Force Merge 影响**：对索引执行 `_forcemerge` 会生成新段，下次增量快照会包含这些段，快照体积可能增大。
- **快照链不可过深**：虽然理论上可以无限增量，但建议定期创建全量快照，避免快照链过长导致恢复时需回溯大量增量。

### Searchable Snapshot

**概念定义**

Searchable Snapshot（可搜索快照）是 7.10+ 引入的功能，允许直接将快照挂载为可搜索的索引，无需先恢复数据到本地磁盘。数据保留在快照仓库中，按需读取，大幅降低存储成本。

**核心参数**

| 参数 | 说明 |
|------|------|
| `index.store.type` | 索引存储类型（`snapshot`） |
| `index.store.snapshot.repository_name` | 快照仓库名称 |
| `index.store.snapshot.snapshot_name` | 快照名称 |
| `index.store.snapshot.index_name` | 快照中索引名称 |
| `index.store.snapshot.partial` | 是否允许部分搜索（默认 `false`） |

**配置示例**

```bash
# 方式一：挂载完整快照索引（Fully Mounted）
POST /_snapshot/s3_backup/snapshot_20250115/_mount
{
  "index": "logs-2025.01.15",
  "renamed_index": "searchable-logs-2025.01.15",
  "index_settings": {
    "index.number_of_replicas": 0
  }
}

# 方式二：部分挂载（Partially Mounted）——仅缓存热数据
POST /_snapshot/s3_backup/snapshot_20250115/_mount
{
  "index": "logs-2025.01.15",
  "renamed_index": "searchable-logs-2025.01.15",
  "index_settings": {
    "index.number_of_replicas": 0,
    "index.store.snapshot.partial": true
  }
}

# 查看已挂载的可搜索快照
GET /_cat/indices/searchable-*?v

# 删除可搜索快照索引（仅删除挂载，不删除快照）
DELETE /searchable-logs-2025.01.15

# 在 ILM 中配置 Cold 阶段使用 Searchable Snapshot
PUT /_ilm/policy/logs_policy
{
  "phases": {
    "hot": {
      "actions": { "rollover": { "max_size": "50gb", "max_age": "1d" } }
    },
    "warm": {
      "min_age": "3d",
      "actions": { "shrink": { "number_of_shards": 1 }, "forcemerge": { "max_num_segments": 1 } }
    },
    "cold": {
      "min_age": "7d",
      "actions": { "searchable_snapshot": { "snapshot_repository": "s3_backup" } }
    },
    "delete": {
      "min_age": "90d",
      "actions": { "delete": {} }
    }
  }
}
```

**注意事项与最佳实践**

- **Frozen 层**：8.x 中的 Frozen 层依赖 Searchable Snapshot，数据存储在低成本对象存储中，按需缓存到本地。
- **性能差异**：Fully Mounted 方式首次查询延迟较高（需从快照仓库读取），后续查询依赖本地缓存。Partially Mounted 仅缓存部分数据。
- **只读**：挂载的 Searchable Snapshot 索引是只读的，不能写入或修改。
- **成本优化**：Searchable Snapshot 是冷/冻结数据的理想方案，存储成本可降低 50-90%。
- **节点要求**：挂载 Searchable Snapshot 需要 `data_frozen` 角色节点，或使用 `data_content` 节点（Fully Mounted）。

### SLM（Snapshot Lifecycle Management）

**概念定义**

SLM（Snapshot Lifecycle Management）是 Elasticsearch 的快照自动管理功能，通过定义策略（Policy）自动创建、保留和删除快照，等同于快照版的 ILM。

**核心参数**

| 参数 | 说明 |
|------|------|
| `schedule` | 快照执行计划（Cron 表达式） |
| `name` | 快照命名模板，支持 `<snapshot-{now/d}>` 等日期数学表达式 |
| `repository` | 快照仓库名称 |
| `indices` | 快照索引列表（支持通配符） |
| `include_global_state` | 是否包含全局状态 |
| `retention.expire_after` | 快照过期时间（如 `30d`） |
| `retention.min_count` | 最少保留快照数量 |
| `retention.max_count` | 最多保留快照数量 |

**配置示例**

```bash
# 创建 SLM 策略
PUT /_slm/policy/daily_backup
{
  "schedule": "0 30 2 * * ?",          # 每天凌晨 2:30
  "name": "<daily-{now/d}>",           # 快照命名：daily-2025.01.15
  "repository": "s3_backup",
  "config": {
    "indices": ["logs-*", "metrics-*", "app-*", ".kibana*"],
    "ignore_unavailable": true,
    "include_global_state": true,
    "partial": false
  },
  "retention": {
    "expire_after": "30d",
    "min_count": 5,
    "max_count": 50
  }
}

# 每小时快照策略
PUT /_slm/policy/hourly_backup
{
  "schedule": "0 0 * * * ?",
  "name": "<hourly-{now/d}-{now/h}>",
  "repository": "s3_backup",
  "config": {
    "indices": ["orders-*", "payments-*"],
    "include_global_state": false
  },
  "retention": {
    "expire_after": "7d",
    "min_count": 24,
    "max_count": 168
  }
}

# 立即执行 SLM 策略
POST /_slm/policy/daily_backup/_execute

# 查看 SLM 策略
GET /_slm/policy

# 查看 SLM 执行历史
GET /_slm/stats

# 查看 SLM 状态
GET /_slm/status

# 停止 SLM
POST /_slm/stop

# 启动 SLM
POST /_slm/start

# 删除 SLM 策略
DELETE /_slm/policy/daily_backup
```

**注意事项与最佳实践**

- **Cron 表达式**：SLM 使用 Quartz Cron 格式（6 字段：秒 分 时 日 月 周），注意与 Unix Cron（5 字段）的区别。
- **保留策略优先级**：`min_count` > `max_count` > `expire_after`。当 `max_count` 与 `expire_after` 冲突时，以 `max_count` 为准。
- **快照失败处理**：SLM 策略失败后会自动重试，但不会无限重试。应监控 SLM 执行状态，避免快照缺失。
- **与 ILM 配合**：ILM 负责索引生命周期（热→冷→删除），SLM 负责快照生命周期（备份→保留→删除），二者互补。
- **多集群 SLM**：每个集群独立配置 SLM 策略，快照仓库可共享。

## 跨集群操作

### CCS（Cross Cluster Search）

**概念定义**

CCS（Cross Cluster Search）允许一个集群（协调集群）向一个或多个远程集群发起搜索请求，聚合返回结果。CCS 不复制数据，而是实时查询远程集群。

**核心参数**

| 参数 | 说明 |
|------|------|
| `cluster.remote` | 远程集群连接配置 |
| `cluster.remote.{name}.seeds` | 远程集群种子节点列表 |
| `cluster.remote.{name}.mode` | 连接模式：`sniff`（默认）/ `proxy` |
| `cluster.remote.{name}.skip_unavailable` | 远程集群不可用时是否跳过（默认 `false`） |
| `cluster.remote.{name}.transport.compress` | 是否压缩跨集群流量（默认 `true`） |

**配置示例**

```yaml
# elasticsearch.yml — 在协调集群上配置
cluster:
  remote:
    cluster_one:
      seeds:
        - 10.0.1.10:9300
        - 10.0.1.11:9300
        - 10.0.1.12:9300
      mode: sniff
      skip_unavailable: false
      transport:
        compress: true
        ping_schedule: 30s
    cluster_two:
      seeds:
        - 10.0.2.10:9300
      mode: proxy
      proxy_address: 10.0.2.100:9300
      skip_unavailable: true
```

```bash
# 查看已配置的远程集群
GET /_remote/info

# CCS 查询——在远程集群上搜索
GET /cluster_one:logs-*,cluster_two:metrics-*/_search
{
  "query": {
    "match": {
      "message": "error"
    }
  }
}

# 集群间混合搜索（本地 + 远程）
GET /local-logs,cluster_one:remote-logs/_search
{
  "query": {
    "range": {
      "@timestamp": {
        "gte": "now-1h"
      }
    }
  }
}

# 使用 CCS 且允许部分结果
GET /cluster_one:logs-*,cluster_two:logs-*/_search?ignore_unavailable=true
{
  "query": { "match_all": {} }
}

# 在 Kibana 中创建跨集群索引模式
# Index Pattern: cluster_one:logs-*,cluster_two:metrics-*,local-*
```

**注意事项与最佳实践**

- **网络延迟**：CCS 的性能取决于网络延迟。远程集群应在同一数据中心，延迟 < 10ms。跨地域 CCS 延迟会显著增加。
- **认证**：8.x 默认启用安全，远程集群间需配置 TLS 证书和认证。可使用 API Key 进行跨集群认证。
- **`skip_unavailable`**：设为 `true` 可在远程集群不可用时返回部分结果，避免单点故障影响全局搜索。
- **`sniff` vs `proxy`**：`sniff` 模式自动发现远程集群所有节点，适合节点数多的集群；`proxy` 模式通过固定地址连接，适合防火墙/负载均衡环境。
- **最小化跨集群通信**：CCS 会将查询下推到远程集群执行，仅返回打分和聚合结果，而非原始数据。但 `_source` 检索仍需传输完整文档。

### CCR（Cross Cluster Replication）

**概念定义**

CCR（Cross Cluster Replication）是跨集群数据复制功能，将 Leader 集群的索引实时复制到 Follower 集群。CCR 基于分片级别的软删除（Soft Delete）机制，实现近实时同步。

**核心参数**

| 参数 | 说明 |
|------|------|
| `leader_index` | 主集群索引名称 |
| `follower_index` | 从集群索引名称 |
| `max_read_request_operation_count` | 每次读取的最大操作数（默认 5120） |
| `max_read_request_size` | 每次读取的最大字节数（默认 32mb） |
| `max_outstanding_read_requests` | 最大并发读取请求数（默认 12） |
| `max_write_request_operation_count` | 每次写入的最大操作数（默认 5120） |
| `max_write_request_size` | 每次写入的最大字节数（默认 2gb） |
| `max_write_buffer_count` | 最大写缓冲区数量（默认 2147483647） |
| `max_write_buffer_size` | 最大写缓冲区大小（默认 512mb） |
| `max_retry_delay` | 最大重试延迟（默认 60s） |

**配置示例**

```yaml
# elasticsearch.yml — 在 Follower 集群上配置远程集群连接
cluster:
  remote:
    leader_cluster:
      seeds:
        - 10.0.0.10:9300
        - 10.0.0.11:9300
        - 10.0.0.12:9300
      mode: sniff
```

```bash
# 在 Leader 集群上创建索引
PUT /orders
{
  "settings": {
    "index.soft_deletes.enabled": true,       # CCR 必需
    "index.soft_deletes.retention_lease.period": "12h"
  }
}

# 在 Follower 集群上创建 Follower 索引
PUT /orders/_ccr/follow
{
  "remote_cluster": "leader_cluster",
  "leader_index": "orders",
  "max_read_request_operation_count": 5120,
  "max_outstanding_read_requests": 12,
  "max_write_request_operation_count": 5120,
  "max_write_buffer_size": "512mb",
  "max_retry_delay": "60s",
  "read_poll_timeout": "60s"
}

# 暂停复制
POST /orders/_ccr/pause_follow

# 恢复复制
POST /orders/_ccr/resume_follow
{
  "max_read_request_operation_count": 10240,
  "max_write_buffer_size": "1gb"
}

# 取消复制（将 Follower 转为普通索引）
POST /orders/_ccr/unfollow

# 查看 CCR 状态
GET /_ccr/stats

# 查看特定索引的 CCR 信息
GET /orders/_ccr/info
```

**注意事项与最佳实践**

- **`soft_deletes` 必须开启**：Leader 索引必须启用 `index.soft_deletes.enabled: true`（7.6+ 默认启用）。软删除保留被删除文档的历史，供 CCR 同步使用。
- **`retention_lease` 保活**：Follower 通过 Retention Lease 告知 Leader 其同步进度，Leader 据此保留对应的软删除记录。Follower 长时间离线会导致 Retention Lease 过期，需要重新全量同步。
- **Follower 索引只读**：Follower 索引是只读的，不能直接写入。需通过 `unfollow` 解除复制关系后才能写入。
- **自动跟进**：可使用 `/_ccr/auto_follow` 按模式自动创建 Follower 索引，适合日志/时序场景。
- **灾难恢复**：CCR 是异地灾备的核心方案，Leader 集群故障后可快速将 Follower 提升为写索引。

### 远程集群配置

**概念定义**

远程集群配置是 CCS 和 CCR 的前置条件，定义了本地集群如何连接到远程集群的 Transport 层。配置通过 `cluster.remote` 命名空间在 `elasticsearch.yml` 中静态设置，也可通过 API 动态管理。

**核心参数**

| 参数 | 说明 |
|------|------|
| `cluster.remote.{name}.seeds` | 远程集群种子节点地址列表 |
| `cluster.remote.{name}.mode` | `sniff`（默认）/ `proxy` |
| `cluster.remote.{name}.proxy_address` | Proxy 模式下的固定地址 |
| `cluster.remote.{name}.transport.compress` | 是否压缩（默认 `true`） |
| `cluster.remote.{name}.transport.ping_schedule` | 心跳间隔（默认 `30s`） |
| `cluster.remote.{name}.skip_unavailable` | 不可用时是否跳过 |
| `cluster.remote.{name}.cluster.remote.*.credentials` | 远程集群认证凭据（API Key） |

**配置示例**

```yaml
# elasticsearch.yml — 静态配置
cluster:
  remote:
    dc2_cluster:
      seeds:
        - es-dc2-01:9300
        - es-dc2-02:9300
        - es-dc2-03:9300
      mode: sniff
      transport:
        compress: true
        ping_schedule: 30s
      skip_unavailable: false
```

```bash
# 动态配置（通过 API，8.x 支持）
PUT /_cluster/settings
{
  "persistent": {
    "cluster.remote.dc2_cluster.seeds": [
      "es-dc2-01:9300",
      "es-dc2-02:9300",
      "es-dc2-03:9300"
    ],
    "cluster.remote.dc2_cluster.mode": "sniff",
    "cluster.remote.dc2_cluster.skip_unavailable": false,
    "cluster.remote.dc2_cluster.transport.compress": true
  }
}

# 配置跨集群认证（API Key）
PUT /_cluster/settings
{
  "persistent": {
    "cluster.remote.dc2_cluster.credentials": {
      "api_key": "base64_encoded_api_key"
    }
  }
}

# 删除远程集群配置
PUT /_cluster/settings
{
  "persistent": {
    "cluster.remote.dc2_cluster.seeds": null,
    "cluster.remote.dc2_cluster.mode": null,
    "cluster.remote.dc2_cluster.skip_unavailable": null
  }
}

# 查看远程集群连接状态
GET /_remote/info
```

**注意事项与最佳实践**

- **种子节点**：至少配置 2 个种子节点，提高连接可靠性。种子节点仅用于初始发现，连接建立后会自动发现远程集群全部节点。
- **跨集群网络**：远程集群间的 9300 端口（Transport）必须互通。生产环境建议使用专用网络或 VPN。
- **TLS 证书**：8.x 中 Transport 层 TLS 默认开启，远程集群间需共享相同的 CA 证书或配置互信。
- **认证机制**：8.x 推荐使用 API Key 进行跨集群认证，粒度更细且易于管理。也可以使用用户名密码。
- **`sniff` vs `proxy`**：如果远程集群节点在 NAT/防火墙后，使用 `proxy` 模式通过固定负载均衡地址连接。

## 性能调优

### JVM 调优

**概念定义**

Elasticsearch 运行在 JVM 上，JVM 调优直接影响集群的稳定性和性能。核心调优维度包括 Heap Size、GC 策略和 JVM 参数。

**核心参数**

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `-Xms` / `-Xmx` | 1g | Heap 初始/最大大小，生产环境应设为相同值 |
| `-XX:+UseG1GC` | 8.x 默认 | G1 垃圾回收器（8.x 默认） |
| `-XX:MaxGCPauseMillis` | 200 | G1 最大 GC 暂停目标（毫秒） |
| `-XX:G1HeapRegionSize` | 自动 | G1 Region 大小（建议 16m 或 32m） |
| `-XX:InitiatingHeapOccupancyPercent` | 45 | 触发并发标记周期的 Heap 占用率 |
| `-XX:+HeapDumpOnOutOfMemoryError` | - | OOM 时自动生成 Heap Dump |
| `-XX:HeapDumpPath` | - | Heap Dump 文件路径 |
| `-XX:+ExitOnOutOfMemoryError` | - | OOM 时自动退出（推荐） |
| `-Djava.io.tmpdir` | `/tmp` | 临时目录（建议使用独立磁盘） |

**配置示例**

```bash
# jvm.options — 生产环境推荐配置
# Heap 设置
-Xms31g
-Xmx31g

# GC 设置
-XX:+UseG1GC
-XX:MaxGCPauseMillis=200
-XX:G1HeapRegionSize=32m
-XX:InitiatingHeapOccupancyPercent=30
-XX:+ParallelRefProcEnabled
-XX:+UnlockExperimentalVMOptions
-XX:G1NewSizePercent=5
-XX:G1MaxNewSizePercent=40
-XX:G1MixedGCLiveThresholdPercent=85
-XX:+UnlockDiagnosticVMOptions
-XX:G1SummarizeRSetStatsPeriod=1

# 内存保护
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/var/log/elasticsearch/heapdump.hprof
-XX:+ExitOnOutOfMemoryError
-XX:ErrorFile=/var/log/elasticsearch/hs_err_pid%p.log

# GC 日志
-Xlog:gc*,gc+age=trace,safepoint:file=/var/log/elasticsearch/gc.log:utctime,pid,tags:filecount=32,filesize=64m

# 其他
-Djava.io.tmpdir=/data/elasticsearch/tmp
-Djdk.io.permissionsUseCanonicalPath=true
```

**注意事项与最佳实践**

- **Heap 不超过 32 GB**：`-Xms` 和 `-Xmx` 必须设为相同值，防止 Heap 动态调整带来的性能抖动。31 GB 是安全值。超过 32 GB 后指针压缩失效，实际内存利用率下降约 30%。
- **G1 GC 是 8.x 默认**：G1 比 CMS 更适合大 Heap 和低延迟场景。JDK 21（8.x 捆绑）的 G1 已非常成熟。
- **`InitiatingHeapOccupancyPercent`**：默认 45，建议调低至 30，使 G1 更早开始并发标记，减少 Full GC 概率。
- **GC 日志**：生产环境必须开启 GC 日志，便于事后分析 GC 行为。使用 `-Xlog` 统一日志格式（JDK 9+）。
- **`ExitOnOutOfMemoryError`**：强烈建议开启，OOM 后自动退出，由编排系统（K8S/systemd）重启，避免节点处于半死不活状态。

### 写入性能优化

**概念定义**

写入性能优化针对索引（Indexing）和批量写入（Bulk）操作的吞吐量调优，涉及客户端策略、索引设置、Translog 配置和硬件层面。

**核心参数**

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `index.refresh_interval` | `1s` | 刷新间隔（使文档可搜索），写入密集时可调大 |
| `index.translog.durability` | `request` | Translog 持久化策略：`request` / `async` |
| `index.translog.sync_interval` | `5s` | `async` 模式下的同步间隔 |
| `index.translog.flush_threshold_size` | `512mb` | Translog 触发 Flush 的大小阈值 |
| `index.number_of_replicas` | `1` | 写入时可临时设为 0，写入完成后恢复 |
| `indices.memory.index_buffer_size` | `10%` | 索引缓冲区占 Heap 的比例 |
| `bulk.queue_size` | `thread_pool.write.queue_size` | Bulk 请求队列大小 |

**配置示例**

```bash
# 写入优化索引模板
PUT /_index_template/high_throughput
{
  "index_patterns": ["logs-*", "metrics-*"],
  "template": {
    "settings": {
      "index.refresh_interval": "30s",
      "index.translog.durability": "async",
      "index.translog.sync_interval": "30s",
      "index.translog.flush_threshold_size": "1gb",
      "index.number_of_replicas": 0,
      "index.number_of_shards": 5,
      "index.merge.scheduler.max_thread_count": 1
    },
    "mappings": {
      "dynamic": false,
      "_source": {
        "enabled": true
      }
    }
  }
}

# 写入完成后恢复设置
PUT /logs-2025.01.15/_settings
{
  "index.number_of_replicas": 1,
  "index.refresh_interval": "5s"
}
```

#### 客户端 Bulk 优化

**注意事项与最佳实践**

- **Bulk 大小权衡**：Bulk 批次过小（< 1 MB），网络往返开销大，吞吐量低。批次过大（> 20 MB），单次请求耗时长，内存压力大。建议 5-15 MB 或 500-2000 条文档。
- **`refresh_interval`**：写入密集时将 `refresh_interval` 设为 `30s` 或 `-1`（禁用），写入完成后恢复。每次 Refresh 都会产生新的段文件，增加 I/O 负担。
- **`translog.durability`**：设为 `async` 可大幅提升写入性能，但可能丢失最近 5s（默认 `sync_interval`）的数据。用于日志等可容忍少量丢失的场景。
- **副本数**：写入时临时将 `number_of_replicas` 设为 0，写入完成后再恢复，可减少一半写入流量。
- **`dynamic: false`**：关闭动态映射，避免字段类型推断导致映射爆炸和写入性能下降。
- **禁用 `_all` 和 `_field_names`**：8.x 中 `_all` 已移除，`_field_names` 也不再需要，但注意 `dynamic: true` 时仍可能有开销。

### 查询性能优化

**概念定义**

查询性能优化聚焦于搜索和聚合操作的响应时间（Latency）和吞吐量（Throughput），涉及缓存策略、查询优化和 Profile API 诊断。

**核心参数**

| 参数 | 说明 |
|------|------|
| `indices.queries.cache.size` | 查询缓存占 Heap 的比例（默认 10%） |
| `indices.requests.cache.size` | 请求缓存占 Heap 的比例（默认 1%） |
| `indices.fielddata.cache.size` | Fielddata 缓存占 Heap 的比例（默认无限制，实际受熔断器限制） |
| `index.queries.cache.enabled` | 是否启用查询缓存（默认 `true`） |
| `index.requests.cache.enabled` | 是否启用请求缓存（默认 `true`） |
| `index.max_result_window` | 分页深度上限（默认 10000） |

**配置示例**

```bash
# 查询缓存配置
PUT /_cluster/settings
{
  "persistent": {
    "indices.queries.cache.size": "15%",
    "indices.requests.cache.size": "2%"
  }
}

# 索引级缓存配置
PUT /my_index/_settings
{
  "index.queries.cache.enabled": true,
  "index.requests.cache.enabled": true
}

# 使用 Profile API 诊断慢查询
GET /my_index/_search
{
  "profile": true,
  "query": {
    "bool": {
      "must": [
        {"match": {"title": "elasticsearch"}},
        {"range": {"date": {"gte": "2025-01-01"}}}
      ]
    }
  }
}
```

```json
}
```

#### 查询优化策略

| 策略 | 说明 |
|------|------|
| **Filter Context 替代 Query Context** | `filter` 不计算评分，可被缓存，性能远优于 `must` |
| **`search_as_you_type` 替代 `match`** | 自动补全场景使用专用字段类型 |
| **`constant_keyword` 固定值** | 将固定值字段设为 `constant_keyword`，跳过索引和搜索 |
| **`_source` 过滤** | `_source: ["field1", "field2"]` 减少网络传输 |
| **`track_total_hits` 控制** | 设为 `false` 或限制数值（如 `10000`），避免精确计数 |
| **`preference` 路由** | 使用 `preference` 参数将相同查询路由到相同分片，利用缓存 |
| **`search_after` 替代深度分页** | 深度分页使用 `search_after` 替代 `from/size` |
| **`terms` 查询优化** | 大量词项（> 1000）使用 `terms` 查询的 `index` 模式 |

**注意事项与最佳实践**

- **查询缓存（Query Cache）**：仅对 `filter` 上下文生效，缓存的是位集（BitSet）而非结果集。适合数据量小、查询重复度高的场景。
- **请求缓存（Request Cache）**：缓存整个查询的 JSON 响应，仅对 `size=0` 的聚合查询和 `suggest` 查询生效。适合 Kibana 仪表盘等重复查询。
- **Fielddata 缓存 vs Doc Values**：8.x 中 `text` 字段默认禁用 Fielddata，聚合/排序应使用 `keyword` 类型（基于 Doc Values）。Fielddata 仅用于分词后的文本聚合。
- **Profile API 开销**：`profile: true` 会额外消耗 CPU，仅用于诊断，生产环境不要全量开启。

### 冷热分层架构

**概念定义**

冷热分层架构（Hot-Warm-Cold Architecture）根据数据访问频率将索引分布到不同硬件规格的节点上。热节点存储最近、频繁访问的数据，温/冷节点存储历史数据，通过 ILM 自动迁移。

**核心参数**

| 参数 | 说明 |
|------|------|
| `node.attr.box_type` | 节点属性，用于分片分配过滤（`hot`/`warm`/`cold`/`frozen`） |
| `index.routing.allocation.require.box_type` | 索引分配过滤条件 |
| `index.routing.allocation.include.box_type` | 索引分配包含条件 |
| `index.routing.allocation.exclude.box_type` | 索引分配排除条件 |

**配置示例**

```yaml
# Data Hot 节点
node.roles: [data_hot, data_content]
node.attr.box_type: hot
node.attr.storage: ssd

# Data Warm 节点
node.roles: [data_warm]
node.attr.box_type: warm
node.attr.storage: hdd

# Data Cold 节点
node.roles: [data_cold]
node.attr.box_type: cold
node.attr.storage: hdd

# Data Frozen 节点
node.roles: [data_frozen]
node.attr.box_type: frozen
node.attr.storage: hdd
```

```bash
# ILM 策略——冷热分层自动迁移
PUT /_ilm/policy/hot_warm_cold_delete
{
  "phases": {
    "hot": {
      "min_age": "0ms",
      "actions": {
        "rollover": {
          "max_primary_shard_size": "50gb",
          "max_age": "1d"
        },
        "set_priority": {
          "priority": 100
        }
      }
    },
    "warm": {
      "min_age": "3d",
      "actions": {
        "allocate": {
          "require": {
            "box_type": "warm"
          },
          "number_of_replicas": 1
        },
        "shrink": {
          "number_of_shards": 1
        },
        "forcemerge": {
          "max_num_segments": 1
        },
        "set_priority": {
          "priority": 50
        }
      }
    },
    "cold": {
      "min_age": "30d",
      "actions": {
        "allocate": {
          "require": {
            "box_type": "cold"
          },
          "number_of_replicas": 0
        },
        "set_priority": {
          "priority": 0
        }
      }
    },
    "delete": {
      "min_age": "90d",
      "actions": {
        "delete": {}
      }
    }
  }
}

# 将 ILM 策略绑定到索引模板
PUT /_index_template/logs_template
{
  "index_patterns": ["logs-*"],
  "template": {
    "settings": {
      "index.lifecycle.name": "hot_warm_cold_delete",
      "index.lifecycle.rollover_alias": "logs",
      "index.routing.allocation.require.box_type": "hot"
    }
  }
}
```

**注意事项与最佳实践**

- **热节点使用 SSD**：热节点是写入和查询的入口，必须使用 NVMe SSD 或 SATA SSD，确保低延迟。
- **温节点可接受 HDD**：温节点数据访问频率低，HDD 可满足需求，但建议使用 7200 RPM 企业级硬盘。
- **冷节点成本最低**：冷节点可使用大容量 HDD，并配合 Searchable Snapshot 将数据卸载到对象存储。
- **Shrink 操作**：在 Warm 阶段执行 Shrink 减少主分片数，可显著降低 Heap 开销。但 Shrink 要求索引只读，且目标分片数必须是原分片数的因子。
- **Force Merge**：在 Warm 阶段执行 Force Merge 为 1 个段，减少文件句柄和内存开销。但 Force Merge 是 I/O 密集型操作，注意控制并发。

### 索引排序

**概念定义**

索引排序（Index Sorting）在索引写入时按指定字段顺序存储文档，使得范围查询和排序操作无需在查询时排序，直接利用存储顺序即可。是 Lucene 层面提供的特性。

**核心参数**

| 参数 | 说明 |
|------|------|
| `index.sort.field` | 排序字段（支持多字段） |
| `index.sort.order` | 排序方向：`asc` / `desc` |
| `index.sort.mode` | 多值字段排序模式：`min` / `max` |
| `index.sort.missing` | 缺失值处理：`_first` / `_last` |

**配置示例**

```bash
# 创建索引时指定排序字段
PUT /events
{
  "settings": {
    "index.sort.field": ["user_id", "@timestamp"],
    "index.sort.order": ["asc", "desc"]
  },
  "mappings": {
    "properties": {
      "user_id": { "type": "keyword" },
      "@timestamp": { "type": "date" },
      "event_type": { "type": "keyword" },
      "data": { "type": "text" }
    }
  }
}

# 多字段复合排序
PUT /orders
{
  "settings": {
    "index.sort.field": ["customer_id", "order_date"],
    "index.sort.order": ["asc", "desc"],
    "index.sort.mode": ["min", "min"],
    "index.sort.missing": ["_last", "_last"]
  }
}
```

**注意事项与最佳实践**

- **排序字段不可变**：索引排序在索引创建时设定，创建后不可修改。
- **写入性能影响**：索引排序在写入时额外排序，写入性能下降约 30-50%。适用于读多写少的场景。
- **查询性能提升**：对于按排序字段的 `range` 查询和 `sort` 操作，性能提升可达 10-100 倍。对于不按排序字段的查询，无明显影响。
- **适用场景**：时序数据（按 `@timestamp` 排序）、用户维度数据（按 `user_id` 排序）、多租户数据（按 `tenant_id` 排序）。
- **与 Segment 排序**：段内排序已经完成，搜索时 Lucene 可以直接跳过不满足条件的段，实现 Early Termination。

### 段合并策略

**概念定义**

段合并（Segment Merge）是 Lucene 后台合并小段为大段的过程，直接影响搜索性能和磁盘 I/O。合并策略由 TieredMergePolicy 控制。

**核心参数**

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `index.merge.policy.max_merged_segment` | `5gb` | 合并后最大段大小 |
| `index.merge.policy.segments_per_tier` | `10` | 每层允许的段数 |
| `index.merge.policy.max_merge_at_once` | `10` | 一次合并最多段数 |
| `index.merge.policy.max_merge_at_once_explicit` | `30` | Force Merge 时一次最多合并段数 |
| `index.merge.scheduler.max_thread_count` | `Math.max(1, Math.min(4, processors/2))` | 合并线程数 |
| `index.merge.scheduler.auto_throttle` | `true` | 是否自动调节合并速度 |
| `indices.store.throttle.max_bytes_per_sec` | `40mb` | 合并 I/O 限速 |

**配置示例**

```bash
# 索引级合并策略配置
PUT /my_index/_settings
{
  "index.merge.policy.max_merged_segment": "10gb",
  "index.merge.policy.segments_per_tier": 5,
  "index.merge.policy.max_merge_at_once": 5,
  "index.merge.scheduler.max_thread_count": 1,
  "index.merge.scheduler.auto_throttle": true,
  "indices.store.throttle.max_bytes_per_sec": "100mb"
}

# 对只读索引执行 Force Merge
POST /my_index/_forcemerge?max_num_segments=1&only_expunge_deletes=false

# 仅清理已删除文档
POST /my_index/_forcemerge?only_expunge_deletes=true

# 查看段信息
GET /_cat/segments/my_index?v&h=index,shard,segment,size,size.memory,committed,searchable,version,generation
```

**注意事项与最佳实践**

- **`max_merged_segment`**：默认 5 GB，SSD 环境可增大至 10 GB，减少段总数。但大段 ( > 50 GB) 会拖慢恢复和重平衡。
- **合并线程数**：SSD 环境可设为 2-4，HDD 环境建议 1。过多线程数会导致 I/O 争抢。
- **Force Merge 时机**：仅对已不再写入的索引（如 ILM Warm 阶段）执行 Force Merge，写入密集的索引禁止 Force Merge。
- **Force Merge 开销**：Force Merge 会大量消耗 I/O 和 CPU，建议在业务低峰期执行，并使用 `max_num_segments` 控制目标段数。
- **`only_expunge_deletes`**：仅清理已删除文档，不合并段。适合快速回收空间，但不会减少段数。

## 升级与迁移

### 滚动升级

**概念定义**

滚动升级（Rolling Upgrade）是 Elasticsearch 在不中断服务的情况下，逐个节点升级到新版本的过程。集群在整个升级过程中保持可用（状态为 Yellow，因为有节点离开）。

#### 升级流程

| 步骤 | 操作 | 说明 |
|------|------|------|
| 1 | 检查弃用日志 | 查看 8.x 弃用 API，确保无兼容性问题 |
| 2 | 暂停分片分配 | `PUT /_cluster/settings {"persistent":{"cluster.routing.allocation.enable":"primaries"}}` |
| 3 | 停止非必要索引 | 暂停 ILM、SLM、Watcher、Datafeed |
| 4 | Flush 同步 | `POST /_flush/synced` |
| 5 | 关闭节点 | `systemctl stop elasticsearch` 或优雅停止 |
| 6 | 升级节点 | 替换二进制文件、更新配置 |
| 7 | 启动节点 | `systemctl start elasticsearch` |
| 8 | 等待节点加入 | `GET /_cat/health?v` 等待状态恢复 |
| 9 | 恢复分片分配 | `PUT /_cluster/settings {"persistent":{"cluster.routing.allocation.enable":null}}` |
| 10 | 重复步骤 2-9 | 对下一个节点重复 |

**配置示例**

```bash
# 步骤 1：检查弃用日志
GET /_migration/deprecations?filter_path=*.*

# 步骤 2：暂停分片分配
PUT /_cluster/settings
{
  "persistent": {
    "cluster.routing.allocation.enable": "primaries"
  }
}

# 步骤 4：同步刷新
POST /_flush/synced

# 步骤 5：优雅停止节点
# 在目标节点上执行：
systemctl stop elasticsearch

# 步骤 6：升级（替换二进制文件）
# 备份配置文件
cp -r /etc/elasticsearch /etc/elasticsearch.bak
# 安装新版本
yum install elasticsearch-8.17.0  # 或解压 tarball

# 步骤 8：监控节点重新加入
GET /_cat/nodes?v
GET /_cluster/health?wait_for_status=yellow&timeout=60s

# 步骤 9：恢复分片分配
PUT /_cluster/settings
{
  "persistent": {
    "cluster.routing.allocation.enable": null
  }
}

# 步骤 10：恢复 ILM、SLM 等
POST /_ilm/start
POST /_slm/start
```

**注意事项与最佳实践**

- **版本跨度**：Elasticsearch 仅支持相邻大版本的滚动升级（如 7.17.x -> 8.17.x）。跨大版本（如 6.x -> 8.x）必须先升级到 7.17.x。
- **Master 节点最后升级**：先升级非 Master 节点，最后升级 Master 节点，确保集群在升级期间保持 Master 稳定。
- **`synced flush` 加速恢复**：`_flush/synced` 可大幅减少节点重启后的分片恢复时间，但仅在集群稳定时有效。
- **升级前备份**：任何升级前必须创建完整快照！这是不可逆操作的唯一安全网。
- **客户端兼容性**：Java 客户端应与服务端版本匹配。elasticsearch-java 8.x 客户端可连接 7.17.x 和 8.x 服务端。

### 7.x 到 8.x 迁移要点

**概念定义**

从 Elasticsearch 7.x 迁移到 8.x 需关注一系列破坏性变更（Breaking Changes），包括 API 变更、配置变更、默认值变更和安全增强。

#### 关键变更

| 变更类别 | 7.x 行为 | 8.x 行为 | 影响 |
|----------|----------|----------|------|
| **安全默认开启** | 手动启用 X-Pack Security | 默认启用，自动生成证书和密码 | 客户端必须使用 HTTPS + 认证 |
| **API 路径变更** | `_template` / `_index_template` 共存 | 仅 `_index_template`（组合模板） | 旧版 `_template` 迁移到 `_index_template` |
| **Mapping 类型** | 默认 `_doc` 类型（7.x 已弃用） | 完全移除 Mapping Type | 所有 `_doc` 引用需移除 |
| **Discovery 配置** | `discovery.zen.*` 配置族 | 移除 `discovery.zen.*`，使用 `discovery.seed_hosts` | 配置需更新 |
| **Transport 层** | 默认不加密 | 默认 TLS 加密 | 节点间通信需证书 |
| **JDK 版本** | 捆绑 JDK 17 | 捆绑 JDK 21 | JVM 参数可能需要调整 |
| **REST API 兼容性** | 7.x 响应格式 | 某些响应格式变化 | 需检查代码中解析响应的逻辑 |
| **`_source` 默认** | `_source.enabled: true` | 不变，但 `_source` 合成模式（Synthetic Source）引入 | 可选优化 |
| **节点角色** | 通用 `data` 角色 | 细分 `data_hot`/`data_warm`/`data_cold`/`data_frozen` | 建议使用细分角色 |
| **Norms 默认** | `norms: true` | `norms: false`（`keyword` 除外） | 评分计算可能受影响 |

#### 迁移检查清单

```bash
# 1. 检查弃用 API
GET /_migration/deprecations

# 2. 迁移索引模板
## 旧版 _template 迁移到 _index_template
PUT /_index_template/my_template
{
  "index_patterns": ["my-index-*"],
  "priority": 100,
  "template": {
    "settings": { "number_of_shards": 1 },
    "mappings": { "properties": { "field": { "type": "keyword" } } }
  }
}

# 3. 更新客户端连接
# 添加认证配置（HTTPS + 用户名密码或 API Key）

# 4. 更新 Kibana 配置
# kibana.yml
elasticsearch.hosts: ["https://localhost:9200"]
elasticsearch.username: "kibana_system"
elasticsearch.password: "password"
elasticsearch.ssl.verificationMode: certificate

# 5. 验证集群健康
GET /_cluster/health
GET /_cat/nodes?v
```

**注意事项与最佳实践**

- **先在测试环境验证**：任何迁移必须在与生产环境配置一致的测试集群上先验证。
- **快照是安全网**：迁移前完整快照，迁移失败可快速回滚。
- **客户端分批迁移**：先升级 Elasticsearch 服务端，再逐步升级客户端应用。7.x 客户端可连接 8.x 服务端（兼容性有限）。
- **安全配置先行**：8.x 安全默认开启，迁移前先规划好证书和认证方案。
- **监控迁移过程**：迁移期间密切关注 `_cluster/health` 和 `_cat/recovery`。

### 蓝绿部署

**概念定义**

蓝绿部署（Blue-Green Deployment）是零停机升级策略：同时维护蓝色（旧版本）和绿色（新版本）两个集群，通过流量切换完成升级。相比滚动升级，蓝绿部署更安全，回滚更快。

**核心参数**

| 参数 | 说明 |
|------|------|
| 快照仓库 | 蓝绿集群共享的快照存储后端 |
| 负载均衡器 | 流量切换组件（HAProxy、Nginx、F5 等） |
| 数据同步方式 | 快照恢复 / CCR / 双写 |

#### 蓝绿部署流程

| 步骤 | 操作 | 说明 |
|------|------|------|
| 1 | 创建蓝集群快照 | 在蓝色集群（旧版本）创建完整快照 |
| 2 | 部署绿集群 | 部署新版本绿色集群（相同规模） |
| 3 | 从快照恢复 | 绿色集群从快照恢复数据 |
| 4 | 同步增量数据 | 使用 CCR 或双写同步蓝色集群的增量写入 |
| 5 | 验证绿集群 | 功能测试、性能测试、数据一致性校验 |
| 6 | 切换流量 | 负载均衡器将流量从蓝色集群切换到绿色集群 |
| 7 | 监控绿集群 | 观察绿色集群运行状态，确认无异常 |
| 8 | 下线蓝集群 | 确认绿色集群稳定后，下线蓝色集群 |

**配置示例**

```bash
# 步骤 1：创建蓝集群快照
PUT /_snapshot/shared_repo/blue_to_green_migration
{
  "indices": "*",
  "include_global_state": true,
  "metadata": {
    "purpose": "blue-green migration",
    "source_version": "7.17.0",
    "target_version": "8.17.0"
  }
}

# 步骤 3：在绿集群恢复快照
POST /_snapshot/shared_repo/blue_to_green_migration/_restore
{
  "indices": "app-*,logs-*,metrics-*",
  "include_global_state": false,
  "index_settings": {
    "index.number_of_replicas": 1
  }
}

# 步骤 4：使用 CCR 同步增量数据（可选）
# 在蓝集群 Leader 上创建索引
# 在绿集群 Follower 上创建 CCR 跟进
# 确保数据实时同步

# 步骤 6：负载均衡器切换示例（HAProxy）
# 修改 haproxy.cfg，将 frontend 指向新集群
# frontend es_frontend
#   bind *:9200
#   default_backend es_green_cluster
#
# backend es_green_cluster
#   server es-green-01 10.0.2.10:9200 check
#   server es-green-02 10.0.2.11:9200 check
#   server es-green-03 10.0.2.12:9200 check

# 步骤 7：验证绿集群
GET /_cluster/health
GET /_cat/indices?v
GET /_cat/nodes?v
```

**注意事项与最佳实践**

- **共享快照仓库**：蓝绿集群必须共享同一个快照仓库（如 S3），确保快照可以跨集群访问。
- **增量同步**：快照恢复后到流量切换前的时间窗口内，蓝集群仍有新数据写入。需通过 CCR 或双写机制同步增量数据。
- **DNS 切换 vs 负载均衡**：DNS 切换有 DNS 缓存延迟，建议使用负载均衡器（HAProxy / Nginx）实现秒级流量切换。
- **回滚策略**：蓝绿部署的核心优势是快速回滚——只需将流量切回蓝色集群即可。
- **成本**：蓝绿部署需要双倍硬件资源，但时间窗口通常较短（数小时至数天）。

## 常见故障排查

### 脑裂（Split Brain）

**概念定义**

脑裂是指集群中部分节点因网络分区或 GC 暂停而无法与 Master 通信，导致选举出多个 Master，形成两个或多个独立的集群。8.x 使用 Quorum 选举机制大幅降低了脑裂概率。

**核心参数**

| 参数 | 说明 |
|------|------|
| `discovery.seed_hosts` | 种子节点列表，确保所有节点可互相发现 |
| `cluster.initial_master_nodes` | 初始 Master 候选节点 |
| `discovery.find_peers_interval` | 发现对等节点间隔（默认 1s） |

#### 排查步骤

```bash
# 1. 检查集群状态
GET /_cluster/health
# 如果看到多个 Master 或节点数异常，可能是脑裂

# 2. 检查 Master 节点
GET /_cat/master?v
# 正常情况只有一个 Master

# 3. 检查各节点的集群视图
GET /_cat/nodes?v&h=name,ip,node.role,master,version
# 对比各节点看到的节点数是否一致

# 4. 检查网络连通性
# 在各节点上执行：
# telnet <other-node> 9300
# 或
# nc -zv <other-node> 9300

# 5. 检查节点日志
grep -i "master.*elected\|master.*removed\|master.*not.*discovered" \
  /var/log/elasticsearch/*.log
```

#### 恢复方法

```bash
# 方法一：重启所有节点（推荐）
# 1. 停止所有节点
# 2. 先启动应成为 Master 的节点
# 3. 再启动其他节点

# 方法二：使用 Voting Configuration Exclusion API
# 排除不应成为 Master 的节点
POST /_cluster/voting_config_exclusions/node-2
# 查看排除列表
GET /_cluster/state?filter_path=metadata.cluster_coordination.voting_config_exclusions
# 清除排除
DELETE /_cluster/voting_config_exclusions
```

**注意事项与最佳实践**

- **Master 节点数量**：始终配置 3 个 Master 专用节点（奇数），这是防止脑裂的最有效手段。
- **网络隔离**：确保 Master 节点之间的网络延迟 < 10ms，避免跨数据中心部署 Master 节点。
- **GC 暂停**：长时间 GC 暂停（> 30s）可能导致节点被误判为离线。通过 JVM 调优控制 GC 暂停时间。
- **8.x 的改进**：8.x 使用基于 Raft 的协调层，Quorum 选举自动处理，无需手动配置 `minimum_master_nodes`。

### OOM（Out of Memory）

**概念定义**

OOM（Out of Memory）指 JVM Heap 耗尽，无法分配新对象，导致节点崩溃或极度缓慢。Elasticsearch 的常见 OOM 场景包括：大聚合、深度分页、Fielddata 爆炸、段合并、Bulk 请求过大。

**核心参数**

| 参数 | 说明 |
|------|------|
| `-Xms` / `-Xmx` | JVM Heap 大小 |
| `indices.breaker.total.limit` | 父熔断器限制（默认 Heap 的 95%） |
| `indices.breaker.fielddata.limit` | Fielddata 熔断器（默认 Heap 的 40%） |
| `indices.breaker.request.limit` | 请求熔断器（默认 Heap 的 60%） |
| `indices.breaker.in_flight_requests.limit` | 进行中请求熔断器（默认 Heap 的 100%） |
| `indices.memory.index_buffer_size` | 索引缓冲区（默认 Heap 的 10%） |

#### 排查步骤

```bash
# 1. 检查 JVM Heap 使用率
GET /_cat/nodes?v&h=name,heap.percent,heap.current,heap.max,ram.percent

# 2. 检查 GC 情况
GET /_nodes/stats/jvm?pretty&filter_path=**.jvm.gc.collectors

# 3. 检查熔断器状态
GET /_nodes/stats/breaker?pretty

# 4. 检查 Fielddata 使用
GET /_cat/fielddata?v&h=node,field,size

# 5. 检查是否有大聚合
# 查看慢查询日志中的聚合查询

# 6. Heap Dump 分析（如果配置了 HeapDumpOnOutOfMemoryError）
# 使用 MAT 或 JProfiler 分析 heapdump.hprof
```

#### 常见 OOM 场景与解决方案

| 场景 | 原因 | 解决方案 |
|------|------|----------|
| **大聚合 OOM** | `terms` 聚合桶数过多，Fielddata 膨胀 | 限制 `size` 参数，使用 `execution_hint: map`，改用 `composite` 聚合 |
| **深度分页 OOM** | `from/size` 过大，需在内存中排序大量文档 | 使用 `search_after` 或 Scroll API |
| **Bulk OOM** | Bulk 请求体过大（> 100 MB） | 限制 Bulk 批次大小（5-15 MB） |
| **段合并 OOM** | 合并大段时内存不足 | 减小 `max_merged_segment`，增加节点内存 |
| **Fielddata 爆炸** | 对 `text` 字段聚合，Fielddata 无限制增长 | 对 `keyword` 字段聚合，或限制 Fielddata 缓存 |
| **请求队列堆积** | 搜索线程池队列满，请求堆积 | 优化查询，增加协调节点 |

**配置示例**

```bash
# 预防 OOM 的熔断器配置
PUT /_cluster/settings
{
  "persistent": {
    "indices.breaker.total.limit": "90%",
    "indices.breaker.fielddata.limit": "30%",
    "indices.breaker.request.limit": "50%",
    "indices.memory.index_buffer_size": "15%"
  }
}
```

**注意事项与最佳实践**

- **`ExitOnOutOfMemoryError`**：这是最重要的 OOM 防护参数。开启后 OOM 时进程自动退出，由编排系统重启，避免半死不活状态。
- **Heap 不超过 32 GB**：超过后指针压缩失效，实际可用内存反而减少。
- **监控先行**：建立 Heap 使用率和 GC 频率的监控告警，在 OOM 发生前就发现问题。
- **熔断器是最后防线**：不要依赖熔断器来限制请求，应在客户端层面控制请求大小。

### 慢查询排查

**概念定义**

慢查询排查是通过慢查询日志、Profile API 和 Hot Threads API 定位并优化执行时间过长的搜索和索引操作。

#### 排查流程

```bash
# 步骤 1：开启慢查询日志
PUT /my_index/_settings
{
  "index.search.slowlog.threshold.query.warn": "2s",
  "index.search.slowlog.threshold.query.info": "1s",
  "index.search.slowlog.threshold.fetch.warn": "1s",
  "index.search.slowlog.level": "info"
}

# 步骤 2：查看慢查询日志文件
# {path.logs}/{cluster_name}_index_search_slowlog.log

# 步骤 3：使用 Profile API 分析具体查询
GET /my_index/_search
{
  "profile": true,
  "query": {
    ## 粘贴慢查询中的 query
  }
}

# 步骤 4：使用 Hot Threads 定位 CPU 热点
GET /_nodes/hot_threads?interval=10s&threads=5&type=cpu

# 步骤 5：检查索引状态
GET /_cat/indices/my_index?v&h=health,pri,rep,docs.count,store.size

# 步骤 6：检查段信息
GET /_cat/segments/my_index?v&h=index,shard,segment,size,size.memory,committed
```

#### 常见慢查询类型与优化

| 类型 | 典型特征 | 优化方向 |
|------|----------|----------|
| **全表扫描** | `match_all` 或 `match` 无词项匹配 | 限制时间范围，添加 `filter` 条件 |
| **深度分页** | `from` 值很大 | 改用 `search_after` |
| **大聚合** | `terms` 聚合延迟高 | 限制 `size`，使用 `execution_hint` |
| **通配符/正则** | `wildcard` / `regexp` 查询 | 改用 `ngram` 分词，或限制前缀 |
| **脚本查询** | `script` 查询慢 | 索引时预处理，避免运行时计算 |
| **高基数聚合** | 唯一值过多 | 使用 `cardinality` 预聚合，或改用 `sampler` 聚合 |
| **Fetch 阶段慢** | `_source` 大，Fetch 阶段耗时长 | `_source` 过滤，或使用 `stored_fields` |

**注意事项与最佳实践**

- **慢查询日志是起点**：从慢查询日志提取耗时查询，用 Profile API 分析各阶段耗时，确定瓶颈在 Query 还是 Fetch 阶段。
- **Hot Threads 定位 CPU 热点**：`GET /_nodes/hot_threads` 显示当前 CPU 最繁忙的线程，是定位 CPU 尖峰的利器。
- **段数影响查询性能**：段数过多（> 1000/分片）会显著降速，执行 Force Merge 可减少段数。
- **缓存命中率**：`GET /_nodes/stats/indices/query_cache` 检查查询缓存命中率，低命中率需优化查询模式。

### Unassigned Shard

**概念定义**

Unassigned Shard 是指分片分配失败，无法分配到任何节点上。这是集群状态 Yellow 或 Red 的最常见原因。

**核心参数**

| 参数 | 说明 |
|------|------|
| `cluster.routing.allocation.enable` | 分片分配开关：`all` / `primaries` / `new_primaries` / `none` |
| `cluster.routing.allocation.node_concurrent_recoveries` | 单节点并发恢复数（默认 2） |
| `cluster.routing.allocation.disk.watermark.low` | 磁盘低水位线（默认 85%） |
| `cluster.routing.allocation.disk.watermark.high` | 磁盘高水位线（默认 90%） |
| `index.routing.allocation.require.*` | 索引分配过滤条件 |

#### 排查步骤

```bash
# 步骤 1：查看未分配分片
GET /_cat/shards?v&h=index,shard,prirep,state,unassigned.reason,node

# 步骤 2：使用 Allocation Explain API
GET /_cluster/allocation/explain
{
  "index": "my_index",
  "shard": 0,
  "primary": true
}

# 步骤 3：查看磁盘空间
GET /_cat/allocation?v

# 步骤 4：检查分片分配设置
GET /_cluster/settings?include_defaults=true&filter_path=*.routing.allocation.*
```

#### 常见未分配原因与解决方案

| 原因（`unassigned.reason`） | 说明 | 解决方案 |
|------|------|----------|
| `INDEX_CREATED` | 索引刚创建，副本尚未分配 | 等待自动分配 |
| `CLUSTER_RECOVERED` | 集群恢复中，分片尚未分配 | 等待恢复完成 |
| `INDEX_REOPENED` | 索引重新打开，分片分配中 | 等待自动分配 |
| `DANGLING_INDEX_IMPORTED` | 导入悬空索引 | 等待自动分配 |
| `NEW_INDEX_RESTORED` | 从快照恢复 | 等待恢复完成 |
| `NODE_LEFT` | 节点离开，分片需重新分配 | 等待自动重分配，或增加节点 |
| `ALLOCATION_FAILED` | 分配失败（磁盘/内存不足） | 检查磁盘空间、扩容节点 |
| `REPLICA_ADDED` | 副本数增加 | 等待自动分配 |
| `REALLOCATED_REPLICA` | 副本重分配 | 等待自动分配 |
| `REROUTE_CANCELLED` | 重路由被取消 | 使用 `_cluster/reroute` 重试 |

#### 强制分配命令

```bash
# 手动分配分片到指定节点（慎用）
POST /_cluster/reroute
{
  "commands": [
    {
      "allocate_replica": {
        "index": "my_index",
        "shard": 0,
        "node": "data-node-2"
      }
    }
  ]
}

# 强制分配主分片（数据可能丢失，极端情况使用）
POST /_cluster/reroute
{
  "commands": [
    {
      "allocate_stale_primary": {
        "index": "my_index",
        "shard": 0,
        "node": "data-node-1",
        "accept_data_loss": true
      }
    }
  ]
}

# 重试所有失败的分片分配
POST /_cluster/reroute?retry_failed=true
```

**注意事项与最佳实践**

- **Allocation Explain 是首选诊断工具**：`GET /_cluster/allocation/explain` 精确给出分片无法分配的原因，避免猜测。
- **磁盘水位线是常见原因**：磁盘使用率超过 `watermark.high` 时，分片停止分配。需扩容磁盘或删除旧数据。
- **`accept_data_loss` 慎用**：强制分配主分片可能导致数据丢失，仅在确认数据可以从副本恢复或可接受丢失时使用。
- **索引分片分配过滤**：检查 `index.routing.allocation.require.*` 是否设置了不存在的节点属性，导致分片无法分配。

### 集群状态 Red/Yellow

**概念定义**

集群状态分为三种：**Green**（所有主分片和副本分片已分配）、**Yellow**（所有主分片已分配但有副本未分配）、**Red**（至少一个主分片未分配，数据不完整）。

**核心参数**

| 状态 | 含义 | 数据可用性 | 写入可用性 |
|------|------|------------|------------|
| **Green** | 健康 | 完全可用 | 完全可用 |
| **Yellow** | 副本未分配 | 完全可用（副本可能丢失） | 完全可用 |
| **Red** | 主分片未分配 | 部分数据不可用 | 部分索引不可写 |

#### 排查步骤

```bash
# 1. 检查集群状态
GET /_cluster/health
GET /_cat/health?v

# 2. 查看 Red/Yellow 索引
GET /_cat/indices?v&health=yellow
GET /_cat/indices?v&health=red

# 3. 查看未分配分片
GET /_cat/shards?v&h=index,shard,prirep,state,unassigned.reason

# 4. 诊断具体分片
GET /_cluster/allocation/explain
{
  "index": "index_with_red_shard",
  "shard": 0,
  "primary": true
}

# 5. 检查节点可用性
GET /_cat/nodes?v&h=name,node.role,disk.used_percent,heap.percent
```

#### 常见原因与解决方案

| 状态 | 常见原因 | 解决方案 |
|------|----------|----------|
| **Yellow** | 单节点集群（副本无法分配） | 添加更多节点，或设置 `number_of_replicas: 0` |
| **Yellow** | 节点数不足（副本数 > 数据节点数-1） | 减少副本数或增加节点 |
| **Yellow** | 磁盘水位线触发 | 扩容磁盘，删除旧数据 |
| **Yellow** | 分片分配过滤条件过严 | 放宽过滤条件 |
| **Red** | 持有主分片的节点永久丢失 | 从快照恢复，或 `allocate_stale_primary` |
| **Red** | 磁盘故障导致数据损坏 | 从快照恢复，或接受数据丢失 |
| **Red** | 所有副本节点同时故障 | 等待节点恢复 |

**注意事项与最佳实践**

- **Yellow 不等于不可用**：Yellow 状态下读写正常，但容错能力下降。生产环境应尽快恢复 Green。
- **Red 是紧急状态**：Red 意味着数据丢失或不可用，需立即处理。先恢复数据，再排查根因。
- **单节点集群始终 Yellow**：如果 `number_of_replicas > 0` 且仅有一个节点，副本无法分配，始终 Yellow。这是正常现象。
- **监控告警**：配置集群状态监控，Yellow 超时 30 分钟或 Red 即时告警。

### 磁盘空间不足

**概念定义**

Elasticsearch 有三层磁盘水位线保护机制，防止磁盘被写满导致节点不可用。磁盘空间不足会触发分片重分配限制、索引只读保护等。

**核心参数**

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `cluster.routing.allocation.disk.watermark.low` | `85%` | 低水位线：不再分配新分片到该节点 |
| `cluster.routing.allocation.disk.watermark.high` | `90%` | 高水位线：尝试将分片迁移出该节点 |
| `cluster.routing.allocation.disk.watermark.flood_stage` | `95%` | 洪水线：所有索引设为只读（`index.blocks.read_only_allow_delete`） |
| `cluster.routing.allocation.disk.watermark.flood_stage.frozen` | `95%` | Frozen 索引洪水线 |

#### 排查步骤

```bash
# 1. 检查磁盘使用
GET /_cat/allocation?v&h=node,disk.total,disk.used,disk.avail,disk.percent

# 2. 检查是否触发只读
GET /_cat/indices?v&h=index,health,status,blocks.read_only_allow_delete

# 3. 检查磁盘水位线配置
GET /_cluster/settings?include_defaults=true&filter_path=*.routing.allocation.disk.*

# 4. 查找大索引
GET /_cat/indices?v&h=index,docs.count,store.size,pri.store.size&s=store.size:desc
```

#### 解决方案

```bash
# 方案一：扩容磁盘（根本解决）
# 增加磁盘空间或挂载新磁盘

# 方案二：清除只读锁（临时方案，仅在磁盘已释放空间后使用）
PUT /_all/_settings
{
  "index.blocks.read_only_allow_delete": null
}

# 方案三：删除旧索引
DELETE /logs-2025.01.*

# 方案四：使用 ILM 自动删除过期数据
PUT /_ilm/policy/delete_old
{
  "phases": {
    "hot": { "actions": {} },
    "delete": { "min_age": "30d", "actions": { "delete": {} } }
  }
}

# 方案五：调整水位线（临时）
PUT /_cluster/settings
{
  "transient": {
    "cluster.routing.allocation.disk.watermark.low": "90%",
    "cluster.routing.allocation.disk.watermark.high": "95%",
    "cluster.routing.allocation.disk.watermark.flood_stage": "98%"
  }
}

# 方案六：移动分片到磁盘空间充足的节点
POST /_cluster/reroute
{
  "commands": [
    {
      "move": {
        "index": "my_index", "shard": 0,
        "from_node": "node-1", "to_node": "node-2"
      }
    }
  ]
}
```

**注意事项与最佳实践**

- **`flood_stage` 只读保护**：到达 95% 水位线时，所有索引被设为只读（`index.blocks.read_only_allow_delete: true`），写入操作全部失败。这是最后防线。
- **清除只读锁的前提**：必须先释放磁盘空间，再清除只读锁。否则锁会立即被重新触发。
- **ILM 是长期方案**：使用 ILM 自动管理数据生命周期，定期删除过期数据，从根本上避免磁盘满。
- **监控磁盘趋势**：使用 Kibana Stack Monitoring 或 Prometheus 监控磁盘使用趋势，提前预警。
- **`transient` vs `persistent`**：使用 `transient` 设置临时调整水位线，集群重启后恢复默认值。

### Circuit Breaker 熔断

**概念定义**

Circuit Breaker（熔断器）是 Elasticsearch 的内存保护机制，当某种操作的内存使用超过阈值时，拒绝该操作并抛出 `CircuitBreakingException`，防止 OOM。

#### 熔断器类型

| 熔断器 | 默认限制 | 说明 |
|--------|----------|------|
| **Parent** | Heap 的 95% | 父熔断器，所有子熔断器总和的上限 |
| **Fielddata** | Heap 的 40% | Fielddata 缓存（`text` 字段聚合时使用） |
| **Request** | Heap 的 60% | 单个请求的内存使用上限 |
| **In Flight Requests** | Heap 的 100% | 所有进行中请求的内存使用总和 |
| **Accounting** | Heap 的 100% | 记账请求内存 |
| **Script Compilation** | 每 5 分钟 150 个脚本编译 | 防止脚本编译耗尽 CPU |

**核心参数**

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `indices.breaker.total.limit` | `95%` | 父熔断器限制 |
| `indices.breaker.total.use_real_memory` | `true` | 使用实际内存而非估算值 |
| `indices.breaker.fielddata.limit` | `40%` | Fielddata 熔断器 |
| `indices.breaker.fielddata.overhead` | `1.03` | Fielddata 开销系数 |
| `indices.breaker.request.limit` | `60%` | 请求熔断器 |
| `indices.breaker.request.overhead` | `1.0` | 请求开销系数 |

#### 排查步骤

```bash
# 1. 查看熔断器状态
GET /_nodes/stats/breaker?pretty

# 2. 关键字段解读
# tripped: 熔断器触发次数（> 0 说明已触发）
# limit_size_in_bytes: 熔断器限制
# estimated_size_in_bytes: 当前估算使用量

# 3. 查看错误日志
grep "CircuitBreakingException" /var/log/elasticsearch/*.log
```

#### 常见熔断场景与解决

| 场景 | 触发熔断器 | 解决方案 |
|------|-----------|----------|
| 大 `terms` 聚合 | Fielddata | 限制 `size`，对 `keyword` 字段聚合，使用 `composite` 聚合 |
| 大 `_source` 检索 | Request | `_source` 过滤，减少返回字段 |
| 深度分页 + 排序 | Request | 使用 `search_after` |
| 并发请求过多 | In Flight Requests | 限制客户端并发，增加协调节点 |
| 脚本编译过频 | Script Compilation | 缓存脚本，减少动态编译 |

**注意事项与最佳实践**

- **熔断器是保护机制，不是问题根源**：触发熔断器说明请求或配置有问题，应优化请求而非调高阈值。
- **`tripped` 计数器**：`tripped > 0` 说明熔断器已触发。建议监控此指标并设置告警。
- **`use_real_memory`**：设为 `true` 时使用实际内存使用量，更准确但开销略高。生产环境建议保持 `true`。
- **Fielddata 熔断器**：如果对 `text` 字段聚合，会大量消耗 Fielddata 缓存。强烈建议对 `keyword` 字段聚合。
