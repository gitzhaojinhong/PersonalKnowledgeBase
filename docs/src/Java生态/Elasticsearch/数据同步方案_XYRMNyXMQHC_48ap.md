## 数据同步方案

| 维度 | 双写 | MQ 异步 | 定时扫表 | Binlog 监听 |
| --- | --- | --- | --- | --- |
| 实时性 | 极高（毫秒级） | 高（10-100ms） | 低（分钟级） | 极高（毫秒级） |
| 代码侵入 | 高（改所有写入逻辑） | 中 | 无 | 无 |
| 系统复杂度 | 低 | 中 | 低 | 高 |
| 可靠性 | 中（有一致性风险） | 高（MQ 保证） | 中 | 高 |
| 适用规模 | 小型 | 中大型 | 小型/离线 | 大型 |

## 方案一：双写策略

**用业务代码同时写两端**

* 实现上，在同一个事务里先写 MySQL、再写 ES。

**优点：**

* 代码直白，代码直接控制两端，写入后立即可搜，毫秒级实时，小型系统中最容易落地。

**但问题恰恰藏在"同一个事务"里：**

* 一是**远程调用进入事务**，会大幅拉长事务时间、占用数据库连接，吞吐受限；
* 二是**一致性存在缺口**——比如 ES 写入超时但实际已成功，而数据库回滚，就会造成两端数据不一致且难以察觉；
* 三是 **ES 一旦不可用**，主业务流程直接被拖垮。因此它需要配合重试机制、幂等保证和定期对账补偿才能兜底。
* 适用场景很明确：数据量小、实时性要求极高、能接受一定一致性风险的小型系统。

## 方案二：MQ 异步消费

**把同步从业务链路中剥离：**

* 思路是数据库操作与 ES 更新解耦：业务照常写 MySQL，通过消息队列异步通知消费者更新 ES。
* 这带来三个结构性收益：业务代码侵入性降低、主流程不被 ES 阻塞、MQ 自带重试机制支撑最终一致性。

**代价是引入了新的基础设施：**

* 系统复杂度上升，消息存在延迟（毫秒级变成几十毫秒级），且必须处理**重复消费**问题——通过幂等设计保证同一条消息处理多次结果一致。

**进阶做法是本地消息表：**

* 把消息先落库、确认后再投递，保证消息不丢失。适用中大型、已有 MQ 基础设施、可接受毫秒级延迟、追求最终一致性的系统。

## 方案三：定时任务扫表

**定时批量对账式同步：**

* 定期扫描数据库表的变更记录（依赖 `update_time` 时间戳或自增 ID 做增量标识），批量同步到 ES。

**最大优点是零侵入：**

* 不改任何写入逻辑，也不引入新中间件，实现最简单。

**但它是四种方案里实时性最差的（分钟级）：**

* 频繁扫表还会给数据库带来压力，
* 而且**天然感知不到硬删除**（记录被直接 DELETE 后无从扫描），

所以常用于对实时性要求不高的离线分析、数据变更频率低的场景，或者无法修改业务代码的遗留系统。优化手段包括用自增 ID 做增量同步、分页查询避免一次性加载全表导致内存溢出。

## 方案四：监听 Binlog

**从数据库日志层面实时捕获变更：**

* 这是推荐的、也是业界公认的最佳实践。原理是让 Canal、Debezium、Maxwell 等组件伪装成 MySQL 从库，消费 binlog 日志流，实时解析每一次增删改并同步到 ES（及 Redis、数仓等多目标）。

**它的核心竞争力在于：**

* 对业务代码完全零侵入（连逻辑都不用改）、毫秒级实时、能捕获包括删除在内的所有变更、ES 故障不影响主业务。

**代价是需要引入第三方组件：**

* 开启 binlog 有轻微性能开销、还要维护监听服务自身的高可用。在大规模场景下，通常演进为 **Canal + Kafka + ES** 架构，Kafka 负责削峰填谷和消息持久化，进一步提升可靠性与吞吐量。
